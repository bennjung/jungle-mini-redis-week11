# 티켓 예매 시나리오 정의 및 Mini Redis 요구사항 해결 분석

> 이 문서는 티켓 오픈·예매 시나리오에서 요구사항을 추출하고, 현재 구현된 Mini Redis([app.py](../app.py), [storage.py](../storage.py))가 각 요구사항을 어디까지 해결하는지 분석한 검토 문서입니다. 확정된 시나리오 계약(`resc/`)을 대체하지 않습니다.

---

## 1. 티켓 예매 시나리오 정의

### 배경
인기 공연의 VIP 좌석 `S`석(예: `500`석)을 정해진 시각에 오픈한다. 오픈 직후 수천~수만 건의 잔여 좌석 조회 요청과, 실제 좌석 수보다 훨씬 많은 선착순 예매 요청이 동시에 서버로 몰린다.

### 참여 주체
- **공연 관리자(시스템)**: 좌석 수량을 초기화·관리하고 판매 마감 시 정리한다.
- **예매자(다수 동시 클라이언트)**: 잔여 좌석을 조회하고, 좌석이 남아 있으면 1매(또는 N매) 예매를 요청한다. 필요 시 예매를 취소한다.

### 시나리오 흐름

1. **Step 1 — 좌석 오픈 (초기화)**
   - 공연 시작 전 잔여 좌석을 `S`석(`500`)으로 등록한다.
2. **Step 2 — 대량 동시 잔여 좌석 조회**
   - 다수의 예매자가 동시에 잔여 좌석을 반복 조회한다. 조회는 좌석 수를 변경하지 않으며 최신 잔여 좌석을 반환한다.
3. **Step 3 — 선착순 경합 예매 및 매진 처리**
   - `S`석보다 많은 `B`건(예: `5,000`건)의 예매 요청이 동시에 들어온다.
   - 정확히 `S`건만 좌석을 1씩 차감하고 예매 성공 응답을 받는다.
   - 좌석이 `0`이 된 이후의 모든 요청은 음수로 내려가지 않고 매진 거절 응답을 받는다.
4. **Step 4 — 예매 취소 및 좌석 복구**
   - 예매자가 취소하면 좌석을 복구하되, 초기 총 좌석 수 `S`를 초과해 증가하지 않는다.
5. **Step 5 — 실서비스 확장 상황 (결제 대기 · 중복 방지 · 대기열 · 장애 복구)**
   - 예매 요청 후 결제 완료까지 좌석을 일정 시간 임시 선점(만료 시 자동 해제)한다.
   - 동일 사용자의 1인 다매 중복 예매를 차단한다.
   - 접속 폭주 시 대기열로 순번을 제어하고, 서버가 재시작돼도 확정된 예매·잔여 좌석 상태를 보존한다.

## 2. 시나리오에서 추출한 요구사항

| ID | 요구사항 | 핵심 검증 기준 |
| :--- | :--- | :--- |
| **R1** | **좌석 수량 저장·조회·폐기** | 초기 좌석 등록, 조회 시 현재 수량 반환, 없는 키 구분 |
| **R2** | **원자적 재고 차감 및 초과 예매 방지** | 동시 경합에서 `0` 미만으로 내려가지 않고 정확히 `S`건만 성공 |
| **R3** | **원자적 좌석 복구 및 총량 상한 유지** | 취소 시 좌석 복구, 총 좌석 수 `S` 초과 불가 |
| **R4** | **고빈도 동시 조회·예매 성능** | 대량 동시 요청에서 오류 없이 높은 처리량(req/s)과 낮은 지연 유지 |
| **R5** | **임시 선점 및 자동 만료 (TTL)** | 결제 대기 키에 유효 기간을 부여하고, 만료 시 자동 무효화·해제 |
| **R6** | **1인당 예매 제한 / 중복 예매 방지** | 동일 사용자 키/집합 기준으로 중복 예매 요청 차단 |
| **R7** | **접속 대기열 및 과부하 제어** | 순번(FIFO) 보장, 수용 한계 초과 시 질서 있는 대기/거절(`429`/`503`) |
| **R8** | **다중 키 복합 원자 처리** | "좌석 차감 + 예매자 기록" 등 여러 키 변경을 하나의 원자 단위로 실행 |
| **R9** | **서버 재시작·장애 시 데이터 보존** | 프로세스 종료·재기동 후에도 잔여 좌석·예매 상태 복구 |

## 3. 현재 Mini Redis 해결 여부 분석 (Gap Analysis)

### 요약 표

| ID | 요구사항 | 해결 여부 | 현재 근거 / 미해결 원인 |
| :--- | :--- | :--- | :--- |
| **R1** | 좌석 수량 저장·조회·폐기 | **해결** | `PUT /kv`, `GET /kv`, `DELETE /kv` 구현 완료 |
| **R2** | 원자적 차감 및 초과 예매 방지 | **해결** | `POST /kv/decr` (`minimum: 0`) + 단일 이벤트 루프 순차 처리 |
| **R3** | 원자적 복구 및 상한 유지 | **해결** | `POST /kv/incr` (`maximum: S`) 구현 완료 |
| **R4** | 고빈도 동시 처리 성능 | **부분 해결** | JMeter FastAPI `1,620~3,813 req/s`(MySQL 재측정 미수행), 로컬 SQLite 직접 호출 대비는 HTTP 비용으로 열세 |
| **R5** | 임시 선점 및 자동 만료 (TTL) | **부분 해결** | TTL(`PUT ttl`·`expire`·`ttl`·`persist`, lazy/active 만료) 구현 완료, 만료 시 좌석 카운터 자동 복구 콜백은 미지원 |
| **R6** | 1인당 제한 / 중복 예매 방지 | **미해결** | `SETNX`·`Set` 자료구조 미지원 (`PUT /kv`는 무조건 덮어씀) |
| **R7** | 대기열 및 과부하 제어 | **미해결** | 유저 레벨 대기열·백프레셔 없음 (OS 커널 backlog + 이벤트 루프 의존) |
| **R8** | 다중 키 복합 원자 처리 | **미해결** | `MULTI`/`EXEC`·Lua 스크립트 없음 (단일 키 연산만 지원) |
| **R9** | 서버 장애·재시작 시 보존 | **미해결** | 인메모리 전용(`MiniRedis._data`), 영속화 제외 |

---

### 항목별 상세 분석

#### R1 ~ R3. 기본 좌석 관리 · 초과 예매 방지 · 취소 복구 — **해결**
- **해결 방식**:
  - `MiniRedis`([storage.py](../storage.py))는 인스턴스별 Python `dict`를 사용하며, `app.py`([app.py](../app.py))는 `uvicorn(..., workers=1)` 단일 이벤트 루프로 요청을 하나씩 처리한다.
  - 예매 시 `POST /kv/decr`에 `minimum: 0`을 전달하면 계산 결과가 `0` 미만일 때 상태를 바꾸지 않고 `HTTP 409 CONDITION_NOT_MET`을 반환한다.
  - 취소 시 `POST /kv/incr`에 `maximum: S`를 전달하면 총 좌석 수를 넘기지 않고 복구한다.
- **검증 근거**: [demo_ticket.py](../demo_ticket.py) 실행에서 초기 `500`석에 `5,000`건(동시성 `100`) 예매 경합 시 **성공 `500`건, 매진 거절 `4,500`건, 오류 `0`건, 최종 잔여 좌석 `0`석**을 확인했다.

#### R4. 고빈도 동시 조회·예매 성능 — **부분 해결 (비교 대상·경로에 따라 다름)**
- **외부 디스크 내구성 RDBMS(MySQL 8.4) 및 스택 비교**:
  - 기존 JMeter 비교([03-performance-results.json](../resc/scenario_03_performance/03-performance-results.json), Flask 3.1.3 기준)에서는 Mini Redis HTTP가 중앙값 `1,593.6~2,582.5 req/s`, MySQL 8.4(JDBC, `sync_binlog=1`, `innodb_flush_log_at_trx_commit=1`)가 `66.7~82.6 req/s`로 관찰되었다.
  - 이후 스택 비교([03-stack-comparison-results.json](../resc/scenario_03_performance/03-stack-comparison-results.json))에서 FastAPI 카운터 처리량은 중앙값 `1,620.2~3,813.1 req/s`로 Flask 대비 `1.16~1.69배`였으나, MySQL과의 동일 조건 재측정은 수행하지 않았다.
- **로컬 SQLite 직접 호출 대비**:
  - [demo_ticket.py](../demo_ticket.py) 실측(동시성 `100`)에서는 `MiniRedis (Python 직접 호출)`이 `185,230~301,544 req/s`인 반면, `Mini Redis (FastAPI HTTP)`는 `520.9~569.6 req/s`, `SQLite (WAL + busy_timeout, sqlite3 직접 호출)`는 `21,381.6~22,614.9 req/s`로 측정되었다.
  - **원인**: `SQLite`는 네트워크/HTTP 없이 프로세스 내 C 라이브러리(`libsqlite3`)를 직접 호출하는 반면, 현재 Mini Redis HTTP 경로는 매 요청마다 **TCP 루프백 + HTTP/JSON 직렬화 + Python `uvicorn` 단일 이벤트 루프** 비용을 치르기 때문이다.
  - 따라서 현재 HTTP 경로만으로는 **"초당 수만 건"의 HTTP 처리량 요구사항을 충족하지 못한다.**

#### R5. 임시 선점 및 자동 만료 (TTL) — **부분 해결 (만료는 구현, 자동 복구 콜백은 미지원)**
- `PUT /kv`의 `ttl`, `POST /kv/expire`, `GET /kv/ttl`, `POST /kv/persist`와 lazy 만료 + 100ms active 정리([app.py](../app.py), [storage.py](../storage.py))가 구현·검증되었다.
- 다만 임시 선점 키(`hold:<user>`)가 만료될 때 별도 좌석 카운터를 **자동으로 `incr` 복구하는 이벤트/콜백**은 TTL 계약 범위에 없어 애플리케이션 쪽 별도 처리가 필요하다.

#### R6 ~ R9. 중복 예매 방지 · 대기열 · 다중 키 트랜잭션 · 영속성 — **미해결 (현재 설계 범위 밖)**
- **R6 (중복 예매 방지)**: 키가 없을 때만 생성하는 `SETNX`나 예매자 집합을 관리하는 `Set`(`SADD`/`SISMEMBER`) 명령이 없다.
- **R7 (대기열 및 과부하 제어)**: 별도 유저 레벨 대기열·백프레셔가 없어 OS 커널 `listen` backlog와 이벤트 루프에 대기를 맡긴다([rest-api.md](../rest-api.md) 8.6절). 엄밀한 선착순(FIFO)이나 연결 종료 후 이미 수신된 요청의 자동 취소는 보장하지 않는다.
- **R8 (다중 키 복합 원자 처리)**: `MULTI`/`EXEC`나 Lua 스크립트가 없어 "좌석 차감 + 예매자 키 기록"을 하나의 원자적 연산으로 묶을 수 없다.
- **R9 (영속성)**: 데이터는 메모리에만 보관되며 서버 재시작 시 사라진다([01-storage-scenario.md](../resc/scenario_01_storage/01-storage-scenario.md) 범위 제외).

## 4. 결론

1. **현재 Mini Redis가 확실히 해결하는 것**:
   - 단일 키 카운터 기반의 **실시간 잔여 좌석 조회**, **초과 예매 없는 원자적 선착순 차감·복구(정합성)**, **키별 TTL 만료(lazy + 100ms active 정리)**.
2. **현재 Mini Redis가 해결하지 못하는 것**:
   - HTTP API 경로에서의 **초당 수만 건 처리량**(로컬 임베디드 SQLite 직접 호출보다 HTTP/JSON 오버헤드가 큼),
   - **TTL 만료 시 좌석 자동 복구 콜백**, **1인 1매 중복 방지(`SETNX`/`Set`)**, **FIFO 대기열**, **다중 키 원자 트랜잭션**, **장애·재시작 시 영속성**.
3. **권장 후속 단계**:
   - 현재 FastAPI 구현과 MySQL 8.4의 동일 조건 직접 비교가 필요하면 별도 측정 환경에서 JMeter 비교를 수행한다.
