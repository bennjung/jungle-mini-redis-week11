## 1. 프로젝트 소개 — 약 20초

`[README 1. 프로젝트 소개]`

안녕하세요, 4팀 박찬입니다. 카운터나 외부 API 응답처럼 자주 읽고 갱신하는 데이터를 매번 DB나 외부 서버에서 처리하면 지연과 부하가 커집니다. 이를 메모리에 키-값 형태로 보관해 빠르게 처리하는 인메모리 저장소, Mini Redis를 만들었습니다.

---

## 2. 아키텍처 — 약 25초

`[README 2. 아키텍처 다이어그램]`

먼저 전체 아키텍처부터 말씀드리겠습니다. 이 저장소는 키만 알면 바로 찾을 수 있는 데이터라 스키마나 조인 없이 빠르게 접근하려고 Key-Value 모델을 택했고, 빠른 구현과 검증을 위해 Python과 내장 딕셔너리를 썼습니다.

통신은 REST API를 선택했고, 서버는 단일 이벤트 루프 기반의 `uvicorn`과 `FastAPI`로 구성해 내부 락 없이 원자적 연산과 주기적 무효화 정리를 함께 처리합니다.

---

## 3. 시나리오 기반 기능 설계 — 약 25초

`[README 3. 시나리오 기반 기능 설계]`

이제 이 구조에 필요한 기능들은 외부 날씨 API를 캐싱하는 시나리오를 바탕으로 구현했습니다.

첫째, 날씨는 계속 바뀌고 여러 서버가 캐시를 공유하면 만료 판단이 어긋날 수 있어, MiniRedis가 시간 기준 만료를 맡도록 TTL 기능을 넣었습니다.

둘째, 캐시가 만료되는 순간 동시 요청이 몰려 외부 API를 중복 호출하는 캐시 스탬피드를 막기 위해, 별도 키별 락을 두어 한 요청만 캐시를 갱신하게 했습니다.

## 4. 날씨 데모 — 약 40초 *(화면 전환·클릭 포함)*

`[날씨 데모 화면]`

방금 말씀드린 흐름을 날씨 데모로 직접 보여드리겠습니다.

`[서울 첫 번째 클릭]`

처음 조회하면 저장된 캐시가 없어서 Open-Meteo를 호출해 결과를 저장합니다.

`[서울 두 번째 클릭]`

다시 조회하면 저장된 응답을 바로 가져오기 때문에 외부 호출 없이 즉시 응답하며, 모니터 화면에서 외부 API 호출이 늘지 않은 것도 확인할 수 있습니다.

## 5. 요청 구간 분석 — 약 25초

`[README 5. 요청 구간 분석 그림·표]`

캐시 동작을 확인했으니, 이제 HTTP로 요청을 처리할 때 실제로 어디에서 시간이 걸리는지 구간별로 측정해 본 결과를 말씀드리겠습니다.

측정해 보니, C 구현 딕셔너리를 쓰는 저장소 비용은 아주 작았고 지연 대부분은 앞단 HTTP 파싱과 프레임워크에서 나왔습니다. 그래서 계약 호환성을 지키며 바로 바꿀 수 있는 HTTP 파서 교체만 우선 적용해 단건 지연을 크게 줄였습니다.
