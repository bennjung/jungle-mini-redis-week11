## 빠진 상황

- **TTL을 API 응답 전용으로 보면 안 된다.** 04는 API 응답 캐시를 예시로 든 것뿐이고, TTL은 저장소의 일반 키 기능이다. 세션·토큰, 레이트 리밋, OTP, 멱등 키, 분산 락, 임시 데이터, 랭킹 초기화 같은 사용처가 빠져 있다.
- **저장소 TTL과 API 캐시 정책의 경계가 빠져 있다.** TTL을 `set`/`expire`로 저장소 기능으로 넣을지, 데모 앱이 만료 시각을 관리할지 정해야 한다. API 응답 캐시는 그 위의 한 사용 사례다.
- **일반 키 TTL 테스트가 빠져 있다.** 문자열뿐만 아니라 숫자·불리언·`null`·배열·객체 등 모든 value 타입에 TTL이 적용되는지, 덮어쓸 때 TTL 유지/초기화, 남은 TTL 조회, 만료 취소, 경계, lazy/active 정리를 확인해야 한다.
- **TTL의 전체 범위를 04가 정의하지 않는다는 점이 빠져 있다.** 04는 응답 재사용·만료·무효화 시나리오이고, TTL 자체의 계약은 저장소 문서에서 정의해야 한다.
- **TTL 구현 후 03 성능 재측정** — TTL 확인, TTL 인덱스 갱신, active 정리가 카운터 증가 경로에 영향을 줄 수 있다. 03의 현재 결과는 TTL 없는 구성이므로, TTL 포함 최종 구현에서 같은 조건으로 다시 측정해야 한다. MySQL에도 동등한 TTL/만료 조건을 둘지, TTL 없는 경로와 TTL 있는 경로를 분리할지 정해야 한다.

## 미정 사항에 대한 생각

### TTL 계층

- **TTL은 저장소(MiniRedis)가 관리한다.**
  - `MiniRedis`가 키별 만료 시각을 보관한다. 애플리케이션은 TTL을 직접 계산하지 않는다.
  - `get(key)`는 조회 시점에 `현재 시각 >= 만료 시각`인지 확인하고, 만료됐으면 "없음"으로 응답하면서 해당 키를 삭제한다.
  - 이렇게 하면 API 응답 캐시뿐 아니라 세션, 레이트 리밋, 임시 데이터도 같은 TTL 기능을 쓸 수 있다.
  - API 캐시 앱은 이 기능을 호출하는 소비자다. 캐시 앱이 원본 API를 호출하는 것이지, MiniRedis가 API를 호출하는 것이 아니다.
  - 이유: TTL을 저장소 기능으로 두면 캐시·세션·레이트 리밋이 같은 만료 로직을 재사용하고, 앱마다 만료 계산을 중복하지 않는다.

- **TTL API는 네 가지로 제공한다.**
  - `set(key, value, ttl=None)` — 값을 저장하면서 TTL을 함께 걸 수 있다.
  - `expire(key, ttl)` — 기존 키의 값은 그대로 두고 TTL만 설정하거나 바꾼다.
  - `ttl(key)` — 남은 TTL을 조회한다.
  - `persist(key)` — TTL을 제거해 만료되지 않게 한다.
  - HTTP는 `PUT /kv`의 선택 `ttl`, `POST /kv/expire`, `GET /kv/ttl`, `POST /kv/persist`로 연결한다.

- **같은 키에 값을 다시 저장해도 기존 TTL은 유지한다.**
  - `set(key, value)`에 `ttl`을 주지 않으면 기존 만료 시각이 그대로 남는다.
  - 이유: 캐시에서 값을 다시 쓰면서 TTL을 빠뜨리면 영구 캐시가 된다. 세션 갱신에서도 만료가 유지되는 쪽이 안전하다.
  - TTL을 없애려면 `persist`, 새로 걸려면 `set(..., ttl=...)` 또는 `expire`를 쓴다.
  - Redis 기본은 덮어쓸 때 TTL을 초기화하므로, 이 문서는 Redis와 다르다는 점을 명시한다.

- **만료 시각에 도달하면 즉시 만료로 본다.**
  - `현재 시각 >= 만료 시각`이면 "없음".
  - `get`이 만료된 키를 만나면 그 자리에서 삭제한다.
  - 테스트는 가짜 시계로 정각을 검증한다.
- **`ttl=0`** — `set(..., ttl=0)`은 `INVALID_INPUT`으로 거절한다. `expire(key, 0)`은 키를 즉시 삭제한다.
- **명시적 `null`** — `set`의 `"ttl": null`은 생략으로 보고 기존 TTL을 유지한다. `expire`의 TTL은 필수이므로 `null`은 거절한다.
- **`expire` 성공 응답** — `{"found": true, "ttl": ttl}`. 키가 없으면 `{"found": false}`.
- **`ttl` 표시 규칙** — TTL 단위가 정해진 뒤 내림/반올림을 정한다. 미정.
- **`ttl`·`persist` 응답 형태(제안)**
  - `ttl` — 키 있고 TTL 있음: `{"found": true, "ttl": 남은 시간}`, TTL 없음: `{"found": true, "ttl": -1}`, 키 없음: `{"found": false}`.
  - `persist` — TTL 제거: `{"found": true, "persisted": true}`, TTL 없음: `{"found": true, "persisted": false}`, 키 없음: `{"found": false}`.
  - 단위와 정확한 형태는 다음에 정한다.

### TTL 만료 정리 방식 후보

TTL이 걸린 키를 어떻게 정리할지 세 가지 후보가 있습니다. 아직 하나를 고른 것은 아닙니다.

먼저 두 가지를 구분합니다.

- **Lazy 만료** — 모든 후보에 공통으로 필요합니다. `get`·`set`·`delete` 할 때 만료 시각을 확인하고, 지났으면 "없음"으로 응답하면서 그 자리에서 삭제합니다. **접근된 키의 정확성**을 보장합니다.
- **Active 만료** — 아무도 다시 찾지 않는 콜드 키를 메모리에서 회수하는 작업입니다. 아래 세 후보는 이 active 만료를 **언제, 얼마나** 할지에 대한 것입니다.

#### 후보 1: 요청마다 1개

- TTL 키 목록에 커서를 두고, 요청이 하나 처리될 때마다 커서를 하나 전진시켜 그 키만 만료 확인합니다.
- 장점: 모든 요청이 비슷하게 아주 작은 비용을 냅니다. 특정 요청만 느려지지 않습니다.
- 단점: 정리 속도가 요청 수에 비례합니다. 요청이 적으면 콜드 키가 오래 남습니다.

#### 후보 2: 요청마다 3~5개

- 같은 커서 방식이지만 한 요청에 3~5개를 확인합니다.
- 장점: 후보 1보다 정리가 빠르고, 비용은 여전히 작게 분산됩니다.
- 단점: 개수를 늘릴수록 그 요청의 지연이 조금씩 늘어납니다.

#### 후보 3: 시간 기준

- 요청 수와 무관하게 일정 시간마다 정리합니다. 예: 1초마다.
- 한 번에 몇 개를 볼지는 **TTL 키 수**와 **전체를 한 번 훑는 목표 시간**으로 정합니다.

예를 들어 설명하면 이렇습니다.

- TTL이 걸린 키가 10,000개 있고, 60초 안에 전체를 한 번 훑고 싶다면, 초당 약 167개를 확인하면 됩니다. (`10,000 ÷ 60`)
- TTL 키가 10개뿐이면 초당 0.17개가 되어 사실상 정리가 멈춥니다. 그래서 **최소 초당 확인 수**를 둡니다. 예: 최소 1개.
- TTL 키가 100만 개면 초당 16,667개가 되어 CPU를 너무 많이 씁니다. 그래서 **최대 초당 확인 수**를 둡니다. 예: 최대 1,000개.
- 정리하면 `초당 확인 수 = 최소값과 최대값 사이에서 (TTL 키 수 ÷ 목표 시간)`입니다. 최대값에 걸리면 전체를 한 번 훑는 데 목표 시간보다 더 오래 걸립니다.

1초에 몰아서 처리하면 그 요청이 느려질 수 있으므로, 100ms처럼 **작은 간격으로 나눠** 조금씩 하는 편이 좋습니다.

- 장점: 요청량과 무관하게 정리됩니다.
- 단점: 배치를 몰면 꼬리 지연이 생기고, TTL 키가 최대값을 넘으면 전체 순회가 목표 시간보다 오래 걸립니다.

#### 공통 자료구조

- TTL이 있는 키만 빠르게 찾기 위해 `키 → 만료 시각` 인덱스를 둡니다.
- 커서 방식이면 TTL 키 목록을 순서대로 순회합니다. 키가 추가·삭제되면 커서가 어긋날 수 있어 보정이 필요합니다.
- 무작위 표본을 쓰려면 TTL 키 목록과 위치 인덱스를 유지합니다. 매번 전체 목록을 복사하면 TTL 키 수에 비례해 느려지므로 피해야 합니다.

#### 아직 정하지 않은 것

- **TTL 단위와 `ttl` 표시 규칙** — 초 단위, 밀리초 단위, 둘 다 중 무엇을 쓸지. `ttl` 응답의 내림/반올림과 테스트용 가짜 시계 도입 여부도 함께 정해야 한다. 다른 의견 필요.
  - 초 단위 + 가짜 시계: API가 단순하고 테스트가 정확함.
  - 밀리초 단위: 테스트가 빠르지만 API 숫자가 커짐.
  - 둘 다: `ttl`/`ttl_ms` 두 표면을 관리해야 함.
- `ttl`·`persist` 응답의 정확한 형태.
- 후보 1·2·3 중 무엇을 쓸지.
- 후보 3을 쓴다면 목표 시간, 최소 확인 수, 최대 확인 수를 몇으로 할지.
- 요청이 아예 없을 때도 정리해야 하는지, 그러려면 백그라운드 타이머가 필요한지.
