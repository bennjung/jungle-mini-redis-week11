# 시나리오 04 응답 캐시 — 검토 메모

검토 대상: [API 응답 재사용·만료·수동 무효화](04-response-cache-scenario.md).
작성 기준: [테스트 시나리오 초안 검토 메모](../템플릿-scenario-preparation-template.md).

기존 시나리오를 다시 작성하지 않고, 사용자와 합의한 보완 내용과 선택이 남은 항목을 구분한다. 아래 기록만으로 테스트 계약 전체가 확정된 것은 아니다.

## 검토 메모

### 합의 사항

- **[S4-01·02·03] 예제 입력.** 예제 API 응답 `{"message":"hello"}`, 키 `"api:hello"`, TTL 10초는 예시로 사용한다. 실제 API와 테스트 입력 전체를 확정한 것은 아니다.
- **[S4-01·02] TTL 시작·만료 경계.** TTL은 저장 성공 시점부터 계산하고, 현재 시각이 만료 시각 이상이면 만료로 판단한다.
- **[S4-01·02·03] 원본 API 실패.** 실패를 사용자에게 알리고, 실패 응답은 캐시에 저장하지 않는다.
- **[S4-01·02·03] Mini Redis 실패.** 원본 API를 호출해 응답을 제공한다. 캐시 저장 실패 때문에 정상적인 원본 API 응답을 버리지 않는다.
- 위 실패 상황의 HTTP 상태와 응답 본문은 미결이다.

### 빠진 상황

- **[S4-01·02·03] 원본 API 호출 횟수로 캐시 사용 확인 — 합의됨.** 각 시나리오에서 원본 API 호출 횟수를 0부터 관찰한다. 최초 요청으로 원본 API를 호출해 응답을 저장하면 누적 1회, 유효한 캐시를 재사용하면 누적 1회를 유지한다. 만료 또는 수동 무효화 후 재요청하면 원본 API를 다시 호출하므로 누적 2회가 된다. 만료와 수동 무효화는 각각 별도로 검증한다. 응답 내용이 같더라도 호출 횟수로 재사용과 재조회를 구분한다.
- **[S4-01·02] 같은 키의 응답을 덮어쓰면 TTL도 갱신 — 합의됨.** 같은 키에 새 응답을 저장하면 새 응답에 대한 TTL도 새로 시작한다. 기존 응답의 만료 시점을 그대로 적용하지 않는다. 검증 시 기존 만료 시점과 새 만료 시점을 구분하여, 이전 만료 시점 때문에 새 응답이 만료되지 않는지 확인한다. 구체적인 TTL과 시간 입력은 이 메모에서 정하지 않는다.
- **[S4-02·03] 만료·무효화 이후 새 응답 저장 — 합의됨.** 기존 응답 제거 → 원본 API에 새 응답 요청 → 새 응답 저장 순서로 처리한다. 기존 캐시 응답을 다시 사용하지 않고, 원본에서 받은 새 응답을 저장했는지 확인한다. 원본 응답 내용이 이전과 같을 수도 있으므로 내용 차이만으로 재조회·재저장을 판정하지 않는다. 이 흐름은 만료·무효화 이후 응답을 다시 요청하는 상황을 다루며, 삭제 즉시 원본 API를 호출한다고 정한 것은 아니다.

### 미정 사항에 대한 생각

- **[S4-01·02] 조회 시 TTL 연장 여부 — 선택 필요.** 최초 만료 시점을 유지하는 방식과 조회할 때마다 TTL을 연장하는 방식을 구분한다. 유효 기간 중 반복 조회한 뒤 최초 만료 시점에서 동작을 확인하는 상황이 필요하지만, 어느 방식을 사용할지는 아직 선택하지 않았다. 새 응답으로 덮어쓸 때 TTL을 갱신하는 결정과는 별개다.

서로 다른 요청을 같은 캐시로 잘못 처리하는 경우는 사용자 요청에 따라 이번 검토 항목에 포함하지 않는다. 기존 문서의 나머지 ‘계약 확정 전에 합의할 사항’은 이번 메모에서 추가로 검토하지 않는다.
