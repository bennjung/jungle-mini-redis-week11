# 04 날씨 조회 캐시 — 문제 상황과 TTL/LDC 논의 기록

## 1. 확정된 문제 상황

`[확정]` 04의 문제 상황은 **사용자의 현재 위치 기반 날씨 조회**로 한다. (2026-11-14, 사용자 확인)

### 1.1 서비스 흐름

사용자가 스마트폰에서 현재 위치를 보내면, 날씨 서비스가 해당 위치의 날씨를 조회해 응답한다.

```text
사용자 위치
  → 좌표 정규화
  → 캐시 키 생성
  → MiniRedis 조회
      ├─ 있음: 저장된 API 응답 재사용
      └─ 없음: 원본 날씨 API 호출 → 응답을 TTL과 함께 저장 → 응답
```

### 1.2 캐시 키 예시

```text
weather:37.566:126.978
weather:37.502:127.025
weather:37.384:127.123
weather:35.179:129.075
```

- 요청받은 위치를 기준으로 캐시 키를 만든다.
- 좌표는 적절한 격자로 정규화했다고 가정한다. 정규화 방식과 격자 크기는 아직 확정하지 않았다.
- 키 형식은 예시이며, 응답 종류·단위·언어·API 버전을 키에 포함할지는 3장에서 다시 다룬다.

### 1.3 핫 키와 콜드 키

| 구분 | 요청 패턴 | TTL 만료 뒤 | 정리에 필요한 것 |
| --- | --- | --- | --- |
| 핫 키 | 서울역·강남역처럼 반복 조회되는 지역 | 다음 조회가 다시 발생한다 | 조회 시 확인하는 lazy 만료로 충분 |
| 콜드 키 | 특정 산길·외곽 도로·여행지처럼 한 번 조회하고 다시 접근하지 않는 지역 | 조회가 다시 발생하지 않는다 | 접근 없이도 회수하는 active 만료가 필요 |

- **핫 키/콜드 키는 저장소가 판별하는 상태가 아니라 워크로드 설명이다.** 저장소가 키의 인기도를 따로 추적한다는 뜻이 아니다.
- 콜드 키의 문제는 TTL이 지났는데도 다시 조회되지 않아 lazy 만료가 실행되지 않는다는 점이다. 메모리에는 만료된 항목이 남는다.
- 핫 키의 문제는 반복 조회 자체가 아니라, **TTL을 조회할 때마다 연장하면 데이터가 영원히 갱신되지 않는 것**이다. 이 구분은 3장 R5에서 다룬다.

### 1.4 이 문제 상황이 다루는 범위

| 04의 축 | 이 시나리오와의 관계 |
| --- | --- |
| 축 2. 다른 원본의 캐시 — 시간 경과 | 핵심이다. 날씨 원본 응답을 TTL과 함께 보관하고, 만료 뒤 재조회한다. |
| 축 2. 다른 원본의 캐시 — 원본 변경 | 조건부다. 예보 갱신을 무효화 신호로 다룰 때만 포함한다. |
| 축 3. 대량 무효화 | 조건부다. 예보 갱신이 지역 전체 키에 걸릴 때만 포함한다. |
| 축 1. 데이터 자체의 유효 기간 | 핵심은 아니다. TTL 메커니즘은 공유하지만, TTL 자체의 계약을 어느 문서가 소유할지는 L13에서 정한다. |
| 02. 카운터 정합성 | 다루지 않는다. |
| 03. 성능 비교 | 다루지 않는다. TTL 구현 뒤 03을 같은 조건으로 다시 측정하는 일은 별도다. |

### 1.5 이 시나리오가 대체하지 않는 것

- 원본 사용자 문제의 **읽기-수정-쓰기 경합** 자체를 해결했다고 보지 않는다. 그 문제는 02와 03의 범위다.
- 날씨 캐시의 적중률이 좋다는 사실만으로 저장소의 동시성·성능·내구성을 입증하지 않는다.
- 서버 재시작 뒤 데이터와 TTL이 유지되는지는 이 시나리오의 범위가 아니다. `phase.md`의 선택 요구사항과 구분한다.
- 메모리 상한(`maxmemory`)과 축출(eviction) 정책은 TTL과 별개다. 이 시나리오가 자동으로 요구하는 것은 아니다.

### 1.6 용어 구분

- **TTL** — 저장 시점부터 계산하는 보관 기간. 이 문서에서는 "만료 시각"까지의 남은 시간을 뜻한다.
- **lazy 만료** — `get`·`set`·`delete` 같은 접근이 있을 때 만료를 확인하고 그 자리에서 삭제하는 방식. 접근된 키의 정확성을 보장한다.
- **active 만료** — 접근이 없어도 만료된 키를 찾아 회수하는 방식. 콜드 키의 메모리 회수를 담당한다.
- **논리적 없음** — `get`이 `{"found": false}`를 반환하는 상태. 실제 메모리 제거와 같다고 가정하지 않는다.
- **물리적 제거** — 저장소 내부에서 키와 TTL 인덱스 항목이 실제로 사라진 상태.
- **정리 지연** — 키가 만료된 시점부터 물리적으로 제거될 때까지의 시간 또는 요청 수.

## 2. 기준 워크로드 (참조값, 2026-11-14 확인)

`[확정]` 아래 값은 LDC 논의를 위한 참조값으로 사용하고, 지금은 이 값으로 정리 지연을 예측하지 않는다. (2026-11-14, 프로젝트 사용자 확인)

아래 값은 측정값이 아니다. LDC 선택을 먼저 결정한 뒤, 필요하면 같은 값으로 다시 계산한다.

| 항목 | 기호 | 제안값 | 비고 |
| --- | --- | --- | --- |
| 평균 요청률 | `R` | 50 req/s | 피크 150 req/s |
| 분당 고유 위치 수 | `U` | 300개/min = 5개/s | 요청당 최대 1개 키 생성 가정 |
| 핫 위치 | — | 20개, 전체 요청의 80% | 서울역·강남역 등 |
| 콜드 위치 | — | 나머지 요청, 대부분 1회성 | 산길·외곽·여행지 |
| TTL | `L` | 600초 | 원본 예보 갱신 주기와 같다고 가정 |
| 원본 API 지연 | — | 200ms | 캐시 miss 시 추가 지연 |
| 원본 API 한도 | — | 20 req/s | 초과 시 실패 또는 제한 |
| 허용 낡음 정도 | — | 600초 + 원본 호출·저장 지연 | 원본 관측 시각 기준 |
| 트래픽 패턴 | — | 상시, 아침·저녁 피크 | 긴 유휴 없음 |
| 키 크기 | — | 약 24바이트 | `weather:37.566:126.978` |
| `value` 크기 | — | 약 500바이트 | JSON 응답 문자열 |

### 2.1 이 가정에서 계산되는 값

- 살아 있는 TTL 키 수 ≈ `U × L` = 5 × 600 = **3,000개**.
- 원본 호출: 핫 위치 20개 × (1/600초) ≈ 0.033회/s. 콜드 요청 10 req/s가 모두 miss라면 원본 호출 ≈ 10회/s. 합계 ≈ 10회/s로 원본 한도 20 req/s 안에 들어온다.
- 모든 요청이 서로 다른 콜드 위치라면 원본 호출 = 50회/s가 되어 원본 한도 20 req/s를 넘는다. 이 경우 캐시 적중률이 아니라 원본 호출 제한이 먼저 문제가 된다.
- 후보 1(요청마다 1개 확인)의 정리 용량 = `R` = 50개/s. 생성률 `U` = 5개/s보다 10배 크다.

### 2.2 정상 상태에서 후보 1이 따라가는 이유

요청마다 최대 1개 키가 생성되고 요청률이 일정하면, 커서는 요청마다 1개씩 전진한다.

- TTL 키 수 ≈ `U × L`.
- 한 바퀴 순회 시간 ≈ `(U × L) / R`.
- `U ≤ R`이므로 한 바퀴는 최대 `L`이다.

따라서 정상 상태에서는 만료된 키가 늦어도 대략 `L` 안에 한 번은 커서에 걸린다. 메모리는 살아 있는 키 수 규모로 수렴한다.

다만 `R`이 `U`보다 크면 커서가 살아 있는 키를 여러 번 확인하는 낭비가 생긴다. 이 낭비는 정리 용량의 여유와 맞바꾼 것이다. 만료 시각 힙은 만료된 키만 꺼내므로 이 낭비가 없다.

이 계산이 깨지는 경우는 별도로 다룬다.

- **버스트** — 짧은 시간에 콜드 키 N개가 생기고 요청률이 낮아지면, 한 바퀴가 `L`보다 길어진다. 만료 키가 오래 남는다.
- **유휴** — 타이머가 요청과 무관하게 정리를 실행한다. 유휴 상태에서도 콜드 키가 회수된다.
- **요청당 여러 키 생성** — 날씨 시나리오에는 해당하지 않지만, 한 요청이 여러 키를 만들면 `U > R`이 되어 후보 1이 따라가지 못할 수 있다.

## 3. 도출된 요구사항 후보

`[제안]` 아래 항목은 날씨 시나리오를 기준으로 새로 도출한 검토 후보입니다. 기존 문서에 이미 적힌 항목은 `[기존 문서 기재]`로 표시했습니다. 이 문서에서 다시 확인하지 않은 기재는 확정 계약으로 사용하지 않습니다.

### 3.1 캐시 키와 응답 정합성

- **R1. 좌표 정규화의 단일 기준이 필요하다.**
  - 위도·경도 순서, 소수 자릿수, 반올림 방식, `-0.0` 처리, 문자열 형식을 한 함수로 고정해야 한다.
  - `37.5`와 `37.500`, `-0.0`과 `0.0`이 다른 키가 되면 같은 위치가 여러 키로 갈라져 적중률이 떨어진다.
  - 정규화는 저장소가 아니라 날씨 앱의 책임이다. 저장소는 완성된 `key` 문자열만 받는다.
  - 영향을 주는 LDC 선택: 없음. 04의 앱 경계와 테스트 입력에 영향을 준다.

- **R2. 응답을 바꾸는 입력은 모두 캐시 키에 포함해야 한다.**
  - 제안 키 `weather:위도:경도`는 위치만 포함한다. 응답이 섭씨/화씨, 언어, 현재/예보, API 버전에 따라 달라지면 같은 키로 다른 응답을 덮어쓴다.
  - 예: `weather:v1:current:c:ko:37.566:126.978`처럼 응답 종류와 버전을 키에 넣거나, 그 입력이 하나뿐임을 계약으로 명시한다.
  - 키가 길어져도 256바이트 제한 안에 들어오는지 확인해야 한다.
  - 영향을 주는 LDC 선택: 없음. 04의 앱 경계와 S4-01~03 예제에 영향을 준다.

- **R3. 캐시 키에 개인화 데이터를 넣지 않는다.**
  - 날씨 응답 본문에 사용자 ID, 요청 ID, 개인 설정이 들어가면 다른 사용자에게 그대로 재사용된다.
  - 위치는 개인정보일 수 있다. 격자 정규화는 정밀도를 낮추지만, 키 자체가 대략적인 위치를 드러낸다. 키를 로그에 그대로 남기지 않는지도 함께 정한다.
  - 이 항목은 기능 요구가 아니라 비기능 후보입니다. 범위 포함 여부를 별도로 정한다.
  - 영향을 주는 LDC 선택: 없음. 04의 앱 경계와 로그 정책에 영향을 준다.

- **R4. 키 접두사와 입력 검증으로 키 충돌을 막는다.**
  - 저장소는 평면 키 공간이다. `weather:` 접두사를 고정해 `session:`, `api:`, `counter:` 키와 섞이지 않게 한다.
  - 좌표는 숫자·범위 검증을 통과한 뒤 키로 만든다. 사용자 입력을 그대로 키에 붙이면 다른 키를 덮어쓸 수 있다.
  - 키 길이 1~256바이트, `value` 크기 65,536바이트 제한은 기존 계약을 따른다.
  - 영향을 주는 LDC 선택: 없음. 04의 HTTP/app 경계에 영향을 준다.

### 3.2 TTL의 의미와 신선도

- **R5. TTL은 접근 시점이 아니라 데이터 신선도 기준이어야 한다.**
  - 핫 키를 조회할 때마다 TTL을 연장하면, 계속 조회되는 지역은 만료되지 않아 날씨가 영원히 갱신되지 않는다.
  - 날씨의 TTL은 "원본에서 가져온 뒤 얼마나 지났는가"를 뜻해야 한다. 조회 횟수와 무관하게 저장 시점부터 계산하는 절대 TTL이 맞다.
  - Redis의 `GET`도 TTL을 연장하지 않는다. TTL 연장이 필요하면 `EXPIRE`를 명시적으로 호출한다.
  - 영향을 주는 LDC 선택: TTL 계층, `expire` API, 덮어쓰기 정책.

- **R6. TTL 시작점과 원본 관측 시각을 구분해야 한다.**
  - `[기존 문서 기재]` TTL은 저장 성공 시점부터 계산한다. (`jung-response-scenario.md`)
  - 원본 응답이 이미 5분 지난 데이터라면, 저장 뒤 TTL 10분을 더해 최대 15분 낡은 응답이 될 수 있다.
  - 날씨 응답에 `observed_at`이 있으면, 앱이 남은 TTL을 계산해 전달하거나 허용 낡음 정도를 `TTL + 원본 나이 + 원본 호출·저장 지연`으로 정의해야 한다.
  - 저장소가 원본 관측 시각을 해석하지는 않는다. 앱이 계산한 TTL을 받는다.
  - 영향을 주는 LDC 선택: TTL 계층, TTL 단위, `set(ttl)`의 시작점.

- **R7. 덮어쓰기 때 기존 TTL을 유지할지 갱신할지 문서 사이에 충돌이 있다.**
  - `[충돌]` `ldc-scenario-template.md`는 `set(key, value)`에 `ttl`을 주지 않으면 기존 TTL을 유지한다고 제안한다.
  - `[기존 문서 기재]` `jung-response-scenario.md`는 같은 키에 새 응답을 저장하면 TTL도 새로 시작한다고 적는다.
  - 두 문장은 같은 상황(`ttl` 없는 덮어쓰기)에서 반대 결과를 말한다.
  - **`[확정]` 결정(D-04)** — Redis 기본을 따른다. `set(key, value)`에 `ttl`이 없으면 기존 TTL을 제거한다. 날씨 캐시 갱신 경로는 앱이 `ttl`을 명시해 새 TTL을 건다. 만료된 키를 `ttl` 없이 덮어쓰면 새 키는 TTL 없이 저장된다.
  - **만료된 키를 덮어쓰는 경계** — TTL 초기화 정책에서는 이미 지난 TTL을 물려받는 문제가 생기지 않는다. 대신 캐시 갱신 경로가 `ttl`을 빠뜨리면 새 응답이 영구 키가 된다. 앱 경계의 테스트로 이 실수를 잡아야 한다.
  - 영향을 주는 LDC 선택: 덮어쓰기 정책, lazy 만료 범위, TTL 인덱스 일관성.

- **R8. `get`뿐 아니라 모든 키 연산이 같은 만료 검사를 해야 한다.**
  - `get`·`set`·`delete`뿐 아니라 `expire`·`ttl`·`persist`도 만료된 키를 없는 키로 취급해야 한다.
  - 만료된 키에 `expire`를 호출해 TTL을 다시 걸면 이전 `value`가 되살아나면 안 된다. `{"found": false}`여야 한다.
  - 만료된 키에 `ttl`을 호출했을 때 `-1`(TTL 없음)이나 `0`이 아니라 `{"found": false}`여야 한다.
  - `[기존 문서 기재]` 만료된 키와 처음부터 없던 키의 조회 결과는 `{"found": false}`로 같다. (`chan-scenario-template.md`)
  - 영향을 주는 LDC 선택: lazy 만료 범위, `ttl`·`persist` 응답 형태.

- **R9. TTL 표시 정밀도와 내부 만료 정밀도를 분리해야 한다.**
  - 내부 만료 시각은 경계 판정에 충분한 정밀도로 보관하고, `ttl` 응답은 표시용으로 반올림할 수 있다.
  - `ttl`이 `0`을 반환해도 아직 유효한 키일 수 있다. 클라이언트가 `ttl == 0`을 만료로 해석하면 일찍 재조회하거나 값을 버릴 수 있다. `ttl`은 참고값이고 `get`이 최종 판정이라는 규칙이 필요하다.
  - 내부적으로 초 단위로 내림해 저장하면 만료 시각보다 최대 1초 일찍 삭제될 수 있다. 표시 반올림과 저장 정밀도를 같은 값으로 쓰지 않는다.
  - **`[확정]` 결정(D-06)** — 정수 밀리초를 쓴다. `_expires`의 만료 시각과 `ttl` 응답을 정수 밀리초로 통일하면 별도 반올림 규칙을 두지 않는다. 소수 밀리초는 허용하지 않는 것으로 본다.
  - 영향을 주는 LDC 선택: TTL 단위, `ttl` 표시 규칙, active 만료의 삭제 시점.

- **R10. TTL 단위와 시계 기준을 정해야 한다.**
  - 초 단위면 API가 단순하고 날씨 TTL(600초)에 충분하다. 밀리초 단위는 테스트에는 편하지만 API 숫자가 커진다.
  - 가짜 시계를 주입하면 단위와 무관하게 경계 테스트를 빠르고 정확하게 할 수 있다.
  - 벽시계를 쓰면 NTP 보정으로 시각이 뒤로 가거나 앞으로 갈 때 TTL이 늘어나거나 줄어들 수 있다. 단조 시계를 쓰면 경과 시간은 안정적이지만 절대 시각 기반 만료와 구분해야 한다.
  - 가짜 시계가 lazy 만료와 active 만료 모두를 제어해야 테스트가 결정적이다.
  - **`[확정]` 결정(D-06, D-14)** — 정수 밀리초, 벽시계의 절대 epoch ms. 가짜 시계로 lazy·active 모두를 제어한다. 벽시계 보정에 TTL이 흔들릴 수 있는 비용은 받아들인다.
  - 영향을 주는 LDC 선택: TTL 단위, TTL 계층, active 만료 방식, 테스트 전략.

### 3.3 active 만료와 메모리

- **R11. active 만료에는 "언제까지 지워져야 한다"는 완료 기준이 필요하다.**
  - "주기적으로 정리한다"만으로는 테스트가 통과했는지 판정할 수 없다.
  - 만료된 키가 **요청 N회 안에** 또는 **시간 T 안에** 물리적으로 제거된다는 상한을 정해야 한다.
  - 이 상한이 후보 1·2·3을 비교하는 기준이 된다.
  - 영향을 주는 LDC 선택: active 만료 방식, 파라미터, 테스트 전략.

- **R12. 콜드 키가 굶주리지 않는다는 보장이 필요하다.**
  - 무작위 표본 방식은 운이 나쁘면 콜드 키를 오래 못 볼 수 있다. 확률적 보장만 있다.
  - 커서 방식은 TTL 키를 순서대로 한 바퀴 도는 동안 모든 키를 한 번씩 본다. 콜드 키가 특정 구간에 몰려도 결국 방문한다.
  - 만료 시각 기준 힙은 가장 이른 만료부터 보므로 콜드 키를 오래 남기지 않는다.
  - "콜드 키는 접근이 없으니 active 만료가 꼭 필요하다"는 요구는, 단순히 active 만료를 켜는 것보다 **방문 보장**을 요구한다.
  - 영향을 주는 LDC 선택: active 만료 방식, 자료구조.

- **R13. active 만료 비용은 요청 지연 예산 안에 있어야 한다.**
  - 요청마다 몇 개를 확인할지, 한 번에 몇 개를 지울지에 따라 해당 요청의 지연이 늘어난다.
  - 현재 `app.py`는 단일 이벤트 루프·`uvicorn workers=1`로 요청을 하나씩 처리한다. 별도 스레드 타이머를 두면 저장소에 동시 접근이 생겨 잠금·원자성 문제가 따라온다.
  - D-24에서 같은 이벤트 루프의 100ms 주기 task로 확정했다. tick의 저장소 호출은 동기로 끝나므로 사이클 중간에 요청이 끼어들지 않는다.
  - 영향을 주는 LDC 선택: active 만료 방식, 백그라운드 타이머 여부, 03 재측정.

- **R14. TTL 인덱스의 불변 조건을 정해야 한다.**
  - 불변 조건 후보: TTL 인덱스에는 **살아 있는 키 중 TTL이 있는 키만** 들어 있다.
  - `set(ttl)`·`expire`·`persist`·`delete`·lazy 삭제·active 삭제가 모두 인덱스를 같은 규칙으로 갱신해야 한다.
  - active 스캔이 들고 있던 오래된 인덱스 항목이, 그 사이 새 `value`와 새 TTL로 덮어쓴 키를 삭제하면 안 된다. 삭제 전에 현재 만료 정보와 일치하는지 확인해야 한다.
  - 인덱스 항목이 남으면 active 스캔이 같은 키를 반복 확인하며 비용을 낭비한다.
  - 영향을 주는 LDC 선택: TTL 인덱스 자료구조, 덮어쓰기 정책, lazy/active 삭제.

- **R15. 메모리 회수는 "논리적 키 수"와 "프로세스 메모리"를 구분해야 한다.**
  - Python `dict`에서 키를 삭제해도 프로세스 RSS가 즉시 줄지 않을 수 있다. 할당자는 해제한 메모리를 재사용하지만 OS에 바로 반환하지 않을 수 있다.
  - active 만료가 줄이는 것은 논리적 키 수와 저장소가 붙잡고 있는 객체다. "메모리 사용량이 즉시 줄었다"고 주장하려면 RSS 측정이 필요하고, 그 주장은 별도 검증 대상이다.
  - 테스트는 `snapshot`의 키 수 같은 논리적 지표로 판정하고, RSS는 참고 지표로 분리한다.
  - 영향을 주는 LDC 선택: active 만료 방식, 테스트 전략, 03 재측정.

- **R16. 메모리 상한과 TTL은 다른 기능이다.**
  - TTL은 시간이 지난 키를 회수한다. 요청률과 TTL이 유한하면 살아 있는 키 수는 대략 `요청률 × TTL`로 유한하다.
  - 모든 요청이 서로 다른 위치라면 살아 있는 키 수가 `R × L`까지 커진다. TTL은 이 살아 있는 키를 줄이지 않는다.
  - 무작위 좌표를 대량으로 보내는 침입자는 원본 호출과 키 생성을 동시에 늘린다. TTL·active 만료만으로는 막을 수 없다. 원본 호출 제한, 입력 검증, 최대 키 수 같은 별도 수단이 필요하다.
  - Redis의 `maxmemory`·축출 정책은 TTL과 별개다. 이 시나리오에 포함할지는 별도 결정이다.
  - 영향을 주는 LDC 선택: 04 범위, active 만료 파라미터, 03 재측정.

### 3.4 실패·무효화·동시성

- **R17. "실패"와 "유효한 부정 결과"를 구분해야 한다.**
  - `[기존 문서 기재]` 원본 API 실패는 사용자에게 알리고 캐시에 저장하지 않는다. (`jung-response-scenario.md`)
  - 날씨 원본이 지원하지 않는 위치에 404를 주는 것은 실패가 아니라 **유효한 부정 결과**일 수 있다. 이것도 캐시하지 않으면 같은 위치 요청이 매번 원본을 호출한다.
  - 404/`null`을 짧은 TTL로 캐시할지, 캐시하지 않을지 정해야 한다. `null` `value`를 캐시하면 `{"found": true, "value": null}`과 `{"found": false}`를 구분해야 한다.
  - 영향을 주는 LDC 선택: `set`의 `null` 허용, 실패 처리, TTL 정책.

- **R18. 캐시된 응답의 유효성을 재사용 전에 확인해야 한다.**
  - 저장된 JSON이 깨졌거나, 이전 스키마·이전 API 버전의 응답이면 사용자에게 그대로 보내면 안 된다.
  - 이 경우 캐시에 없는 것으로 취급해 원본을 다시 호출하고, 잘못된 항목을 무효화하는 규칙이 필요하다.
  - 키에 버전을 넣는 방식(R2)과 응답 스키마를 검사하는 방식 중 무엇을 쓸지 정해야 한다.
  - 영향을 주는 LDC 선택: 없음. 04의 앱 경계와 무효화에 영향을 준다.

- **R19. 예보 갱신은 키 하나의 삭제로 끝나지 않을 수 있다.**
  - 예보가 갱신되면 같은 지역의 여러 격자 키가 동시에 낡는다. `delete(key)`를 키 수만큼 호출하면 요청과 저장소 연산이 키 수에 비례한다.
  - 선택지:
    - TTL만 기다린다. 추가 기능이 없지만 최대 `L`만큼 낡은 응답이 남는다.
    - 그룹 단위 삭제를 도입한다. `chan-scenario-template.md`의 S4-06 후보. 키 수만큼 비용이 들 수 있다.
    - 키 버전을 올린다. 예: `weather:v2:...`. 한 번의 버전 갱신으로 이전 키를 논리적으로 무효화하고, 이전 키는 TTL로 회수한다. 물리적 메모리는 TTL까지 남는다.
  - "논리적 무효화"와 "물리적 제거"의 시점이 다르다는 점을 명시해야 한다.
  - 영향을 주는 LDC 선택: 04의 무효화 범위, TTL, bulk invalidation 포함 여부.

- **R20. 핫 키 만료 시 동시 miss를 어떻게 다룰지 정해야 한다.**
  - 핫 키가 만료되는 순간 여러 요청이 동시에 miss를 내면, 모두 원본 API를 호출한다. 캐시가 원본을 보호하지 못하는 순간이 생긴다.
  - TTL을 같은 시점에 설정한 키들이 한꺼번에 만료되면 이 현상이 커진다. TTL에 작은 무작위 흔들림(jitter)을 주는 것만으로도 분산할 수 있다. 이는 앱이 TTL 값을 다르게 전달하면 되고, 저장소 기능은 아니다.
  - 단일 요청만 원본을 호출하게 하는 단일 실행(single-flight)·분산 락은 별도 기능이다. 04의 동시성 포함 여부를 먼저 정해야 한다.
  - `[미정]` `04-response-cache-scenario.md`는 동시 만료 요청과 진행 중인 조회·저장과 무효화의 경합을 포함할지 아직 정하지 않았다.
  - 영향을 주는 LDC 선택: 04 범위, TTL 단위(테스트), active 만료 방식(만료 시점 분산).

- **R21. 캐시 쓰기 경로는 TTL을 항상 명시해야 한다.**
  - 앱이 TTL을 빠뜨리면 영구 키가 될 수 있다. `ttl(key)`로 TTL이 있는지 확인하는 테스트를 두면 이 실수를 잡을 수 있다.
  - `[미정]` 저장소가 `set` 없이 TTL을 강제할 수는 없으므로, 이 규칙은 앱 경계의 계약이다.
  - 영향을 주는 LDC 선택: 덮어쓰기 정책, `ttl` API.

### 3.5 관측과 검증

- **R22. 적중률·원본 호출·만료 정리를 같은 기준으로 관찰해야 한다.**
  - `[기존 문서 기재]` 원본 API 호출 횟수로 캐시 재사용을 확인한다. (`jung-response-scenario.md`)
  - 원본 호출 횟수는 "재사용했는가"를 보여주지만, "콜드 키가 실제로 회수됐는가"는 보여주지 않는다. 저장소 수준의 TTL 키 수·만료 키 수가 필요하다.
  - 적중률은 앱 수준 지표(캐시 적중/없음), 만료·정리는 저장소 수준 지표로 소유자를 분리한다.
  - HTTP 디버그 엔드포인트로 내부 키를 노출하는 대신, 저장소 단위 테스트에서 `snapshot`으로 관찰하는 편이 안전하다.
  - 영향을 주는 LDC 선택: 테스트 전략, 관측 표면.

- **R23. 시간 제어와 상태 관찰 도구의 의미를 정해야 한다.**
  - `[제안]` 가짜 시계를 `MiniRedis`에 주입해 lazy·active 만료를 같은 시간 기준으로 제어한다.
  - 현재 `tests/scenario_01_storage/storage_helpers.py`의 `snapshot(store)`는 `store._data.copy()`만 반환한다. TTL 인덱스와 만료된 키의 물리적 존재를 보려면 별도 관찰 도구가 필요하다.
  - 기존 `snapshot`의 의미를 바꾸면 01의 확정 테스트에 영향을 준다. 04 전용 도구를 새로 두는 쪽과 기존 도구를 확장하는 쪽을 구분해 정한다.
  - 영향을 주는 LDC 선택: TTL 인덱스 자료구조, active 만료 방식, 테스트 전략.

- **R24. 기준 워크로드와 성공 지표가 먼저 필요하다.**

## 4. LDC 선택지별 논의

### L1. TTL 계층 — 저장소와 앱

- **저장소 관리(`ldc` 제안)** — `MiniRedis`가 키별 만료 시각을 보관하고 `get`이 판정한다. 여러 클라이언트가 같은 저장소를 쓰면 만료 판정이 한 곳에 모인다. 앱마다 만료 계산을 중복하지 않는다. 날씨 앱은 TTL을 전달하는 소비자가 된다.
- **앱 관리** — 저장소는 일반 KV로 두고, 앱이 `value` 안에 만료 시각을 넣어 스스로 판정한다. 저장소 변경이 작지만, 모든 읽는 쪽이 만료 검사를 반복해야 하고 `{"found": false}` 계약을 저장소가 보장할 수 없다.
- **날씨 시나리오의 판단 기준** — 04의 축 1이 다루는 "여러 클라이언트가 같은 만료 판정을 공유해야 한다"는 논리와, 축 2의 "원본 사본이 시간이 지나면 만료된다"는 요구가 저장소 관리 쪽을 지지한다. 다만 현재 앱은 단일 프로세스이므로 "여러 서버"가 실제 요구인지 확인이 필요하다.
- **결정 (`[확정]`, 2026-11-14)** — 저장소 관리. `MiniRedis`가 키별 만료 시각을 보관하고 `get`이 판정한다. 앱은 TTL을 전달하는 소비자가 된다.

### L2. TTL API 표면

- 후보:
  - 최소: `set(key, value, ttl)`만 추가한다. 날씨 캐시에는 충분하다.
  - 전체: `set(ttl)`, `expire`, `ttl`, `persist` 네 가지를 둔다. 세션·레이트 리밋·모니터링까지 같은 기능을 쓸 수 있다.
- **결정 (`[확정]`, 2026-11-14)** — 네 가지 전체. `set(key, value, ttl)`, `expire(key, ttl)`, `ttl(key)`, `persist(key)`. HTTP는 `PUT /kv`의 선택 `ttl`, `POST /kv/expire`, `GET /kv/ttl`, `POST /kv/persist`.
- 판단 기준: 날씨 앱이 실제로 호출하는 표면, 테스트 가능성, HTTP 표면 증가, 기존 `PUT /kv` 계약과의 충돌.
- **상태** — `[확정]`

### L3. 덮어쓰기 TTL 정책

- 후보:
  - **기존 TTL 유지(`ldc` 제안)** — `set(key, value)`에 `ttl`이 없으면 기존 만료 시각을 유지한다. 캐시에서 TTL을 빠뜨려 영구 키가 되는 위험을 줄인다. 다만 Redis 기본과 다르고, 만료된 키를 덮어쓸 때 새 `value`가 즉시 만료되는 경계가 있다.
  - **TTL 초기화(Redis 기본)** — `set`이 TTL을 제거해 영구 키로 만든다. 예측 가능하지만, 앱이 TTL을 빠뜨리면 영구 캐시가 된다.
  - **명시적 TTL 필수** — 캐시 쓰기 경로는 항상 `ttl`을 전달한다. 저장소 정책과 별개로 앱 계약으로 강제한다. `ttl(key)` 테스트로 확인한다.
  - **만료 키는 새 키로 취급** — 덮어쓰기 전에 만료를 확인하고, 만료됐으면 기존 TTL을 물려주지 않는다.
- `[충돌 해소]` D-04에서 TTL 초기화(Redis 기본)로 결정했다. `jung-response-scenario.md`의 "덮어쓰면 TTL도 갱신"은 캐시 갱신 경로가 `ttl`을 명시하는 경우로 한정해 동기화한다.
- **결정 (`[확정]`, 2026-11-14)** — TTL 초기화(Redis 기본). `set`에 `ttl`이 없으면 기존 TTL을 제거한다. 캐시 갱신 경로는 `ttl`을 명시해야 하며, 이 규칙을 어기면 영구 키가 된다.
- **상태** — `[확정]`

### L4. 만료 경계와 판정 시점

- **결정 (`[확정]`, 2026-11-14)** — `현재 시각 >= 만료 시각`이면 만료로 본다. `get`은 만료된 키를 그 자리에서 삭제하고 `{"found": false}`를 반환한다. 판정 시점은 조회 시점이다.
- **시계 (`[확정]`, 2026-11-14)** — 벽시계의 절대 epoch 밀리초를 쓴다(B안). `_expires[key] = 현재 epoch ms + ttl ms`. `ttl` 응답은 `만료 시각 - 현재 epoch ms`다. 테스트는 가짜 벽시계를 주입한다.
- **이유** — TTL API는 기간을 받지만, `_expires`에 절대 만료 시각을 저장하면 향후 영속화를 도입할 때 그대로 복원할 수 있다. 영속화 자체는 04 범위에 넣지 않는다.
- **비용** — NTP 등으로 벽시계가 뒤로 가면 TTL이 늘어나고, 앞으로 가면 일찍 만료된다. 이 비용은 확장 가능성을 위해 받아들인다.
- **Redis 영속화와의 구분** — Redis는 RDB/AOF로 데이터와 TTL을 디스크에 저장할 수 있어, 재시작 뒤에도 복구할 수 있다. 설정에 따라 다르고, 다운타임이 TTL을 넘기면 로드 시 만료된다. 현재 MiniRedis는 영속화가 없어 재시작 시 상태를 잃는다.
- **상태** — `[확정]`

### L5. TTL 단위와 표시 규칙

- 후보: 정수 초, 밀리초, 둘 다.
- 날씨 TTL 600초에는 정수 초로 충분하다. 경계 테스트는 가짜 시계로 초를 즉시 진행시킬 수 있다.
- `ttl` 응답의 내림·반올림·올림과, 내부 저장 정밀도를 분리한다.
- **결정 (`[확정]`, 2026-11-14)** — 정수 밀리초. `set`·`expire`의 TTL 입력, `_expires`의 만료 시각, `ttl` 응답을 모두 정수 밀리초로 표현한다. 날씨 TTL 600초는 600,000ms다. 테스트는 가짜 시계를 밀리초 단위로 진행시킨다.
- **미정** — 소수 밀리초 허용 여부. 현재 결정은 정수 밀리초이며, 소수는 허용하지 않는 것으로 본다.
- **상태** — `[확정]`

### L6. `ttl`·`persist` 응답 형태

- **결정 (`[확정]`, 2026-11-14)** — 응답 형태는 아래와 같다. `ttl`은 정수 밀리초(D-06)다.
  - `ttl` — 키 있고 TTL 있음: `{"found": true, "ttl": 남은 밀리초}`, TTL 없음: `{"found": true, "ttl": -1}`, 키 없음·만료: `{"found": false}`.
  - `persist` — TTL 제거: `{"found": true, "persisted": true}`, TTL 없음: `{"found": true, "persisted": false}`, 키 없음·만료: `{"found": false}`.
  - `expire` — 키 있고 `ttl>0`: `{"found": true, "ttl": 방금 설정한 TTL}`; 키 있고 `ttl<=0`: 즉시 삭제 후 `{"found": true, "ttl": 0}`; 키 없음·만료: `{"found": false}`. 설정 직후에는 남은 TTL과 같은 값이다.
- 만료된 키에는 `ttl`·`persist`·`expire` 모두 `{"found": false}`를 반환한다.
- `expire`는 TTL을 제거하는 연산이 아니다. TTL 제거는 `persist`, 키와 `value`의 즉시 삭제는 `delete`다. `expire(key, 0)`은 L7에서 즉시 삭제로 확정했다.
- **상태** — `[확정]`

### L7. `ttl=0`·음수·명시적 `null`

- **결정 (`[확정]`, 2026-11-14)** — 아래와 같다.
  - `set`의 TTL은 양수만 허용한다. `ttl=0`과 음수는 `INVALID_INPUT`.
  - `expire(key, ttl<=0)`는 키와 `value`를 즉시 삭제한다. 응답은 `{"found": true, "ttl": 0}`.
  - `set`의 `"ttl": null`은 생략으로 취급한다. D-04에 따라 기존 TTL을 제거한다.
- **근거** — Redis의 `SET EX`/`PX`·`SETEX`/`PSETEX`는 0·음수에서 `ERR invalid expire time`으로 거절하고, `EXPIRE`/`PEXPIRE`는 0·음수에서 키를 삭제한다.
- **상태** — `[확정]`

### L9. active 만료 방식

- **후보 1: 요청마다 1개** — 커서를 하나 전진. 정상 상태에서 요청당 키 생성이 1개 이하면 생성 속도를 따라간다. 버스트·유휴에 약하다.
- **후보 2: 요청마다 3~5개** — 후보 1보다 3~5배 빠르다. 대신 매 요청 확인 비용이 늘고, 정상 상태에서는 살아 있는 키를 더 자주 확인해 낭비할 수 있다.
- **후보 3: 시간 기준** — 요청 수와 무관하게 일정 시간마다 확인. 백그라운드 타이머를 쓰면 현재 단일 이벤트 루프(`uvicorn workers=1`) 서버에 동시성이 생긴다. 요청 트리거로 시간 예산만 계산하는 변형은 스레드 없이 가능하다.
- **후보 4(제안): 만료 시각 힙** — `(만료 시각, key)` 최소 힙을 두고 요청마다 만료된 상단을 꺼낸다. 가장 이른 만료부터 정리하므로 콜드 키 정리 지연을 줄이는 데 유리하다. 힙 삽입과 만료 항목 꺼내기가 O(log n)이다. 임의 키 삭제는 힙에서 바로 빼지 않고, 꺼낼 때 현재 상태와 비교해 버리는 방식이다. 그래서 덮어쓰기·삭제로 생긴 낡은 항목이 임시로 쌓일 수 있다.
- **후보 5(제안): 요청 트리거 시간 예산** — 요청마다 경과 시간에 비례한 확인 예산을 계산해 상한까지 확인한다. 시간 기준의 장점을 스레드 없이 얻는다. 후보 1·2보다 구현이 복잡하다.
- **판단 기준** — 정리 지연 상한, 요청 지연 영향, 유휴 시 동작, 단일 이벤트 루프 서버 적합성, 테스트 결정성, 콜드 키 방문 보장.
- **결정 (`[확정]`, 2026-11-14, D-24)** — 시간 기준. FastAPI `lifespan`이 100ms 주기 타이머 task를 소유하고, 요청 수와 무관하게 active 사이클을 실행한다. TTL 키는 별도 `_expires` 해시 테이블에만 둔다. Redis의 expires 딕셔너리와 serverCron·activeExpireCycle에서 착안했다.
- **상태** — `[확정]` (방식), 세부 확인 순서·예산은 L10에서 정한다.

### L10. active 만료 파라미터

- 후보 3·5를 쓰면 목표 순회 시간, 최소·최대 초당 확인 수, 요청당 상한을 정해야 한다.
- 후보 1·2를 쓰면 요청당 확인 수와 커서 보정 규칙을 정해야 한다.
- 후보 4를 쓰면 요청당 최대 꺼내는 수와 힙 압축 주기를 정해야 한다.
- **결정 (`[확정]`, 2026-11-14)** — 무작위 표본. `_expires`에서 표본을 뽑아 만료를 확인하고, 만료 비율이 높으면 반복한다. Redis active expire와 같은 계열이다.
- **파라미터 (`[확정]`, 2026-11-14)** — 표본 20개, 표본의 25% 이상이 만료면 같은 트리거에서 1회 더(최대 2회), 초당 최대 10회, 마지막 사이클에서 100ms 이상 지났으면 1회 실행. 테스트는 시드 고정 RNG 또는 표본 선택기 주입으로 재현한다.
- **현재 상태** — 표본 중복은 중복 없음으로 확정했다(2026-11-14). active 사이클을 요청 처리 진입 시 실행할지 종료 시 실행할지, 어떤 연산이 트리거할지는 아직 미정이다.
- **상태** — `[확정]` (방식·파라미터), 세부 실행 규칙은 미정.

### L11. 유휴 시 정리와 백그라운드 타이머

- 날씨 서비스가 상시 트래픽이면 요청 트리거 정리로 충분할 수 있다.

### L12. TTL 인덱스 자료구조

- 후보: `key → 만료 시각` 딕셔너리 + 순회용 목록, 메인 `_data` 항목에 만료 시각 포함, `(만료 시각, key)` 힙.
- **결정 (`[확정]`, 2026-11-14)** — `_data`와 분리된 `_expires` 딕셔너리를 둔다. `_expires`에는 TTL이 있는 키만 담고, 각 키의 만료 시각을 함께 저장한다. 만료 시각은 벽시계의 절대 epoch 밀리초다(L4). `_data`는 TTL이 없는 키를 포함한 전체 키를 보관한다.
- **확정** — 확인 방식은 L10에서 무작위 표본으로 정했다. 만료 시각의 내부 단위는 L5에서 정수 밀리초로 정했다.
- **결정 (`[확정]`, 2026-11-14)** — 보조 인덱스는 `_ttl_keys` 배열 + `_ttl_pos` 위치 맵으로 한다(C안). `_ttl_keys`는 TTL이 있는 키의 배열, `_ttl_pos`는 `key → _ttl_keys에서의 위치`다. 삭제는 마지막 원소와 swap한 뒤 pop하며, 마지막에서 옮겨온 키의 위치도 갱신한다. `_expires`가 TTL의 진실원이고, 두 구조는 표본 선택용 보조 인덱스다.
- **제약** — Python `dict`는 Redis의 `dictGetRandomKey`처럼 O(1) 랜덤 키 선택을 제공하지 않는다. `random.choice(list(_expires))`는 O(N) 복사가 필요하다. 그래서 `_ttl_keys`·`_ttl_pos`를 둔다.
- **범위 밖 후보** — 커스텀 해시 테이블(bucket 배열)은 O(1) 랜덤 키 선택을 줄 수 있지만, 현재 `AGENTS.md`의 "Python `dict` 사용" 결정을 바꾸는 별도 작업이다. TTL 표본 구조 결정과 분리해 검토한다.
- R14의 불변 조건을 만족해야 한다.
- **상태** — `[확정]` (자료구조와 보조 인덱스).

#### L12.1 갱신 규칙

| 연산 | `_data` | `_expires` | `_ttl_keys` / `_ttl_pos` |
| --- | --- | --- | --- |
| `set(key, value, ttl)` — 새 TTL | `value` 저장 | 추가 | 목록 끝에 추가, 위치 기록 |
| `set(key, value, ttl)` — 기존 TTL 갱신 | `value` 저장 | 만료 시각 갱신 | 변화 없음 |
| `set(key, value)` — TTL 없음(D-04) | `value` 저장 | 있으면 제거 | 있으면 swap-pop 제거 |
| `expire(key, ttl > 0)` | 변화 없음 | 추가·갱신 | 없으면 목록 끝에 추가 |
| `expire(key, ttl<=0)` | 키 제거 | 제거 | swap-pop 제거 |
| `persist(key)` | 변화 없음 | 있으면 제거 | 있으면 swap-pop 제거 |
| `delete(key)` | 키 제거 | 있으면 제거 | 있으면 swap-pop 제거 |
| lazy 만료(`get` 등) | 키 제거 | 제거 | swap-pop 제거 |
| active 만료 | 키 제거 | 제거 | swap-pop 제거 |

- `expire(key, ttl<=0)`의 삭제 동작은 D-11·D-12에서 확정했다.
- L12.1의 각 연산은 시작 시 lazy 만료 검사를 적용한다(L8). 만료된 키는 없는 키로 취급한 뒤 표의 동작을 수행한다.
- swap-pop은 `i = _ttl_pos.pop(key)`, `last = _ttl_keys.pop()`, `i < len(_ttl_keys)`이면 `_ttl_keys[i] = last`, `_ttl_pos[last] = i`, 마지막에 `del _expires[key]` 순서로 한다. `key`가 마지막 원소이면 `i == len(_ttl_keys)`가 되어 swap을 건너뛴다.

#### L12.2 불변 조건과 테스트

- `set(_expires) == set(_ttl_keys) == set(_ttl_pos)`
- 모든 `key`에 대해 `_ttl_keys[_ttl_pos[key]] == key`
- `len(_expires) == len(_ttl_keys) == len(_ttl_pos)`
- `_ttl_keys`에 중복 키가 없다.
- 각 연산 직후 위 조건을 확인한다: 새 TTL, TTL 갱신, TTL 없는 덮어쓰기, `delete`, `persist`, `expire`, lazy 만료, active 만료, 삭제 후 재추가.
- `ttl_snapshot(store)` 같은 테스트 전용 도구로 세 구조를 관찰한다. HTTP로 내부 구조를 노출하지 않는다.
- 기존 `snapshot(store)`는 `_data`만 보므로 01 테스트는 그대로 둔다.

## 6. 기존 문서와의 충돌·동기화 대상

### 6.1 충돌

- **덮어쓰기 TTL** — D-04에서 TTL 초기화(Redis 기본)로 해소했다. `jung-response-scenario.md`의 "덮어쓰면 TTL도 갱신"은 캐시 경로가 `ttl`을 명시하는 경우로 한정해 동기화해야 한다. `ldc-scenario-template.md`의 "기존 TTL 유지" 제안은 채택하지 않는다.
- **예제 입력** — `04-response-cache-scenario.md`와 `jung-response-scenario.md`는 `api:hello`, `{"message":"hello"}`를 예시로 쓴다. 문제 상황을 날씨로 바꾸면 이 예제를 날씨 키·응답으로 교체할지, 최소 예제로 남길지 정해야 한다.
- **성능 서술** — 날씨 캐시의 적중률 개선을 03의 카운터 성능 비교와 섞지 않는다. 03은 카운터 작업의 비교다.

### 6.2 이미 맞닿아 있는 내용

- `chan-scenario-template.md`의 축 2에는 이미 "날씨 정보를 Mini Redis에 10분간 보관한다"는 예시가 있다. 이번 확정은 새로운 개념을 추가하는 것이 아니라, 그 예시를 04의 대표 문제 상황으로 끌어올리는 것이다.
- `jung-response-scenario.md`의 원본 호출 횟수 관찰, TTL 시작 시점, 실패 처리 기재는 날씨 시나리오에도 참고할 수 있다. 다만 개인 메모의 기재이므로 확정 계약으로 쓰기 전에 다시 확인한다. 덮어쓰기 TTL 문장은 `ldc`의 제안과 충돌한다.

### 6.3 결정 후 동기화할 문서

- `04-response-cache-scenario.md` — 사용자 시나리오, S4-01~03 예제, 범위·완료 판단, TTL 계약 링크.
