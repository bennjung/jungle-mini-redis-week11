# 테스트 시나리오 초안 검토 메모

검토 대상: [4. API 응답 재사용·만료·수동 무효화](04-response-cache-scenario.md)와 [phase.md](../phase.md).

이 메모는 이 두 문서만을 근거로 한다. 04번은 앞선 시나리오 이후의 고도화 iteration이므로, 앞선 문서에서 정한 계약과 다른 동작을 이번에 정할 수 있다고 본다. 다만 04번 안의 시나리오끼리는 같은 전제를 공유해야 한다.

04번 문서의 ‘API 응답 재사용’ 소재는 이 메모에서 다루지 않는다. 아래 내용은 논의를 위한 개인 의견이며 확정된 계약이 아니다.

## 도입: 무효화가 필요한 이유

무효화는 **저장된 데이터가 더 이상 유효한 것으로 취급되지 않는 상태**를 뜻한다. 삭제는 그 상태를 만드는 수단 중 하나다. 아래 세 축은 무효화가 필요한 서로 다른 이유이며, 요구하는 저장소의 역할과 검증 대상이 각각 다르다. 각 축에 적은 사용자 상황은 설명을 위한 가정이며, 실제로 관찰된 문제가 아니다.

### 축 1. 단일 원본에서 데이터 자체의 유효성 상실

**사용자 상황(예시).** 인증 서비스를 운영하는 개발자는 인증번호를 Mini Redis에 보관하고, 여러 대의 인증 서버가 같은 저장소를 조회한다. 사용자는 인증번호를 받은 뒤 정해진 시간 안에 입력해야 한다. 만료 검사를 서버마다 하면, 시계나 코드가 다른 서버에서 기간이 지난 인증번호가 통과될 수 있다.

여러 클라이언트가 같은 저장소의 같은 데이터를 조회하고, 그 데이터에는 유효 기간이 있다. 클라이언트마다 만료를 판단하면 시계, 검사 코드, 조회 시점의 차이로 같은 데이터에 대한 판단이 갈라진다. **원본이 판단하면 같은 기준이 적용된다.**

저장소가 보장하는 범위는 조회 시점의 유효성이다. 클라이언트가 응답을 받은 뒤 값을 사용하는 시점의 유효성까지 보장하지는 않는다.

### 축 2. 다른 원본의 캐시

**사용자 상황(예시 1 — 원본 변경).** 상품 서비스 앞에서 데이터를 보관하는 개발자는 상품 정보를 Mini Redis에 사본으로 둔다. 운영자가 상품 가격을 바꾸면, 사본은 이전 가격을 계속 보여준다. 원본이 바뀐 사실을 저장소가 알 수 없으므로, 가격 변경을 처리하는 쪽에서 사본을 무효화해야 한다.

**사용자 상황(예시 2 — 시간 경과).** 날씨 서비스 앞에서 데이터를 보관하는 개발자는 날씨 정보를 Mini Redis에 10분간 보관한다. 10분이 지나면 원본이 바뀌지 않았더라도 사본을 다시 받아온다. 원본 변경을 통지받을 수 없는 외부 서비스라면 시간이 유일한 무효화 기준이 된다.

Mini Redis가 다른 시스템의 데이터 사본을 보관하면, 원본이 바뀌었을 때 사본은 낡은 데이터가 된다. 저장소는 원본의 변경을 스스로 알 수 없으므로 **외부에서 온 무효화 신호**가 필요하다. 원본 변경을 알 수 없을 때는 **시간 경과**가 사본을 버리는 기준이 된다.

두 경우는 같은 축이지만 계기가 다르다. 원본 변경은 사본이 틀린 것이고, 시간 경과는 원본은 유효할 수 있지만 사본이 오래된 것이다. 축 1의 시간 만료는 데이터 자체의 유효 기간이 끝난 경우이므로 이것과도 구분된다.

같은 축의 다른 예로 사용자 프로필 수정 후 무효화, 권한 회수 후 즉시 무효화가 있다.

관찰 결과는 삭제와 같을 수 있지만 소유권이 다르다. Mini Redis가 원본이면 데이터 폐기이고, 캐시면 사본 폐기다. 응답 재사용 소재는 이 축의 예시로 쓰지 않는다.

### 축 3. 대량 무효화의 효율

**사용자 상황(예시).** 보안 담당자는 침해가 의심되는 조직의 사용자 세션 3만 개를 한 번에 끊어야 한다. 세션 키를 하나씩 삭제하면 요청도 3만 번, 저장소 연산도 3만 번 필요하다. 조직 단위로 한 번에 무효화하면 요청 1회로 끝난다.

이처럼 수만 개의 검색 결과나 세션을 한 번에 무효화하는 상황에서는 개별 요청의 수가 곧 비용이 된다. **그룹 단위로 한 번에 폐기하면 왕복이 1회로 줄어든다.**

`phase.md`는 대량 무효화를 명시하지 않는다. 이 축은 무효화가 필요한 상황을 설명하는 예이며, 04번 검증 범위에 넣을지는 별도로 정한다. 도입한다면 개별 삭제와 관찰 결과가 같아야 한다는 정합성 조건이 04번 안에 생긴다.

## 검토 메모

### 빠진 상황

- **축 1**
  - 기존 S4-01~03은 응답 재사용 소재라 요구사항 근거가 없다. 응답과 무관한 데이터 자체의 만료가 비어 있다.
  - 유효 기간이 있는 키와 없는 키가 함께 있을 때 서로 영향을 주지 않는지.
  - 만료된 키와 처음부터 없던 키의 조회 결과가 같은지 다른지.
  - 만료 전에 같은 키를 다시 저장하면 유효 기간이 유지·변경·해제되는지.
- **축 2**
  - 무효화 후 원본을 다시 조회하는 경로가 초안에 없다.
  - 원본 변경 전에 저장한 사본과 변경 후 저장한 사본을 구분할 수 있는지.
  - 원본이 바뀌지 않았는데 시간만 지나 사본을 버리는 경우가 초안에 없다.
  - 원본 변경 신호와 시간 경과가 같은 사본에 겹칠 때.
- **축 3**
  - 여러 키를 한 번에 무효화하는 상황이 04번 초안 어디에도 없다.
  - 그룹 경계에 걸친 키와 다른 그룹 키가 보존되는지.
  - 대량 무효화 후 같은 그룹에 다시 저장하면 유효한지.

### 다른 의견

- **무효화를 삭제의 다른 이름으로 두면** 축 2의 소유권 구분과 축 3의 그룹 단위 폐기를 표현할 수 없다. 축 1은 개념만으로 충분하고, 연산은 기존 `delete(key)`로 달성된다.
- **세 축을 한 시나리오에 섞지 말자.** 요구하는 저장소 역할과 실패 원인이 서로 다르다.
- **세 축이 같은 결과를 전제해야 한다.** 유효 기간 만료, 외부 무효화, 그룹 무효화가 조회에서 서로 다른 ‘유효하지 않음’을 만들면 04번 안에서 정합성이 깨진다.
- **축 3은 범위 결정이 먼저다.** 상황 설명으로는 유효하지만, 04번의 검증 대상에 넣을지부터 정한다.
- **데이터 내용이 같다는 사실로 무효화를 입증하지 않는다.** 저장소에서 얻은 값이 사용되었는지 관찰할 수 있어야 한다.
- **사용자 무효화의 위치** — `phase.md`가 요구하는데 세 축에 없다. 축 1의 만료와 같은 결과를 내야 하는지, 별도 시나리오가 필요한지 정해야 한다.
- **축 2의 두 계기를 분리하자.** 원본 변경과 시간 경과는 기대 결과가 같아도 실패 원인이 다르다. 원본 변경 쪽이 실패하면 무효화 신호 처리 문제이고, 시간 경과 쪽이 실패하면 기간 판정 문제다.

### 미정 사항에 대한 생각

- **유효 기간 지정** — 저장 시 함께 지정하는지 별도 호출인지, 기간을 지정하지 않은 데이터의 취급.
- **시간 기준** — 기간의 단위와 시작 시점, 시간 진행을 재현하는 방법.
- **만료 경계** — 만료 직전·정확한 만료 시각·직후의 기대 결과.
- **재저장과 갱신** — 만료 전 재저장, 만료 후 재저장, 만료 전 삭제의 각 동작.
- **무효화 신호** — 축 2에서 외부가 보내는 신호의 형태. `delete(key)`와 같은지 다른지.
- **사본 보관 기간** — 축 2의 시간 경과에서 기간을 어떻게 지정하고, 원본 변경 신호와 함께 쓰는지.
- **그룹 정의** — 축 3에서 무엇을 같은 그룹으로 볼지, 그룹을 등록해야 하는지.
- **실제 제거** — 판정 후 메모리에서 제거하는 시점과 이번 검증 포함 여부.
- **동시 요청** — 여러 클라이언트의 조회·갱신과 만료·무효화가 겹치는 상황의 포함 여부.
- **성능 비교** — 축 3의 개별 삭제 반복 대비 효과를 이번 검증에 넣을지, 넣는다면 어떤 조건으로 비교할지.

## 합의한 사항

- 만료된 키와 처음부터 없던 키의 조회 결과를 `{"found": false}`로 통일한다. 응답 필드 구성까지 같다.
- 판단 기준은 조회 시점의 유효성이다. 메모리에서 실제 제거를 했는지와 무관하게 결과가 같아야 한다.

## 이 결정에 따라 확인할 것

- 유효하지 않은 키에 대한 삭제 결과를 `{"found": false}`로 두는 것이 위 결정과 일관되는지.
- 만료된 키에 다시 저장할 때 새 유효 기간을 적용하는지.
- 만료 여부 진단이 필요해질 때 조회 응답과 분리할 수단을 둘지.

## 추가 제안: 축별 시나리오 후보

아래는 축마다 분리한 후보이며, 응답 재사용 소재의 S4-01~03은 이 메모에서 다루지 않는다.

### S4-04. 단일 원본에서 유효 기간이 지난 데이터 (축 1)

- 사전 상태: 같은 저장소를 여러 클라이언트가 사용한다. 키 `session:one`의 `value`가 유효 기간과 함께 저장되어 있다. 유효 기간이 없는 다른 키가 함께 있다.
- 입력·행동: 유효 기간 안에 두 클라이언트가 `session:one`을 조회한다. 기간이 지난 뒤 같은 키를 다시 조회한다.
- 검증 시점: 각 조회 응답 수신 후.
- 기대 결과: 기간 안에는 저장한 `value`가 반환되고 두 클라이언트의 결과가 같다. 기간이 지난 뒤에는 `{"found": false}`가 반환되며, 처음부터 없던 키의 조회 결과와 필드 구성까지 같다. 유효 기간이 없는 키는 그대로 조회된다.
- 유지 조건: 다른 키의 `value`와 유효 기간은 변하지 않는다. 기간이 지난 뒤 다시 조회해도 이전 값이 되살아나지 않는다.
- 실행 범위: 외부 사용 경로(HTTP). 설계 후 호출 대상을 명시한다.
- 미정: 유효 기간 지정 방법, 단위와 시작 시점, 만료 경계, 클라이언트 수, 시간 진행 재현 방법.

### S4-05. 다른 원본의 사본 무효화 (축 2)

- 사전 상태: 다른 시스템의 데이터(예: 상품 가격)를 저장소에 사본으로 보관했다. 원본은 이후 변경된다.
- 입력·행동: 사본을 조회한 뒤 원본이 변경되고, 외부에서 해당 사본의 무효화 신호를 보낸다. 이어서 같은 사본을 다시 조회한다.
- 검증 시점: 무효화 후 재조회 응답 수신 시.
- 기대 결과: 무효화 전에는 사본이 반환된다. 무효화 후에는 이전 사본이 유효한 값으로 반환되지 않는다.
- 유지 조건: 같은 원본의 다른 사본이나 다른 키는 영향을 받지 않는다. 원본 재조회 결과가 이전 사본과 같을 수 있으므로 `value` 내용만으로 판정하지 않는다.
- 실행 범위: 외부 사용 경로(HTTP). 원본 변경과 무효화 신호를 어떻게 재현할지 설계 후 명시한다.
- 미정: 무효화 신호의 형태와 응답, 원본 변경 재현 방법, 무효화 후 원본 재조회 여부, 내용 외 관찰 방법.

### S4-05-01. 시간 경과로 사본 무효화 (축 2)

- 사전 상태: 다른 시스템의 데이터를 저장소에 사본으로 보관했고, 보관 기간이 함께 지정되어 있다. 원본은 변경되지 않았다.
- 입력·행동: 보관 기간 안에 사본을 조회한다. 기간이 지난 뒤 원본을 변경하지 않은 채 같은 사본을 다시 조회한다.
- 검증 시점: 기간 경과 후 재조회 응답 수신 시.
- 기대 결과: 기간 안에는 저장한 사본이 반환된다. 기간이 지난 뒤에는 원본이 그대로여도 이전 사본이 유효한 값으로 반환되지 않는다.
- 유지 조건: 같은 원본의 다른 사본과 보관 기간이 없는 키는 영향을 받지 않는다. 원본 재조회 결과가 이전 사본과 같을 수 있으므로 `value` 내용만으로 판정하지 않는다.
- 실행 범위: 외부 사용 경로(HTTP). 시간 진행을 어떻게 재현할지 설계 후 명시한다.
- 미정: 보관 기간 지정 방법과 단위, 만료 경계, 만료 후 원본 재조회 여부, 원본 변경과 시간 경과가 같은 사본에 겹칠 때의 처리.

### S4-06. 그룹 단위 대량 무효화 (축 3)

- 사전 상태: 같은 그룹에 속한 키 N개와 다른 그룹의 키가 저장되어 있다. N은 합의로 정한다.
- 입력·행동: 한 그룹에 대해 무효화를 1회 수행한 뒤, 그룹 키와 다른 그룹 키를 각각 조회한다.
- 검증 시점: 무효화 완료 후 각 조회 응답 수신 시.
- 기대 결과: 그룹 키는 유효한 값으로 반환되지 않는다. 다른 그룹의 키는 그대로 조회된다.
- 유지 조건: 키 N개를 개별 삭제한 경우와 관찰 결과가 같다. 무효화 후 같은 그룹에 새로 저장한 키는 유효하다.
- 실행 범위: 외부 사용 경로(HTTP). 개별 삭제 반복과의 요청 수·시간 비교는 별도 시나리오로 분리한다.
- 미정: 그룹 정의와 등록 방법, N, 무효화 요청·응답, 04번 범위 포함 여부, 성능 비교 포함 여부.

모임에서 기존 초안과 이 의견을 함께 검토한다. 합의한 내용만 대상 문서에 반영하며, 개인 메모를 확정 계약으로 취급하지 않는다. 설계와 코드는 아직 작성하지 않는다.
