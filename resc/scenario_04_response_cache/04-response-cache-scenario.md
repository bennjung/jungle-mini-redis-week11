# 4. API 응답 재사용·만료·수동 무효화

## 상태와 근거

- 04의 문제 상황은 **사용자의 현재 위치 기반 날씨 조회**로 확정했다. (2026-11-14, D-01)
- TTL 동작과 재사용 정책은 [TTL 계약](../scenario_01_storage/01-ttl-contract.md)과 [TTL/LDC 결정 로그](04-weather-ttl-decision-log.md)를 따른다. 이 문서는 그 계약을 사용하는 소비자 시나리오다.
- 아래 테스트 시나리오는 초안이다. 정확한 가짜 원본 응답·TTL 값·검증 시점은 아직 확정하지 않았다.
- 요구사항 원문: [phase.md](../phase.md)의 간단한 API 응답 저장·활용, 만료된 값 요청 처리, 사용자에 의한 데이터 무효화.
- 공통 개발 흐름: [AGENTS.md](../../AGENTS.md).
- 선행 문서: [1. 외부에서 값 보관·조회·폐기](../scenario_01_storage/01-storage-scenario.md), [01 TTL 계약](../scenario_01_storage/01-ttl-contract.md).
- 카운터 시나리오와 구별되는 응답 저장·활용 사례다. 카운터 완료만으로 이 요구사항을 충족했다고 보지 않는다.
- 저장소에는 API 응답의 JSON을 UTF-8 글자로 보관한다. 저장소가 JSON 구조를 해석하거나 객체 타입으로 바꾸지 않는다. 키는 1~256바이트, 문자열 `value`는 0~65,536바이트이며 세부 계약은 문서 1을 따른다.
- 날씨 앱은 별도 `/weather` 엔드포인트로 구현하지 않는다. 테스트 하네스가 KV HTTP API를 직접 호출하고, 원본은 가짜 함수로 대체한다. (D-15)

## 사용자 시나리오

사용자가 스마트폰에서 현재 위치를 보내면 날씨 서비스가 해당 위치의 날씨를 조회한다. 서비스는 아직 유효한 원본 응답을 MiniRedis에서 재사용한다. 보관 기간이 지났거나 사용자가 무효화한 응답은 유효한 저장 응답으로 재사용하지 않는다.

- **핫 키** — 서울역·강남역처럼 반복 조회되는 위치. 다음 조회가 발생하므로 lazy 만료로 충분하다.
- **콜드 키** — 산길·외곽·여행지처럼 한 번 조회하고 다시 접근하지 않는 위치. active 만료가 TTL 키를 회수한다.
- 좌표 정규화와 캐시 키 형식은 문제 상황 설명이다. 테스트는 `weather:37.566:126.978` 같은 고정 키를 쓴다.

## 범위와 완료 판단

- 포함: API 응답 저장·재사용, 만료된 값의 요청 처리, 단일 키 수동 무효화.
- 제외: 장애 복구, 여러 원본 사이의 자동 동기화, 재고·호출 제한 정책, 동시성·stampede·single-flight, 대량 무효화, 날씨 앱 엔드포인트.
- 완료 판단: 테스트 하네스가 KV HTTP API로 세 동작을 각각 확인하고, 원본 호출 수로 재사용과 재조회를 구분한다.
- 수동 삭제와 시간 만료는 별개의 검증 대상이다.
- 만료된 값을 사용하지 않는 시점과 메모리에서 실제 제거하는 시점은 같은 것으로 가정하지 않는다.
- 04의 동시성은 순차 요청만 다룬다. 서버는 단일 이벤트 루프·`uvicorn workers=1`로 요청을 하나씩 처리한다. (D-18)

## 테스트 시나리오 초안

### S4-01. 보관한 API 응답 재사용

- 사전 상태: 키 `weather:37.566:126.978`이 없다. 가짜 원본 응답은 `{"temperature":22,"observed_at":"2026-11-14T12:00:00Z"}`이고, 저장소에는 이 내용을 글자로 저장한다.
- 입력·행동: 하네스가 원본 응답을 받아 TTL 600,000ms(예시)와 함께 저장하고, 아직 유효한 동안 같은 응답을 다시 요청한다.
- 검증 시점: 두 번째 요청의 응답 수신 후.
- 기대 결과: 저장한 응답 내용이 재사용되고, 원본 호출 수는 1회를 유지한다.
- 유지 조건: 응답 내용이 같다는 사실만으로 재사용을 입증하지 않는다. 원본 호출 수로 저장 응답 사용을 확인한다.
- 미정: 가짜 원본의 정확한 응답 스키마, 정확한 테스트 TTL, 키 정규화 규칙.

### S4-02. 만료된 응답을 재사용하지 않음

- 사전 상태: S4-01의 응답을 TTL 600,000ms(예시)와 함께 저장했다.
- 입력·행동: 가짜 벽시계를 `now == 만료 시각`까지 진행하고 같은 응답을 요청한다.
- 검증 시점: 만료 이후 요청의 응답 처리 완료 시.
- 기대 결과: 만료된 저장 응답을 유효한 값으로 재사용하지 않고, 원본을 다시 호출해 새 응답을 저장한다.
- 유지 조건: 만료 이후 같은 값을 요청해도 이전 저장 응답이 유효한 것으로 되살아나지 않는다.
- 미정: 경계 입력 `now == expiry`와 `now > expiry`의 정확한 테스트 값, 원본 재조회 결과.

### S4-03. 사용자가 응답을 수동 무효화

- 사전 상태: S4-01의 응답이 저장되어 있고 아직 만료되지 않았다.
- 입력·행동: `DELETE /kv?key=weather%3A37.566%3A126.978`로 무효화한 뒤 같은 응답을 다시 요청한다.
- 검증 시점: 무효화 성공 후 새 요청의 응답 처리 완료 시.
- 기대 결과: 무효화 이전의 저장 응답을 재사용하지 않고, 원본을 다시 호출한다.
- 유지 조건: 다른 키에 저장된 응답에는 영향을 주지 않는다. 원본 재조회 결과가 이전 응답과 같을 수 있으므로 응답 내용만으로 무효화를 입증하지 않는다.
- 미정: 무효화 후 사용자에게 전달할 응답, 원본 장애 시 동작.

> S4-04~06(축 1·2·3 후보)은 [chan-scenario-template.md](chan-scenario-template.md)의 검토 메모에 남아 있다. 이 문서의 확정 범위가 아니며, 대량 무효화(S4-06)는 D-19에서 제외했다.

## 계약 확정 전에 합의할 사항

- 가짜 원본의 정확한 응답 스키마.
- 원본 API 실패는 MiniRedis의 계약이 아니다. 소비자 앱의 책임이며, 이 시나리오는 실패 응답을 정의하지 않는다.
- TTL 값과 만료 경계의 정확한 테스트 입력.
- 무효화 후 사용자에게 전달할 응답.
- 테스트 하네스의 요청 순서와 원본 호출 수 관찰 방법.

TTL 자체의 동작(경계, lazy/active, 응답 형태, 시계)은 [TTL 계약](../scenario_01_storage/01-ttl-contract.md)을 따른다. 이 문서에서 다시 정의하지 않는다.
