# 1. 외부에서 값 보관·조회·폐기

## 상태와 근거

- 아래의 확정된 행동 계약은 사용자 승인 사항이다. 테스트에는 이 계약을 반영하되, 응답의 정확한 표현·호출 방식 등 미정 부분까지 확정된 것으로 간주하지 않는다.
- 요구사항 원문: [phase.md](phase.md)의 해시 테이블 기반 저장소, 외부 사용, API 형태, 데이터 무효화, 저장·조회·삭제 단위 테스트 및 외부 사용 기능 테스트.
- 공통 개발 흐름: [AGENTS.md](../AGENTS.md).
- 이 문서는 외부 행동, 승인된 HTTP API, HTTP와 저장소 사이의 함수 계약 및 저장소 단위 테스트 경계를 정의한다. 저장소는 `storage.py`의 `MiniRedis` 클래스이며, 각 인스턴스의 Python `dict`에 키·`value`를 보관한다. 동시 호출 조건은 아직 결정하지 않는다.

## 사용자 시나리오

외부 사용자가 값을 보관하고 나중에 같은 키로 조회한다. 더 이상 유효하지 않은 값은 사용자가 삭제하여 이후 조회에서 재사용되지 않게 한다.

## 범위와 완료 판단

- 포함: 외부 저장·조회·삭제, 사용자 요청에 의한 키 무효화.
- 제외: 동시 증가, 시간 만료, 성능 우위, 장애 복구.
- 완료 판단: 합의된 저장·조회·삭제 테스트를 단위 수준과 외부 사용 경로에서 검증한다.
- 해시 테이블 사용 여부와 핵심 로직 설명 가능 여부는 행동 테스트와 별도로 확인한다.
- 이 단계만으로 읽기-수정-쓰기 경합 문제가 해결되었다고 보고하지 않는다.

## 확정된 행동 계약

- 같은 키에 다시 저장하면 새 값으로 덮어쓴다.
- 없는 키 조회는 저장된 `value`와 구분되는 ‘없음’을 반환한다. 삭제된 키와 처음부터 없는 키 모두 키가 없는 상태다.
- 한 키를 삭제할 때 키가 있으면 실제로 삭제한 값을 반환한다. 없으면 조회의 ‘없음’과 같은 의미를 반환한다. 반복 삭제는 첫 삭제 이후 ‘없음’을 반환하며 오류로 취급하지 않는다.
- 이번 범위에서 여러 키를 한 번에 삭제하는 기능은 추가하지 않는다.
- 키의 `null`과 빈 문자열 `""`은 거부한다. 키는 UTF-8 텍스트이며 크기는 1~256바이트다.
- `value`는 UTF-8 텍스트 문자열 또는 실제 `null`을 허용한다.
- 문자열 `value`는 자동으로 숫자·객체로 해석하지 않고 그대로 보존한다. JSON도 내부 구조를 해석하지 않고 글자로 보관한다. 임의 바이트열 지원은 이번 범위가 아니다.
- 빈 문자열 `value`와 실제 `null`인 `value`를 모두 허용하며, 각각 키가 없는 상태와 구분한다. 문자열 `"null"`도 실제 `null`과 구분한다. `null` 저장은 키 삭제가 아니다.
- 문자열 `value`의 크기는 0~65,536바이트(64KiB)다. 키·문자열 `value` 크기는 글자 수가 아니라 UTF-8로 표현한 바이트 수로 측정하고, 상한을 포함한다. 실제 `null`은 문자열 `"null"`로 변환하여 측정하지 않는다.
- 크기 초과 등 입력이 잘못되어 거절된 경우 기존 값과 다른 키는 변경되지 않는다. 요청 실패 전반의 보장 범위까지 확정한 것은 아니다.
- `set`·`get`·`delete`는 모두 키의 타입·UTF-8 표현 가능 여부·크기를 검증한다. 문자열 외 키, UTF-8로 인코딩할 수 없는 키, 빈 키와 크기 초과 키는 `{"error": "INVALID_INPUT"}`으로 거절한다.
- `set`의 문자열·실제 `None` 외 `value`와 UTF-8로 인코딩할 수 없는 문자열 `value`도 같은 오류로 거절한다. 모든 검증은 상태 변경 전에 수행한다. Python 함수 인자 누락은 별도이며 HTTP 입력 해석 오류는 [HTTP 담당 범위](01-http-scope.md)를 따른다.
- 크기 상한은 현재 사용자 문제와 작은 API 응답 예제를 위한 초기 계약이며, Redis의 제한을 복제하거나 성능 측정으로 도출한 수치가 아니다. 변경 시 계약 수정 승인을 받는다. 항목별 크기 제한만으로 전체 메모리 사용량을 제한하지는 않는다.

### 확정된 조회·삭제 결과 표현

- 키가 있으면 `{"found": true, "value": ...}`를 반환한다. `value`는 보관된 문자열 또는 실제 `null`이며 빈 문자열도 그대로 반환한다.
- 키가 없으면 `{"found": false}`를 반환하고 `value` 필드는 생략한다. 키 없음은 오류가 아니다.
- 조회의 `found`는 키 존재 여부, 삭제의 `found`는 실제로 삭제한 키가 있었는지를 뜻한다. 삭제 결과의 `value`는 삭제 직전 보관된 내용이다.
- 실제 `null`인 `value`를 삭제하면 첫 결과는 `{"found": true, "value": null}`, 반복 삭제 결과는 `{"found": false}`다.
- 위 결과의 의미와 필드 구성, 외부 통신에 HTTP + JSON을 사용하는 방침은 확정되었다.
- 아래 최소 HTTP API가 승인되었다. HTTP 선택을 Redis 통신 규약 호환 요구로 해석하지 않는다. 미정 입력·운영 정책까지 확정된 것은 아니다.

### 확정된 최소 HTTP API

- 구현 언어는 Python, 웹 프레임워크는 Flask, 테스트 도구는 pytest다. Python·Flask 버전은 아직 미정이다. HTTP 담당의 상세 계약·설계·구현·검증 기록은 [HTTP 담당 범위](01-http-scope.md)를 따른다.

| 동작 | 요청 | 정상 응답 |
| --- | --- | --- |
| 저장·덮어쓰기 | `PUT /kv`, JSON 본문 `{"key":"sample:one","value":"hello"}` | HTTP 200, `{"ok":true}` |
| 조회 | `GET /kv?key=sample:one` | HTTP 200, 위에서 정한 `found`·`value` 결과 |
| 삭제 | `DELETE /kv?key=sample:one` | HTTP 200, 위에서 정한 `found`·`value` 결과 |

- 저장의 `value`는 문자열 또는 실제 `null`이다. `{"key":"sample:null","value":null}`은 정상 입력이다. `value` 필드 누락과 실제 `null`은 구분한다.
- 조회·삭제의 키는 쿼리 매개변수 `key`로 전달한다. 문자열의 실제 내용이 바뀌지 않도록 URL 인코딩하며 크기는 해석한 키의 UTF-8 바이트 수로 판정한다.
- 키 없음은 HTTP 200과 `{"found":false}`다. HTTP 404나 `value:null`로 대체하지 않는다.
- 확정된 입력 제한 위반은 HTTP 400과 `{"error":"INVALID_INPUT"}`으로 거절하고 기존 `value`와 다른 키를 보존한다.
- 문자열 `value` 크기는 JSON 본문 전체 길이나 이스케이프 표기의 길이가 아니라, JSON을 해석하여 얻은 문자열의 UTF-8 바이트 수로 판정한다.
- JSON·본문 구조·필수 필드 오류는 HTTP가 저장소 호출 없이 같은 400 응답으로 거절하고, 키·`value` 타입·크기는 저장소가 검사한다. 상세 입력 계약과 남은 미정 정책은 [HTTP 담당 범위](01-http-scope.md)를 따른다.

## 확정된 시스템 경계와 책임

- 외부 애플리케이션은 HTTP로 요청하며, Mini Redis가 보관 상태를 소유한다. 같은 저장소를 사용하는 요청은 공유 상태를 참조하며 요청마다 새 저장소를 만들지 않는다. 구체적인 프로세스·스레드 운영 방식은 아직 미정이다.
- HTTP 처리 책임: 경로·메서드 판별, JSON 본문·쿼리 해석, 저장소 호출, HTTP 응답 생성. 해시 계산과 보관 위치 선택은 담당하지 않는다.
- 저장소 책임: 키·`value`의 확정 입력 제한을 상태 변경 전에 검증하고, 저장·덮어쓰기·조회·삭제 및 존재 여부와 결과 제공을 담당한다. HTTP 경로·상태 코드·JSON 전송은 담당하지 않는다.
- 저장 요청 흐름: HTTP 입력 해석 → 저장소 호출 → 저장소의 입력 제한 검증 → 유효하면 저장·덮어쓰기, 거절하면 기존 상태 보존 → HTTP 결과 응답.
- 조회·삭제도 같은 책임 경계를 따른다. 존재 여부와 삭제 직전 `value` 확보는 저장소가 담당하며, HTTP 처리 부분이 사전 조회하여 삭제 결과를 추측하지 않는다.
- 단위 테스트는 HTTP 없이 저장소의 행동 계약을 확인하고, 외부 기능 테스트는 실제 HTTP 요청부터 응답까지 확인한다.
- 저장소의 호출 대상은 `storage.py`의 `MiniRedis`다. 내부 보관 구조는 Python `dict`이며 해시 계산·충돌 처리·리사이즈는 Python에 맡긴다. 함수와 입력 거절 전달 방식은 아래 계약을 따르며, 동시 호출 허용 여부와 책임은 현재 결정하지 않는다. 동시 카운터의 안전성과 재시작 후 보존까지 보장하지 않는다.

## 확정된 HTTP 처리·저장소 간 함수 계약

### 호출과 상황별 반환

- 아래는 Python 함수 경계다. 키는 문자열, `value`는 문자열 또는 실제 `None`이다. `None`은 HTTP JSON의 `null`에 대응한다.
- 정상 결과와 확정된 입력 제한 위반은 모두 반환값으로 전달한다. 입력 거절 전용 예외는 도입하지 않는다.
- `from storage import MiniRedis`로 가져오고 `MiniRedis()`로 독립된 빈 저장소를 생성한다. 생성자는 인스턴스별로 `self._data = {}`를 만든다. 저장소의 호출 이름은 `set`·`get`·`delete`이며, Python 예약어 `del`을 함수 이름으로 사용하지 않는다.

| 호출 | 상황 | Python 반환값 | 상태 조건 |
| --- | --- | --- | --- |
| `set(key, value)` | 저장·덮어쓰기 성공 | `{"ok": True}` | 지정한 키에 입력한 `value` 보관, 다른 키 보존 |
| `get(key)` | 키 있음 | `{"found": True, "value": 보관 내용}` | 보관 상태 변경 없음 |
| `get(key)` | 키 없음 | `{"found": False}` | 키 생성 없음 |
| `delete(key)` | 키 있음 | `{"found": True, "value": 삭제 직전 내용}` | 해당 키만 제거 |
| `delete(key)` | 키 없음·반복 삭제 | `{"found": False}` | 보관 상태 변경 없음 |
| 해당 저장소 호출 | 확정된 입력 제한 위반 | `{"error": "INVALID_INPUT"}` | 기존 `value`와 다른 키 보존, 새 항목 추가 없음 |

- 표의 ‘보관 내용’·‘삭제 직전 내용’은 설명이며 실제 반환 문자열이 아니다. 실제 `value`를 타입과 내용 그대로 넣는다. `None`도 `found=True`와 함께 반환하며 `found=False`일 때는 `value`를 생략한다.
- 오류 반환에는 성공을 뜻하는 `ok`·`found`를 섞지 않는다. 정상 반환에는 `error`를 넣지 않는다.
- 입력 제한은 앞의 확정 계약을 따른다. HTTP 입력 형식 검사의 상세 계약은 [HTTP 담당 범위](01-http-scope.md)를 따른다.

### HTTP 연결

- `PUT /kv` → `set(key, value)`, `GET /kv` → `get(key)`, `DELETE /kv` → `delete(key)`.
- `{"error": "INVALID_INPUT"}` 반환은 HTTP 400으로, 나머지 위 정상 반환은 HTTP 200으로 전달한다.
- HTTP 응답 본문은 위 결과를 JSON으로 표현한다. Python의 `True`·`False`·`None`은 JSON에서 `true`·`false`·`null`이 된다.
- 예상하지 못한 내부 오류는 위 입력 거절 반환과 구분한다. 모든 예외를 일괄적으로 `INVALID_INPUT`으로 바꾸지 않는다. 예상하지 못한 오류의 구체적 처리 정책은 미정이다.
- 동시 호출 조건은 이번 경계 합의에서 결정하지 않는다. 순차 테스트 조건을 동시 호출 안전성 보장으로 해석하지 않는다.

### 저장소 함수 처리 흐름

- `MiniRedis()`: 인스턴스별 빈 `self._data` 딕셔너리를 생성한다.
- `set(key, value)`: 키·value 타입 확인 → UTF-8 바이트 수 확인 → 위반 시 상태 유지 및 `INVALID_INPUT` 반환 → 정상이면 `self._data[key] = value` → 성공 반환.
- `get(key)`: 키 타입·UTF-8 바이트 수 확인 → 위반 시 `INVALID_INPUT` 반환 → 키가 없으면 `found=False` → 있으면 `found=True`와 보관한 value 반환. 저장 상태는 변경하지 않는다.
- `delete(key)`: 키 타입·UTF-8 바이트 수 확인 → 위반 시 상태 유지 및 `INVALID_INPUT` 반환 → 키가 없으면 `found=False` → 있으면 `pop`으로 삭제 직전 value를 확보하며 제거 → `found=True`와 해당 value 반환.
- 테스트 전용 `snapshot(store)`: `tests/storage_helpers.py`에서 저장소 내부 딕셔너리의 독립된 전체 사본을 반환한다. value가 문자열 또는 None이므로 사본의 항목 변경이 원본에 영향을 주지 않는다. `MiniRedis`의 메서드가 아니다.
- 키 존재 여부는 value가 None인지와 별개로 `key in self._data`로 확인한다. 입력 인코딩 실패만 `UnicodeEncodeError`로 구분하며 예상하지 못한 모든 오류를 입력 오류로 바꾸지 않는다.

### 기존 테스트의 내부 호출 연결

- 모든 케이스의 저장 행동은 `set`, 조회 행동은 `get`, 삭제 행동은 `delete`로 대응한다. 아래 외부 테스트의 사전 상태·입력·순서·검증 시점·유지 조건은 그대로 유지한다. 실제 `null` 입력은 Python 호출에서 `None`으로 전달하며 문자열 `"null"`로 바꾸지 않는다.
- S1-01~S1-06, S1-06-01, S1-08, S1-08-01의 정상 응답 내용은 위 Python 반환으로 대조한다.
- S1-07의 성공 행은 `set` 반환 `{"ok": True}`, 거절 행은 `{"error": "INVALID_INPUT"}`을 확인하고, 이어지는 `get`으로 기존 상태 보존을 검증한다.
- 단위 테스트 준비·전체 상태 관찰은 아래의 확정된 단위 테스트 실행 계약을 따른다.

### 확정된 단위 테스트 실행 계약

- 기본 테스트 파일은 `tests/test_storage.py`, 추가 입력 거절 테스트는 `tests/test_storage_invalid_input.py`, 도구는 `pytest`다. 각 테스트 및 매개변수 조합마다 새 `MiniRedis()`를 생성하며 처음 상태는 비어 있다.
- 사전 상태는 `set`으로 준비하고 각 저장 성공 반환을 확인한다. 내부 자료구조에 항목을 직접 주입하지 않는다.
- `tests/storage_helpers.py`의 `snapshot(store)`는 현재 전체 `키 → value`를 담은 독립된 Python 딕셔너리 사본을 반환한다. 문자열과 `None`을 그대로 보존하며 저장소를 변경하지 않는다. 항목 수만 반환하는 방식은 사용하지 않는다.
- `snapshot(store)`는 테스트 전용 함수다. `store._data.copy()`로 사본을 만들며 `MiniRedis`에는 스냅샷 메서드를 두지 않는다. 테스트에서 각 동작 전후에 필요에 따라 호출하고 실행 코드는 이 모듈을 가져오거나 호출하지 않는다. HTTP에 노출하지 않는다.
- 각 호출 반환 직후 필드 구성·타입·내용을 확인하고 전체 스냅샷을 기대 상태와 비교한다. 기존 케이스의 호출 순서는 유지한다.
- S1-07의 거절 행은 요청 전후 스냅샷이 같아야 한다. 성공 행은 지정한 키만 추가·변경된 전체 상태여야 한다. 문서의 후속 조회도 생략하지 않는다.
- 스냅샷 독립성은 별도 테스트로 검증한다. 반환 사본의 항목을 수정·추가·삭제해도 실제 저장소가 변경되지 않아야 한다.
- 전체 실행 명령은 프로젝트 루트에서 `.venv/bin/python -m pytest tests/`다. 기존 21개만 확인하려면 `.venv/bin/python -m pytest tests/test_storage.py`로 실행한다. 의존성은 `requirements-dev.txt`에 기록한다.

## 행동 테스트 케이스

### 공통 실행·판정 규칙

- 아래 케이스의 외부 호출 대상은 위의 `PUT /kv`, `GET /kv`, `DELETE /kv`이며, 단위 테스트는 `MiniRedis`의 `set`·`get`·`delete`에 연결한다. 준비·관찰 방법은 위 단위 테스트 실행 계약을 따른다.
- 각 케이스와 표의 각 행은 독립 실행한다. 다른 테스트의 실행 결과를 사전 상태로 사용하지 않는다.
- 각 요청은 앞 요청 완료 후 수행한다. 동시 요청은 이번 범위가 아니다.
- 조회·삭제는 `found`와 `value`의 존재 여부·타입·내용을 검증한다. `{"found": false}`에서는 `value` 필드가 없어야 한다.
- 아래 저장 ‘성공’은 HTTP 200과 `{"ok":true}`, 확정 입력 제한에 대한 ‘거절’은 HTTP 400과 `{"error":"INVALID_INPUT"}`을 뜻한다. 조회·삭제 정상 응답은 HTTP 200이다. 이후 조회만 맞는다고 요청 결과 확인을 생략하지 않는다.
- 각 저장 케이스의 키·`value`는 PUT 본문에 넣고, 각 조회·삭제 케이스의 키는 쿼리 매개변수에 넣는다. S1-07-01의 키 `null`은 PUT 본문의 `{"key":null,"value":"new"}`로 전달한다.
- 문자열 내용은 따옴표로 표시한다. 실제 `null`, 문자열 `"null"`, 빈 문자열 `""`, 키 없음을 구분한다.
- 크기 입력의 ‘반복’은 해당 문자를 정확히 그 횟수만큼 이어 붙인 문자열이다. 따옴표나 설명 문구는 포함하지 않는다.
- 기존 S1 식별자와 입력·기대 동작을 유지하며, 세분화가 필요한 항목은 하위 식별자로 구분한다.

### S1-01. 보관한 값 조회

- 사전 상태: `sample:one` 키가 없다.
- 입력·행동: `sample:one`에 문자열 `value` `"hello"`를 저장하고, 성공 후 같은 키를 두 번 연속 조회한다.
- 검증 시점: 저장 응답 및 각 조회 응답 수신 시.
- 기대 결과: 저장은 성공하고 두 조회 모두 `{"found": true, "value": "hello"}`다.
- 유지 조건: 조회가 보관된 `value`를 변경하지 않는다.
- 실행 범위: 외부 사용 경로와 대응하는 저장소의 `set`·`get` 행동. 단위 테스트는 새 `MiniRedis()`에서 실행한다. HTTP 기능 테스트의 구현은 별도다.

### S1-02. 사용자가 값을 폐기

- 사전 상태: `sample:one`의 `value`는 문자열 `"hello"`다.
- 입력·행동: 해당 키를 삭제하고 같은 키를 두 번 연속 조회한다.
- 검증 시점: 삭제 응답 및 각 조회 응답 수신 시.
- 기대 결과: 삭제는 `{"found": true, "value": "hello"}`, 두 조회 모두 `{"found": false}`다.
- 유지 조건: 조회가 키를 다시 생성하거나 이전 `value`를 되살리지 않는다.

### S1-03. 다른 키에 영향을 주지 않음

- 사전 상태: `sample:one`의 `value`는 `"hello"`, `sample:two`의 `value`는 `"world"`다.
- 입력·행동: `sample:one`을 삭제한 뒤 `sample:two`를 조회한다.
- 검증 시점: 삭제 응답 및 다른 키의 조회 응답 수신 시.
- 기대 결과: 삭제는 `{"found": true, "value": "hello"}`, 조회는 `{"found": true, "value": "world"}`다.
- 유지 조건: 한 키의 삭제가 다른 키의 `value`를 변경하지 않는다.

### S1-04. 같은 키 덮어쓰기

- 사전 상태: `sample:one`의 `value`는 `"hello"`, `sample:two`의 `value`는 `"world"`다.
- 입력·행동: `sample:one`에 `"updated"`를 저장한 뒤 두 키를 조회한다. 같은 순서로 두 키를 한 번씩 더 조회한다.
- 검증 시점: 저장 응답 및 각 조회 응답 수신 시.
- 기대 결과: 저장은 성공한다. 두 차례 모두 `sample:one`은 `{"found": true, "value": "updated"}`, `sample:two`는 `{"found": true, "value": "world"}`다.
- 유지 조건: 다른 키의 `value`가 변경되지 않으며 이전 `value` `"hello"`가 되살아나지 않는다.

### S1-05. 없는 키 조회·삭제와 반복 삭제

- 사전 상태: `sample:missing`은 한 번도 저장하지 않았으며, `sample:one`의 `value`는 `"hello"`다.
- 입력·행동과 각 단계의 기대 결과:
  1. `sample:missing` 조회 → `{"found": false}`.
  2. `sample:missing` 삭제 → `{"found": false}`. 오류가 아니다.
  3. `sample:one` 첫 삭제 → `{"found": true, "value": "hello"}`.
  4. `sample:one` 두 번째 삭제 → `{"found": false}`. 오류가 아니다.
  5. `sample:one` 조회 → `{"found": false}`.
- 검증 시점: 각 응답 수신 시, 다음 요청 전에 해당 결과를 확인한다.
- 유지 조건: 조회·삭제가 없는 키를 생성하지 않는다. 마지막에 `sample:missing`을 다시 조회해도 `{"found": false}`다.

### S1-06. 빈 문자열 value와 글자 그대로 보존

- 사전 상태: `sample:empty`, `sample:text`, `sample:missing`이 없다.
- 입력·행동과 각 단계의 기대 결과:
  1. `sample:empty`에 `""` 저장 → 성공.
  2. `sample:text`에 글자 내용 `{"a":1}` 저장 → 성공.
  3. `sample:empty` 조회 → `{"found": true, "value": ""}`.
  4. `sample:text` 조회 → `{"found": true, "value": "{\"a\":1}"}`. `value`는 객체가 아닌 문자열이다.
  5. `sample:missing` 조회 → `{"found": false}`.
  6. `sample:empty` 첫 삭제 → `{"found": true, "value": ""}`.
  7. `sample:empty` 두 번째 삭제 → `{"found": false}`.
- 검증 시점: 각 응답 수신 시.
- 유지 조건: JSON을 해석하여 타입을 바꾸지 않고, 빈 문자열과 키 없음을 구분한다. 마지막에 `sample:text`를 다시 조회해도 4번과 같다.

#### S1-06-01. 숫자 표현과 null 글자 보존

- 사전 상태: `sample:number`, `sample:word`가 없다.
- 입력·행동: `sample:number`에 문자열 `"10"`, `sample:word`에 문자열 `"null"`을 저장하고 두 키를 조회한다.
- 검증 시점: 각 저장 응답 및 조회 응답 수신 시.
- 기대 결과: 두 저장은 성공한다. 조회는 각각 `{"found": true, "value": "10"}`, `{"found": true, "value": "null"}`이다.
- 유지 조건: 숫자 타입 `10`이나 실제 `null`로 자동 변환하지 않는다.

### S1-07. 키·value 크기 경계와 입력 거절 시 상태 보존

- 사전 상태: 각 행을 독립 실행한다. `sample:one`의 `value`는 `"hello"`, `sample:two`의 `value`는 `"world"`다. 크기 경계에 사용하는 다른 키는 없다.
- 입력·행동: 각 행의 키·`value`로 저장을 요청한다.

| 하위 식별자 | 저장할 키 | 저장할 value | 정확한 크기 | 저장 기대 결과 |
| --- | --- | --- | --- | --- |
| S1-07-01 | 실제 `null` | `"new"` | 키 타입 거절 | 거절 |
| S1-07-02 | `""` | `"new"` | 키 0바이트 | 거절 |
| S1-07-03 | `"a"` | `"hello"` | 키 1바이트 | 성공 |
| S1-07-04 | `a` 256회 | `"hello"` | 키 256바이트 | 성공 |
| S1-07-05 | `a` 257회 | `"hello"` | 키 257바이트 | 거절 |
| S1-07-06 | `한` 85회 뒤에 `a` 1회 | `"hello"` | 키 256바이트 | 성공 |
| S1-07-07 | `한` 86회 | `"hello"` | 키 258바이트 | 거절 |
| S1-07-08 | `sample:one` | `a` 65,536회 | value 65,536바이트 | 성공 |
| S1-07-09 | `sample:one` | `a` 65,537회 | value 65,537바이트 | 거절 |
| S1-07-10 | `sample:one` | `한` 21,845회 뒤에 `a` 1회 | value 65,536바이트 | 성공 |
| S1-07-11 | `sample:one` | `한` 21,845회 뒤에 `a` 2회 | value 65,537바이트 | 거절 |

- 검증 시점: 각 저장 응답 수신 시 성공·거절을 확인한 뒤, 아래의 유효한 키를 조회한다. 기존 S1-07의 후속 조회 대상은 유지한다. 길이 초과 키에 대한 조회·삭제 거절은 S1-09에서 별도로 검증한다.
- 후속 조회 기대 결과:
  - `sample:two`는 모든 행에서 `{"found": true, "value": "world"}`다.
  - S1-07-03·04·06의 새 키 조회는 `{"found": true, "value": "hello"}`다.
  - S1-07-08·10의 `sample:one` 조회는 `found`가 `true`이고 `value`는 표에서 입력한 문자열과 타입·내용이 정확히 같다.
  - 나머지 모든 행의 `sample:one` 조회는 `{"found": true, "value": "hello"}`다. 새 키에 저장한 행에서도 기존 키 보존을 확인한다.
- 유지 조건: 거절된 요청은 저장 항목을 추가하지 않으며 기존 `value`와 다른 키를 변경하지 않는다. 허용된 저장도 다른 키에 영향을 주지 않는다.
- 관찰 방법: 거절 전후 테스트 도구 `snapshot(store)`의 전체 키·`value`가 같은지 비교하여 무효한 항목 추가와 기존 항목 변경·삭제를 확인한다. 외부 조회만으로 이 유지 조건을 완전히 입증했다고 간주하지 않는다. 실행 결과는 아래 검증 상태에서 구분한다.
- 요청과 응답: 저장은 `PUT /kv`, 성공은 HTTP 200과 `{"ok":true}`, 거절은 HTTP 400과 `{"error":"INVALID_INPUT"}`이다. 빈 문자열 `value`의 0바이트 허용 경계는 S1-06에서 검증한다.

### S1-08. 실제 null인 value 보관·조회·삭제

- 사전 상태: `sample:null`과 `sample:missing`이 없다.
- 입력·행동과 각 단계의 기대 결과:
  1. `sample:null`에 실제 `null` 저장 → 성공.
  2. `sample:null` 조회 → `{"found": true, "value": null}`.
  3. `sample:missing` 조회 → `{"found": false}`.
  4. `sample:null` 첫 삭제 → `{"found": true, "value": null}`.
  5. `sample:null` 두 번째 삭제 → `{"found": false}`.
  6. `sample:null` 조회 → `{"found": false}`.
- 검증 시점: 각 응답 수신 시.
- 유지 조건: `null` 저장 때문에 키가 삭제되지 않는다. 실제 `null`, 문자열 `"null"`, 빈 문자열 `""`, 키 없음은 서로 구분된다.
- 응답 표현: 존재하는 실제 `null`인 `value`의 조회와 첫 삭제는 `{"found": true, "value": null}`, 없는 키 조회와 반복 삭제는 `{"found": false}`다.

#### S1-08-01. 문자열과 실제 null 사이의 덮어쓰기

- 사전 상태: `sample:one`의 `value`는 `"hello"`, `sample:two`의 `value`는 `"world"`다.
- 입력·행동: `sample:one`에 실제 `null`을 저장하고 조회한다. 이어서 같은 키에 `"updated"`를 저장하고 조회한다. 마지막에 `sample:two`를 조회한다.
- 검증 시점: 각 저장 응답 및 조회 응답 수신 시.
- 기대 결과: 두 저장 모두 성공한다. 조회는 순서대로 `{"found": true, "value": null}`, `{"found": true, "value": "updated"}`, `{"found": true, "value": "world"}`다.
- 유지 조건: `null`로 덮어써도 키는 존재하며 다른 키는 변경되지 않는다.

### S1-09. 모든 저장소 진입점의 잘못된 키 거절

- 사전 상태: 각 하위 입력·호출 조합은 독립 실행한다. `sample:one`에 `"hello"`, `sample:two`에 `"world"`를 저장한다.
- 호출 대상: 각 표의 키로 `set(key, "new")`, `get(key)`, `delete(key)`를 각각 실행한다. 케이스 ID는 표의 ID에 `-set`·`-get`·`-delete`를 붙인다.

| 하위 식별자 | 정확한 Python key 입력 | 거절 이유 |
| --- | --- | --- |
| S1-09-01 | `None` | 문자열 아님 |
| S1-09-02 | `""` | 0바이트 |
| S1-09-03 | `1` | 문자열 아님 |
| S1-09-04 | `True` | 문자열 아님 |
| S1-09-05 | `[]` | 문자열 아님 |
| S1-09-06 | `{}` | 문자열 아님 |
| S1-09-07 | `b"key"` | 문자열 아님 |
| S1-09-08 | `"a" * 257` | 256바이트 초과 |
| S1-09-09 | `"\ud800"` | UTF-8로 인코딩할 수 없는 단독 서로게이트 |

- 입력·행동: 사전 상태 준비 후 `snapshot(store)`를 보관하고 지정한 함수를 한 번 호출한다.
- 검증 시점: 호출 반환 직후, 다음 저장소 동작 전에 확인한다.
- 기대 결과: `{"error": "INVALID_INPUT"}`이며 다른 성공 필드가 없다.
- 유지 조건: 전후 전체 스냅샷은 사전 상태와 같고, 이후 두 정상 키를 조회해도 각각 `"hello"`·`"world"`다.

### S1-10. 잘못된 value 타입·UTF-8 문자열 거절

- 사전 상태: 각 행은 독립 실행한다. `sample:one`에 `"hello"`, `sample:two`에 `"world"`를 저장한다.

| 하위 식별자 | 정확한 Python value 입력 | 거절 이유 |
| --- | --- | --- |
| S1-10-01 | `1` | 문자열·None 아님 |
| S1-10-02 | `True` | 문자열·None 아님 |
| S1-10-03 | `[]` | 문자열·None 아님 |
| S1-10-04 | `{}` | 문자열·None 아님 |
| S1-10-05 | `b"hello"` | 문자열·None 아님 |
| S1-10-06 | `"\ud800"` | UTF-8로 인코딩할 수 없는 단독 서로게이트 |

- 입력·행동: `snapshot(store)`를 보관하고 `set("sample:one", value)`를 한 번 호출한다.
- 검증 시점: 저장 반환 직후, 다음 저장소 동작 전에 확인한다.
- 기대 결과: `{"error": "INVALID_INPUT"}`이며 다른 성공 필드가 없다.
- 유지 조건: 전후 전체 스냅샷은 사전 상태와 같고, 이후 두 키를 조회해도 각각 `"hello"`·`"world"`다.

### 검증 상태와 설계 단계 인계

- 문서화 범위: 저장·반복 조회, 삭제 반환·삭제 후 없음, 다른 키 보존, 덮어쓰기, 없는 키·반복 삭제, 빈 문자열·JSON·숫자 표현·null 글자 보존, 크기 경계, 실제 `null` 보관·삭제·덮어쓰기, 모든 진입점의 무효 키 거절 및 무효 value 거절.
- `storage.py`에 구현했으며 `.venv/bin/python -m pytest tests/ -q` 실행 결과 54개가 통과했다. 기존 S1-01~08의 20개 케이스와 스냅샷 독립성 1개, 추가 S1-09·10의 33개 케이스다. 상세 명세 대조·구현 전후 실행 결과는 [작업 기록](storage-test-worklog.md)에 남긴다.
- 이 결과는 저장소 단위 테스트에 한정한다. HTTP의 분리 테스트·실행 기록은 [HTTP 담당 범위](01-http-scope.md)에 둔다. 실제 외부 HTTP 기능·동시성·TTL·성능·장애 복구는 아직 검증하지 않았다.
- 구현 언어는 Python이며 테스트 도구·클래스 배치·준비·전체 상태 관찰 방법과 내부 `dict` 사용이 합의되었다. Python·Flask 지원 버전은 미정이며 HTTP 상세는 [HTTP 담당 범위](01-http-scope.md)를 따른다. 테스트 입력과 기대 결과를 구현 편의에 맞춰 변경하지 않는다.
- 해시 충돌·리사이즈는 Python `dict`에 맡기며 별도의 해시 테이블을 직접 구현하지 않는다. 아래 미정 동작에는 기대 결과를 지어내지 않는다.

## 남은 미정 사항

- HTTP 입력 형식의 확정 사항·미정 정책은 [HTTP 담당 범위](01-http-scope.md)를 따른다. Python 함수 인자 누락은 별도이며, 잘못된 키·value 타입과 UTF-8로 인코딩할 수 없는 문자열의 저장소 거절은 확정되었다.
- 입력 거절 외 요청 실패·응답 유실 시 보장 범위.
- 키의 공백·제어문자, 대소문자 비교와 유니코드 정규화 정책 등 아직 합의하지 않은 세부 동작.
- 총 저장량 한도와 자원 부족 처리. 항목별 크기 상한과 별개다.
- HTTP 기능 테스트의 구현 배치. 미정 동작에 의존하는 테스트는 임의로 완성하지 않는다.
