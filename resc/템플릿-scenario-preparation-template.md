# 테스트 시나리오 초안 검토 메모

이미 작성된 시나리오를 처음부터 다시 만들지 않는다. 대상 문서를 읽고 아래 세 항목 중 필요한 것만 짧게 적어 온다. 의견이 없으면 작성하지 않아도 된다.

첫 검토 대상: [값 보관·조회·폐기](scenario_01_storage/01-storage-scenario.md).

## 검토 메모

아래는 예시임. 목차만 가져와서 쓰기

### 빠진 상황

- **같은 키 덮어쓰기** — `hello` 저장 후 `world` 저장 → 조회. S1-01은 최초 저장과 조회만 본다.
- **한 번도 없던 키 조회** — S1-02는 삭제 후 없음만 본다. 최초부터 없는 키의 응답이 같은지 확인이 필요하다.
- **없는 키 삭제 / 반복 삭제** — 삭제 응답과 멱등성.
- **삭제 후 같은 키 재저장** — 이전 값이 되살아나지 않는지.
- **저장 응답 단독 검증** — S1-01은 "저장 성공 응답"을 전제로만 쓰고, 성공·실패 응답 자체는 확인하지 않는다.
- **해시 충돌** — 서로 다른 키가 같은 버킷에 들어가도 둘 다 유지되는지. 두 키만으로는 부족하다. (S1-04 제안 참고)
- **리사이즈** — 키를 늘려 테이블이 커질 때 기존 값이 유지되는지. (S1-04 제안 참고)
- **값 경계** — 빈 값, JSON·개행·유니코드·공백 포함 값, 최대 크기와 상한+1.
- **키 경계** — 빈 키, NUL·제어문자, 최대 길이, 대소문자·정규화 차이.
- **저장 실패 후 이전 값 유지** — 크기 초과 같은 실패 뒤 조회.
- **동시 저장·삭제** — 문서 2는 카운터만 다룬다. 같은 키의 저장/삭제 경합은 어디서 다룰지 비어 있다.
- **사전 상태 준비 방법** — 픽스처로 만들지, 저장 경로로 만들지. 후자면 조회 테스트가 저장 테스트에 의존한다.

### 다른 의견

- **S1-01 분리** — 라운드트립은 유지하고, 저장 응답·조회·덮어쓰기를 별도 시나리오로 나누자. 실패 원인을 분리할 수 있다.
- **S1-02의 삭제 확인** — 지금은 삭제 후 조회로만 확인한다. 삭제 응답(예: 1/0)을 따로 확인해야 삭제와 조회 중 어느 쪽 문제인지 분리된다.
- **"없음" 표현** — 빈 문자열로 표현하면 빈 값과 구분되지 않는다. 별도 상태나 표현이 필요하다.
- **S1-03의 키 수** — 두 키만으로는 해시 충돌을 잡지 못한다. 키를 늘리거나 충돌 가능 쌍을 써야 한다.
- **용어** — 제목은 "폐기", 본문은 "삭제", 범위는 "무효화"로 섞여 있다. 같은 동작이면 하나로 정리하자.
- **값의 경계** — 값은 불투명한 문자열/바이트로 두고, 숫자 해석은 문서 2로 넘기자.
- **"사용자" 정의** — 문서에 정의가 없다. 외부 클라이언트(애플리케이션 또는 그 개발자)로 명시하자. 운영자와 자동 만료는 아니다.
- **의존성 표기** — 조회 시나리오의 사전 상태를 저장 경로로 만들면 저장 시나리오에 의존한다. 의존성을 명시하자.
- **응답 계약** — S1-01의 "저장 성공 응답"은 아직 정의되지 않은 응답을 전제로 한다. 응답 계약이 먼저 필요하다.

### 미정 사항에 대한 생각

**키**

- 비어 있지 않은 UTF-8 문자열(또는 바이트열)로 보고, 빈 키는 거부하는 쪽이 좋다.
- 최대 길이를 정하고 초과는 명확한 오류로 거부한다. 경계값과 상한+1을 테스트한다.
- 유니코드 정규화는 하지 않고 입력 바이트를 그대로 보존하는 쪽이 예측 가능하다.
- NUL·제어문자·공백·개행은 프로토콜이 바이너리 안전하면 허용, 아니면 거부. 어느 쪽이든 명시한다.
- 대소문자는 구분한다.
- 문자열 `"null"`은 유효한 키, 실제 null/빈 입력은 키 없음으로 구분한다.

**값**

- 불투명한 바이트열/문자열로 저장하고, JSON 해석은 하지 않는다.
- 빈 값은 허용하되 "없음"과 구분한다.
- 최대 크기를 정하고, 초과는 명확한 오류로 거부하며 이전 값을 유지한다.

**동작**

- 같은 키 재저장은 새 값으로 덮어쓰기.
- 없는 키 조회는 오류가 아니라 "없음"으로 명시.
- 없는 키 삭제는 오류가 아니라 "삭제된 것 없음(0)"으로, 반복 삭제도 같은 결과(멱등).
- 저장·삭제 실패 시 이전 값 유지. 실패와 없음은 다른 응답.
- 숫자/카운터 동작은 문서 2로 분리.

**검증**

- 해시 테이블 자체 검증(충돌·리사이즈·해시 분포)은 행동 테스트와 별도 단위 테스트로 다룬다.
- 사전 상태 준비를 픽스처로 할지 저장 경로로 할지 정해야 한다. 저장 경로면 외부 경로 테스트지만 의존성이 생기고, 픽스처면 독립적이지만 외부 경로가 아니다.
- **단편화** — 문서 1의 테스트가 아니라 설계·품질 항목으로 넘긴다. 삭제·리사이즈 정책(노드 재사용, tombstone 재해시, 축소 정책)과 메모리 허용 범위를 설계에서 정하고, 필요하면 반복 삽입·삭제 후 메모리 안정성 검사를 별도로 둔다.

## 추가 제안: S1-04. 대량·무작위 삽입·삭제 후 정합성

S1-03을 확장하는 대신 별도 시나리오로 두자는 제안이다. 아직 `01-storage-scenario.md`에는 반영하지 않았다.

- 사전 상태: 저장소가 비어 있다.
- 입력·행동: 고정 시드로 삽입·조회·삭제를 섞은 연산을 합의한 횟수만큼 수행한다. 삽입은 새 키와 기존 키 덮어쓰기를, 삭제는 있는 키와 없는 키를 모두 포함한다. 키 수는 설계 후 리사이즈가 발생하는 규모로 정한다.
- 검증 시점: 전체 연산 완료 후, 필요하면 합의한 주기마다.
- 기대 결과: 같은 연산을 적용한 기준 모델(일반 딕셔너리)과 저장소의 키·값이 전부 일치한다. 삭제한 키는 없고, 덮어쓴 키는 마지막 값이며, 다른 키의 값은 바뀌지 않는다.
- 유지 조건: 같은 시드와 연산 로그로 다시 실행하면 같은 결과가 나온다. 실패하면 연산 로그를 재생해 재현할 수 있다.
- 실행 범위: 외부 사용 경로. 설계 후 대응하는 단위 테스트 호출 대상을 명시한다.
- 미정: 연산 수, 키 수, 시드, 키·값 분포, 검증 주기(매 연산/주기/최종), 실패 시 중단·계속 여부.

모임에서는 기존 초안을 함께 확인하고 위 의견과 미정 사항을 논의한다. 합의한 내용만 대상 문서에 반영하며, 개인 메모를 확정 계약으로 취급하지 않는다. 설계와 코드는 아직 작성하지 않는다.
