# 날씨 데모의 키별 갱신 락 사용

## 1. 상태와 범위

2026-11-18 사용자 승인으로 날씨 데모가 기존 Mini Redis 락 API를 사용하도록 한다. 이 문서는 데모 소비자 계층의 사용 계약과 동결한 테스트 케이스를 기록한다.

- 유지: 기존 2프로세스 구성(Mini Redis `app.py`, 날씨 데모 `demo/weather_app.py`), 조회 버튼 두 번의 순차 데모, 기존 저장소·HTTP 락 API 계약([05 락 계약](05-lock-contract.md)), 04 응답 캐시의 순차 요청 계약([04 시나리오](../scenario_04_response_cache/04-response-cache-scenario.md)).
- 이번 범위: `demo/weather_app.py`, `demo/README.md`, `tests/scenario_04_response_cache/test_weather_demo.py`, `tests/scenario_04_response_cache/test_weather_demo_lock.py`, 이 문서.
- 제외: UI 변경, 루트 `readme.md`, 다중 워커·다중 프로세스 배포, 소유자 프로세스 크래시 복구, 락 TTL heartbeat 연장, Fencing Token.
- 04의 "순차 요청만" 계약과 05의 "저장소 대기 큐 없음" 계약을 바꾸지 않는다. 이 문서의 대기는 데모 앱이 HTTP로 캐시와 락을 다시 확인하는 클라이언트 측 동작이며, 저장소에 대기 큐나 Pub-Sub을 추가하지 않는다.
- 두 요청의 겹침은 날씨 데모 서버의 동기 엔드포인트가 스레드풀에서 실행되어 발생할 수 있다. Mini Redis의 락 연산은 단일 이벤트 루프에서 처리된다.
- 2026-11-18 실행 모니터가 별도 승인으로 추가되었다. 이 문서의 락 사용·터미널 로그·동결 테스트 계약은 그대로 유지하며, 모니터의 이벤트 전달과 화면 계약은 [실행 모니터 계약](../scenario_04_response_cache/04-weather-monitor-contract.md)을 따른다.

## 2. 확정 상수와 동작

### 2.1 상수

| 상수 | 값 | 의미 |
| :--- | ---: | :--- |
| `LOCK_TTL_MS` | `10_000` | 데모가 요청한 락의 TTL. 자동 연장 없음 |
| `LOCK_POLL_INTERVAL_S` | `0.1` | 경합 대기 중 캐시 확인·락 재시도 간격 |
| `LOCK_WAIT_LIMIT_S` | `10.0` | 경합 대기 최대 시간. 초과 시 HTTP 502 |

### 2.2 정상 흐름

1. 캐시를 조회한다. 있으면 락을 사용하지 않고 기존처럼 재사용한다.
2. 캐시가 없으면 요청마다 고유 토큰으로 `POST /kv/lock/acquire`를 호출한다.
3. 락을 얻으면 캐시를 한 번 더 확인한다. 그 사이 다른 요청이 저장했으면 원본을 호출하지 않고 재사용한다.
4. 캐시가 여전히 없으면 Open-Meteo를 1회 호출하고, TTL 60,000ms로 저장한 뒤 소유 토큰으로 락을 해제한다.
5. 원본 호출·저장이 실패해도 소유 토큰으로 락을 해제한 뒤 HTTP 502를 반환한다.

### 2.3 경합·실패·만료

- **경합(409 `LOCK_BUSY`)**: 100ms 간격으로 캐시를 확인하고 락 획득을 다시 시도한다. 마감 전에 캐시가 채워지면 다음 확인에서 저장된 응답으로 200을 반환한다. 락이 풀리면 획득을 재시도해 원본 호출을 이어받을 수 있다.
- **대기 한도**: 첫 경합 시점부터 10초가 지나면 HTTP 502를 반환한다. 대기 중 캐시가 채워지면 남은 시간을 기다리지 않고 반환한다. 마감 시각 이후에 도착한 캐시·락 응답은 늦은 응답으로 보고 성공으로 처리하지 않는다. 늦게 락을 획득한 경우 소유 토큰으로 락을 해제한 뒤 502를 반환한다.
- **소유 요청 실패**: 소유 요청은 락을 해제하고 502를 반환한다. 대기 요청은 다음 확인에서 락 획득을 재시도해 원본 호출을 이어받을 수 있다.
- **락 만료**: 락 TTL은 10초이며 자동 연장하지 않는다. 만료된 락은 다음 `acquire`에서 lazy 만료된 뒤 새 요청이 획득할 수 있다.
- **락 해제 실패**: 저장·응답이 이미 끝난 뒤 해제 응답이 실패하거나 `released=false`이면 성공 응답을 덮어쓰지 않고 터미널에만 기록한다. 락은 TTL 만료로 정리된다. 이 경로는 자동 테스트에서 검증하지 않는다.
- **정상 경로의 원본 호출 수**: 동시에 겹친 두 요청이 모두 성공하는 정상 경로에서는 1회다. 소유 요청이 실패한 뒤 대기 요청이 이어받는 실패 경로에서는 최대 2회다. 두 경우를 같은 성공 지표로 합치지 않는다.
- **두 탭에서 거의 동시에 조회**: 캐시 미스가 실제로 겹치면 위 경합 동작을 한다. 첫 요청이 먼저 저장을 마치면 두 번째 요청은 일반 캐시 히트다. 어느 쪽이 되는지는 도착 시점에 따라 달라진다.

### 2.4 터미널 로그

요청 ID(토큰 앞 8자)를 붙여 요청을 구분하고, 실제 발생한 이벤트만 기록한다.

- `[Mini Redis] 락 획득: ...`
- `[Mini Redis] 락 경합 대기: ...`
- `[Mini Redis] 락 획득(대기 후): ...`
- `[Mini Redis] 조회 성공: ... → 재사용 ...`
- `[Mini Redis] 조회 성공(대기 후): ... → 재사용 ...`
- `[Mini Redis] 락 해제: ...`
- `[Open-Meteo] 원본 호출: N회 ...`
- `[데모] 락 대기 한도 초과: ...`

## 4. 검증 경계

- 자동 테스트는 가짜 원본과 로컬 Mini Redis HTTP API를 사용한다. 실제 Open-Meteo 네트워크, 실제 브라우저 두 탭의 도착 시점, 다중 워커·다중 프로세스는 검증하지 않는다.
- WDL-08~10의 늦은 응답은 주입한 가짜 `monotonic`으로 마감 경계를 재현한 것이다. 실제 네트워크·저장소 지연 분포에서 마감 직후 응답이 어떻게 도착하는지는 검증하지 않는다.
- 락 TTL(10초)보다 소유 요청의 원본 처리 시간이 길어지면 다른 요청이 락을 획득해 원본을 중복 호출할 수 있다. 현재 `httpx` 타임아웃 5초와 저장 경로를 기준으로 TTL 10초를 두었으며, 이 경계는 자동 테스트로 보장하지 않는다.
- 05 계약의 Fencing Token 미지원 한계는 그대로다. 락 TTL이 지난 뒤 소유 요청이 늦게 `PUT /kv`를 보내면 최신 캐시를 덮어쓸 수 있다. 이번 데모 범위에서는 이 경합을 해결하지 않는다.

## 5. 변경 경위와 정정

- **로그 공백**: 동결 문서의 원래 문구는 `[Mini Redis] 조회 성공(대기 후)`였다. 최초 구현은 공백을 넣은 `조회 성공 (대기 후)`로 출력했고, 당시 테스트 기대와 이 문서를 구현에 맞춰 공백 있는 문구로 바꿨다. 독립 검토에서 이 변경이 지적되어 구현을 원래 동결 문구로 되돌리고 테스트·문서도 원래 문구로 복원했다. 영향은 로그 문자열뿐이며 응답 판정과 락 상태 전이는 바뀌지 않는다.
- **요청 ID**: 동결 문서는 요청 ID를 "토큰 앞 8자"로 적었다. 최초 구현은 별도 UUID 8자를 사용했고, 이전 수정에서 문서를 "요청마다 생성한 8자리 ID"로 바꿨다. 독립 검토 지적을 확인하여 구현을 토큰 앞 8자로 되돌리고 문서를 원래 문구로 복원했다. 이제 로그의 요청 ID로 해당 요청의 락 토큰 앞자리를 대조할 수 있으며, WDL-01이 이를 검증한다.
- **대기 한도 경계**: 최초 구현은 마감이 지난 뒤 락 획득이 성공하거나 늦은 캐시 히트가 도착하면 200을 반환했다. 수정 전 WDL-08~10이 200을 반환해 실패하는 것을 확인한 뒤 캐시·락 응답 복귀 시점에 마감을 다시 검사하도록 고쳤다. 늦게 획득한 락은 소유 토큰으로 해제한 뒤 502를 반환하고, 마감 이후 도착한 캐시 히트도 늦은 응답으로 처리해 502를 반환한다.
