# 테스트 시나리오 초안 검토 메모

이미 작성된 시나리오를 처음부터 다시 만들지 않는다. 대상 문서를 읽고 아래 세 항목 중 필요한 것만 짧게 적어 온다. 의견이 없으면 작성하지 않아도 된다.

첫 검토 대상: [값 보관·조회·폐기](01-storage-scenario.md).

- **빠진 상황:** 어떤 상황을 더 확인해야 하는가?
- • 같은 키에 다른 값을 다시 저장하는 경우.
• 없는 키를 조회하거나 삭제하는 경우.
• 같은 키를 두 번 삭제하는 경우.
• 빈 키·빈 값으로 저장하거나 필수 입력을 빠뜨리는 경우.
- **다른 의견:** 어느 항목의 기대 결과가 달라야 한다고 생각하는가? 이유는?
- **미정 사항에 대한 생각:** 문서 끝의 미정 사항 중 어떤 동작이 맞다고 생각하는가? 모르겠으면 질문만 적는다.
- • (이미 value 있는 )같은 키에 다른 값을 다시 저장함.
  - 1.  저장을 거부 - 삭제 전까지 조회만 가능 => 이거 생각해보면 부자연스러움. 업데이트 빈번한데, 삭제와 추가를 각각?
  - 2. 덮어씌움  -> 일단 가장 자연스럽다고 생각. redis 기본 정책 (다만 정책 선택할 수 있음)
  - 3. 업데이트 명령을 별도로 생성 - 그런데 사용자가 최초 생성과 업데이트를 구분해야하지 않나
  - 4. 
• 없는 키 조회: 값이 없다고 구분되어야 한다.
        
• 없는 키·반복 삭제: 이미 없는 상태이고, 멱등성 생각하면 그냥 아무것도 안해야. 다만 응답을 어떻게 하는게 좋을지? 사용자가 실패했다는걸 알면 좋은지 아닐지 생각해야 함.

• 빈 값: 저장할 수 있어도 될 것 같다. 다만 없는 값과 구분되어야 한다.
• 빈 키: 허용할 필요가 있는지는 잘 모르겠다. 팀에서 논의하고 싶다. => value 없을 수가 
• 입력이 잘못되어 거절된 경우: 기존 값과 다른 키는 변경되지 않아야 한다.

> 해시 테이블의 설계 원리, 구현 과정, 주요 함수의 동작 방식을 명확히 설명할 수 있어야 합니다.
=> 어떤 해시 함수 썼고, 테이블 자료구조 썼는지 근거가 명확해야함


모임에서는 기존 초안을 함께 확인하고 위 의견과 미정 사항을 논의한다. 합의한 내용만 대상 문서에 반영하며, 개인 메모를 확정 계약으로 취급하지 않는다. 설계와 코드는 아직 작성하지 않는다.
