# 테스트 시나리오 초안 검토 메모

이미 작성된 시나리오를 처음부터 다시 만들지 않는다. 대상 초안에 대한 개인의 완결된 생각과 제안을 정리하며, 미정 사항을 질문 목록으로 늘리지 않는다.

검토 대상: [2. 같은 카운터의 동시 증가](02-concurrent-counter-scenario.md)

## 검토 메모

아래는 개인 검토 의견이며, 합의 전에는 확정된 동작이 아니다.

**찬의 검토 방향**

- 시나리오 02의 카운터는 동시성 제어를 살펴보는 예시다.
- 카운터 전용 기능으로 범위를 미리 한정하지 않고, 사용자가 조회한 상태를 바탕으로 변경하는 여러 상황과 조작 방식을 검토한다.
- 기존 시나리오 02의 범위 변경 자체는 아직 합의되지 않았다.

### 사용자 관점의 문제 상황 정리

여러 요청이 같은 키의 `value`를 동시에 읽고 변경할 때, 사용자는 각 요청의 결과와 최종 상태를 신뢰할 수 있어야 한다.

- **시나리오 02:** 동시 요청에서도 결과가 정확한지 검토한다.
- **시나리오 03:** 정확성을 유지한 조건에서 성능을 비교한다.

아래는 문제 이해를 위한 예시와 검토 의견이며 확정된 행동 계약은 아니다.

**1. 변경분이 사라지는 상황 — 조회수·카운터 집계**

- 사전 상태: 카운터 `value`가 문자열 `"10"`이다.
- 사용자 행동: 두 요청이 각각 `1`씩 증가시키려 한다.
- 문제 상황:

  ```text
  요청 A: "10" 조회 → 11 계산 → "11" 저장
  요청 B: "10" 조회 → 11 계산 → "11" 저장

  두 요청이 성공했다면 기대하는 최종 수치: 12
  실제 최종 value: "11"
  ```

- 사용자에게 생기는 문제: 두 요청이 성공한 것처럼 보여도 증가분 하나가 사라진다.
- 확인할 결과: 성공한 변경이 빠지거나 중복되지 않고, 기존 수치와 개별 요청 결과에 맞게 반영되는지 확인한다.
- 기존 초안과의 관계: S2-01~03은 이 유형의 증가분 보존을 검토한다. 현재 초안은 주로 모든 요청이 성공한 경우를 다룬다.

**2. 같은 조건을 근거로 여러 요청이 성공하는 상황 — 재고 차감·호출 제한**

- 사전 상태: 남은 수량 또는 허용 횟수가 1이다.
- 사용자 행동: 두 요청이 각각 1을 사용하려 한다.
- 문제 상황:

  ```text
  요청 A: 남은 수량 1 확인 → 사용 성공
  요청 B: 남은 수량 1 확인 → 사용 성공

  남은 수량: 1
  성공한 요청: 2건
  ```

- 사용자에게 생기는 문제: 같은 남은 1을 근거로 재고를 초과 판매하거나 허용 횟수를 초과할 수 있다.
- 확인할 결과:
  - 같은 남은 1을 근거로 두 요청이 모두 성공해서는 안 된다.
  - 조건 확인과 변경이 어긋나지 않는지, 각 요청의 성공·거절과 최종 상태가 서로 일치하는지 검토한다.
  - 거절된 요청의 상태 변경 여부도 합의해야 한다.
- 같은 문제인 이유: 재고 차감과 호출 제한은 모두 현재 상태가 조건을 만족할 때만 변경하는 행동이다.
- 별도 검토: 재고의 도착 순서 보장은 별도로 논의한다.

**논의한 방향**

- **읽은 상태를 바탕으로 한 변경:** 찬의 의견은 상태를 읽고 변경하는 사이 다른 요청의 변경이 끼어들지 않도록 보장하는 것이다. 읽은 이후 상태가 달라졌다는 이유만으로 오류를 반환하는 방식은 요청이 빈번하게 겹치는 사용자 상황에서 계속 실패할 수 있어, 성공적으로 처리하기를 원하는 사용자에게 의미가 작다고 본다.
- **사용자의 요청 방식:** 현재 `get`과 `set` 중 `set`은 기존 상태를 바탕으로 변경하는 명령이 아니라 입력받은 `value`로 덮어쓰는 명령이다. 따라서 이러한 행동을 요청하려면 기존 `get`·`set`과 구분되는 명령이 필요하다는 것이 찬의 의견이다. 구체적인 명령의 종류·입력·응답과 내부 구조는 아직 정하지 않았다.
- **변경 결과 반환:** 변경 직후 결과를 응답에 포함하면 별도 조회 요청을 줄일 수 있다는 찬의 의견이 있다. 반환 결과는 해당 변경 시점의 결과이며 이후에도 최신임을 보장하지 않는다. 반환의 비용과 실제 이득은 아직 측정하지 않았고 응답 계약은 미정이다.
- **기존 동작과의 경합:** 새로운 행동끼리뿐 아니라 기존 저장·조회·삭제와 겹치는 경우도 검토한다. 의도한 `set` 덮어쓰기와 경합에 따른 유실은 구분한다. 만료는 시나리오 04에서 다루므로 이번 검토에서 제외한다.
- **요청 대기:** 경합 시 곧바로 실패시키지 않고 기다리되, 무한정 기다리는 방식과 기다림을 제한하는 방식 사이의 절충이 필요하다는 찬의 의견이다. 구체적인 제한과 결과는 미정이다.
- **검증:** 내부 동작과 외부 요청 경로를 모두 검증하는 방향을 생각한다. 성능 비교를 위한 외부 경로는 시나리오 03에서 정확성을 유지하는 조건으로 사용한다.

**제안의 범위와 한계**

- 카운터의 변경분 보존뿐 아니라 재고 차감·호출 제한의 공통 문제인 조건부 변경도 검토 대상으로 제안한다. 기존 시나리오 02 초안에 이를 반영하려면 별도 합의가 필요하다.
- 성공, 조건 불충족에 따른 거절, 처리 여부를 알 수 없는 경우는 구분해야 한다. 응답 유실 후 재시도의 보장 범위와 응답 표현은 아직 정하지 않았다.
- **재시도 식별의 필요성:** 응답이 유실된 뒤 같은 요청을 다시 보내더라도 중복 반영되지 않게 하려면, 같은 요청의 재시도와 새로운 요청을 구분할 수 있어야 한다. 찬은 이 보장이 실제 사용자 문제에 꼭 필요한지 더 생각해야 한다고 보며, 포함 여부와 구분 방법은 미정이다.
- **변경 결과의 범위:** 변경 결과를 알려주면 별도 조회를 줄일 수 있지만, 반환 후 다른 요청이 변경할 수 있다. 조건 불충족 시 결과에 현재 `value`까지 포함할지와 각 행동의 구체적 응답은 미정이다.
- 기존 저장·조회·삭제와 겹치는 상황에서 요청별 결과와 최종 상태가 설명되어야 한다. 세부 처리 순서와 대기 제한은 아직 정하지 않았으며, 삭제 결과는 문서 01의 삭제 직전 `value` 계약과 함께 검토한다.
- **덮어쓰기와 증가의 예:** 초기 `value`가 `"10"`일 때 `1` 증가 후 `"20"` 저장이면 최종 `value`는 `"20"`이고, 반대 순서면 `"21"`이다. 각 결과는 처리 순서에 따라 설명되지만, 어떤 순서를 보장할지는 미정이다.
- **요청 순서와 대기:** 찬은 서버에 먼저 온 요청을 우선 처리하는 관점을 제시했다. 도착 시점의 기준과 그 순서의 보장 여부, 대기 제한과 중단 시 결과는 아직 확정하지 않았다. 조건 불충족은 기다린 뒤에도 발생할 수 있으며 경합 자체로 인한 실패와 구분한다.
- 현재 사용자 문제는 동일 키 경합이다. 여러 키를 함께 변경할 보장이 필요한지는 확인되지 않았다.
- **여러 키의 보장 구분:** 이체처럼 여러 키가 관련된 사례는 있지만, 명령 사이에 다른 요청이 끼어들지 않는 보장과 일부 실패 시 변경을 되돌리는 보장은 다르다. 현재 사용자 문제에 어느 보장이 필요한지는 확인되지 않았다.
- 이전 상태가 필요한 행동에는 숫자 증감뿐 아니라 문자열 이어 붙이기도 있다. 각 행동의 입력·거절·상태 보존에 관한 세부 계약은 아직 정하지 않았다.
- **행동별 입력:** 실제 지원할 행동과 없는 키, 실제 `null`, 숫자 표현·증가량·크기 초과에 대한 결과는 미정이다. 문자열 이어 붙이기는 이전 상태가 필요한 행동의 예시이며 포함이 확정된 기능이 아니다.
- 내부·외부 경로를 모두 검증하되 구체적인 동시 실행 조건과 관찰 기준은 추후 정한다. 순차 처리 서버만으로 동시 처리 안전성을 입증하지 않는다.
- **검증 한계:** 각 요청의 결과와 최종 상태를 함께 관찰한다. 반복 실행과 다양한 조건을 검토하더라도 테스트 통과만으로 모든 실행 순서의 안전성이 증명되지는 않는다.

### 초안 행동 의미 확인

- **S2-01 (단일 증가의 기준 동작)**: 문자열 `"0"`인 `value`에 `1` 증가 요청을 한 뒤 `"1"`을 조회하고, 이후 조회만 반복하면 변하지 않음을 확인한다. 요청 방식과 성공 응답의 구체적 형태는 아직 미정이다.
- **S2-02 (같은 키의 동시 증가분 보존)**: `100`건의 동시 증가 요청에서 갱신 손실(lost update)이나 중복 반영이 발생하지 않음을 검증한다. `100`건 모두 성공 응답을 받는 것이 전제이므로, 일부 요청이 실패·거부되면 통과로 보지 않는다.
- **S2-03 (기존 값에서 증가분 보존)**: 초기값이 `"0"`이 아닌 `"10"`일 때도 `0`으로 초기화되거나 덮어써지지 않고 기존 `value`에 `100`이 누적되어 `"110"`이 되는지 확인한다.

### 빠진 상황

**동시성 제어 전반 — 검토 후보**

- **상태가 바뀐 뒤 원래 내용으로 돌아옴** — 조회 후 다른 요청이 내용을 바꿨다가 다시 원래 내용으로 되돌린 상황은 아직 제안이 정리되지 않았다.

### 다른 의견

- **검토 범위** — 기존 초안은 같은 카운터의 증가에 한정되어 있다. 동시성 제어 전반을 검토하되 어떤 사용자 행동을 실제 이번 계약과 테스트에 포함할지는 모임에서 결정한다. 카운터 테스트 통과만으로 다른 동작의 안전성을 주장하지 않는다.
- **사용자 행동 먼저** — 특정 증가 명령이나 다른 조작 방식을 전제하지 말고, 사용자가 무엇을 변경하고 어떤 결과를 기대하는지부터 정한 뒤 요청·응답과 설계를 논의한다.
- **사전 상태 준비 의존성 표기** — S2-01~S2-03의 사전 상태(`"0"`, `"10"`)를 문서 1의 저장 경로(`PUT /kv` 또는 `set`)로 준비하는지 명시할 필요가 있다.
- **성공 응답 계약 선행** — S2-01과 S2-02가 "성공 응답"을 기준으로 검증하므로, 증가 요청의 입력 형식과 성공 응답 형태(단순 `ok`인지 증가된 `value` 포함인지)를 먼저 합의해야 한다.
- **동시 실행 검증 한계 보완** — 한 번의 `100`건 통과만으로 레이스 컨디션 부재를 단정할 수 없으므로, 합의 단계에서 반복 횟수나 동시 요청 수 기준을 함께 정해 두는 편이 좋다.

### 미정 사항에 대한 생각 (합의 전 초안)

- **없는 키 증가**: `"0"`에서 시작해 `"1"`로 초기화할지, 존재하지 않는 키 오류로 거절할지 팀 합의 필요 (`02-concurrent-counter-scenario.md` 범위에는 "이미 존재하는 같은 카운터"로 적혀 있음).
- **비정수 / `null` 처리**: 정수 문자열이 아닌 `value`나 실제 `null`에 대해서는 상태 변경 없이 오류로 거절하는 쪽이 문서 1의 데이터 보존 원칙과 일관됨.
- **증가량과 범위**: 1단계에서 확정된 `value` 크기 상한(65,536바이트)과 충돌하지 않도록 정수 표현 규칙(부호·공백 허용 여부, 범위)을 명시해야 함.
- **실패·재시도**: 위의 '결과를 알 수 없는 요청과 재시도'에서 보장 범위를 계속 검토한다. 처리 방식은 정하지 않았다.

모임에서는 기존 초안을 함께 확인하고 위 의견과 미정 사항을 논의한다. 합의한 내용만 대상 문서에 반영하며, 개인 메모를 확정 계약으로 취급하지 않는다. 설계와 코드는 아직 작성하지 않는다.
