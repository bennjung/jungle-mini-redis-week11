# 시나리오 02 동시성 검토 — 최종 결론

## 범위

- 같은 키의 동시 증가·감소와 조건부 증가·감소를 검토한다. 재고 차감과 호출 제한처럼 현재 상태에 조건을 적용하는 사례를 포함한다.
- 증감 명령은 **`INCR`과 `DECR` 두 개만** 사용한다. `POST /kv/incr`와 `POST /kv/decr`에 `key`·`amount`, 선택적 `maximum` 또는 `minimum`을 전달한다. 구체적인 요청·응답 계약은 [REST API 명세 8절](../../rest-api.md#8-json-자료형증감-확장-계약--승인-미구현)에 둔다. 확장 경로는 아직 미구현이다.
- **이유:** 증감량이나 조건마다 명령을 나누지 않으면서, 같은 키의 동시 변경과 조건 확인을 함께 검증한다.

## 명령과 숫자

- `INCR`은 지정한 증감량을 더하고, `DECR`은 지정한 증감량을 뺀다. 증감 대상 `value`와 증감량은 JSON에서 해석된 숫자여야 한다.
- 정수와 소수를 허용한다. 대상 `value`는 음수일 수 있지만, 증감량은 음수를 거절하고 `0`을 허용한다.
- 실제 `null`, `"1"` 같은 문자열, 불리언, 배열, 객체는 증감 대상 숫자가 아니다. 문자열을 다시 숫자로 해석하지 않는다.
- `INCR`에는 상한을, `DECR`에는 하한을 선택적으로 지정한다. 상한을 생략한 증가는 별도 상한 조건 없이, 하한을 생략한 감소는 별도 하한 조건 없이 처리한다.
- 조건 생략은 허용하지만 명시적인 실제 `null`은 숫자 조건이 아니므로 거절한다. 조건 생략을 실제 `null`과 같은 것으로 취급하지 않는다.
- 상한·하한을 지정한 경우 계산 결과가 상한 이하 또는 하한 이상이면 성공한다. 경계와 같아도 성공한다. 현재 수치가 이미 조건 밖인 경우에도 계산 결과를 같은 기준으로 판단한다.
- 소수는 컴퓨터의 일반적인 소수 계산 결과를 따르며, 조건도 실제 계산 결과를 기준으로 판단한다.
- 없는 키는 자동 초기화하지 않고 거절한다. 표현할 수 없는 숫자나 계산 결과도 거절하고 상태를 보존한다.
- **이유:** JSON 타입을 그대로 사용해 문자열과 숫자를 구분하고, 음수 증감량 때문에 명령의 실제 방향이 뒤집히지 않게 한다. 조건은 변경 결과에 적용해 상한·하한 위반을 막는다.

### 저장 계약과 숫자 범위

- 저장 가능한 `value`를 JSON의 모든 자료형으로 확장한다. 문자열·숫자·불리언·실제 `null`·배열·객체와 이들이 중첩된 내용을 포함한다. 객체의 필드 이름은 문자열이다. 표준 JSON에 없는 `NaN`·양의 무한대·음의 무한대·순환 참조는 지원 대상이 아니다.
- [이슈 #1](https://github.com/bennjung/jungle-mini-redis-week11/issues/1)의 자료형 지원과 시나리오 02를 같은 함수 흐름에서 다룬다. 숫자 저장은 증감 실행의 선행 조건이며, 테스트 준비를 위해 저장소 내부 상태에 숫자를 직접 넣어 우회하지 않는다. 구체적인 숫자 범위는 별도 후속 검토로 남긴다.
- 기존 확정 계약과 S1-10-01의 숫자 거절 테스트, 기존 HTTP 동작에 미치는 영향을 확인하고 합의 후 함께 갱신한다. 이 문서만으로 기존 계약이나 테스트가 변경된 것은 아니다.
- **이유:** HTTP에서 해석된 JSON 타입을 그대로 보관하고, 같은 저장 상태에 숫자 증감을 연결하기 위해서다. 전체 자료형을 허용하더라도 증감은 숫자에만 허용한다.

### 자료형별 64KiB 크기 제한

저장 항목 하나의 `value` 상한은 **64KiB(65,536바이트)**이며, 상한과 같으면 허용하고 초과하면 저장 상태를 변경하지 않고 거절한다. 요청 본문 전체나 저장소의 `key`를 합산한 크기가 아니라 `value`만 측정한다. 저장소 `key`는 기존 문자열 1~256 UTF-8 바이트 제한을 유지한다.

| 자료형 | 크기 계산 기준 | 예시 |
| --- | --- | --- |
| 문자열 | 문자열 내용 자체의 UTF-8 바이트 수. 바깥 따옴표는 포함하지 않음 | `"가"`는 3바이트 |
| 숫자 | 공백 없는 JSON 숫자 표현의 UTF-8 바이트 수 | `123`은 3바이트, `-3`은 2바이트, `1.0`은 3바이트 |
| 불리언 | JSON 표현의 UTF-8 바이트 수 | `true`는 4바이트, `false`는 5바이트 |
| 실제 `null` | 기존 기준 유지 | 0바이트 |
| 배열 | 내부 내용과 괄호·따옴표·구분 기호·필수 이스케이프를 포함한 JSON 전체의 UTF-8 바이트 수 | `[1,"가"]`는 9바이트 |
| 객체 | 필드 이름과 내부 내용, 괄호·따옴표·구분 기호·필수 이스케이프를 포함한 JSON 전체의 UTF-8 바이트 수 | `{"a":1}`은 7바이트 |

- 새 타입의 크기 측정에는 `json.dumps(value, ensure_ascii=False, separators=(",", ":"), allow_nan=False)`로 만든 문자열을 UTF-8로 인코딩한 길이를 사용한다. 입력 JSON의 꾸밈 공백이나 유니코드 이스케이프 표기 방식에 따라 제한 판정이 달라지지 않도록 해석된 `value`를 기준으로 한다.
- 최상위 문자열과 실제 `null`은 기존 크기 기준을 유지한다. 배열·객체 내부의 문자열과 `null`은 전체 JSON 표현의 일부로 계산한다.
- 크기 측정용 JSON 표현을 만들더라도 저장 대상을 JSON 문자열로 바꾸지 않는다. 저장·조회·삭제에서 자료형을 유지한다.
- 이 상한은 항목의 크기 판정 기준이며 Python 객체의 실제 메모리 사용량이나 저장소 전체 메모리 제한이 아니다.
- **이유:** 기존 문자열·`null` 계약을 보존하고, 새 타입에는 재현 가능한 크기 기준을 적용하기 위해서다.

### 기존 구조를 유지하는 상위 함수 계약

- 함수별 책임·호출·반환·실패 연결은 [탑다운 함수 문서의 병렬 설계용 공통 계약](02-top-down-functions.md#병렬-설계용-공통-계약)을 따른다. `amount`, 선택 키워드 `maximum`·`minimum`으로 호출하며 조건 생략과 명시적 `None`을 구분한다. 생략 표시의 내부 구현 방식은 고정하지 않는다.
- #1의 숫자 저장은 실제 증감 실행·통합 검증의 선행 조건이지만 설계를 직렬로 묶는 조건은 아니다. 공통 계약을 기준으로 HTTP 연결·자료형 저장·증감 연산을 병렬 설계한다.

- `app.py`의 `create_app(storage)`는 기존 HTTP 요청 해석·본문 구조·필수 필드 검사와 응답 연결을 담당한다. JSON 해석 결과를 숫자나 문자열로 추가 변환하지 않는다.
- `storage.py`의 `MiniRedis.set(key, value)`는 키와 지원 자료형·크기를 상태 변경 전에 확인하고, 성공 시 지정한 키만 저장하거나 덮어쓴 뒤 기존 `{"ok": True}`를 반환한다. 입력 거절은 기존 `{"error": "INVALID_INPUT"}` 반환과 전체 상태 보존을 유지한다.
- `MiniRedis.get(key)`는 키가 있으면 `{"found": True, "value": ...}`, 없으면 `{"found": False}`를 반환한다. 조회는 상태를 변경하지 않는다.
- `MiniRedis.delete(key)`는 키가 있으면 삭제하고 삭제 직전 내용을 `{"found": True, "value": ...}`로 반환한다. 없으면 `{"found": False}`를 반환하며 다른 키는 유지한다.
- 조회·삭제 반환의 타입과 내용을 유지하고, 실제 `null`인 항목과 키 없음을 구분한다. 키 입력 거절 계약은 유지한다.
- 증감은 기존 HTTP → 저장소 흐름에서 저장소 연산 한 번으로 처리한다. HTTP에서 `get` → 계산 → `set`으로 분리하지 않는다. 증감량·선택적 상한을 받는 `incr`와 증감량·선택적 하한을 받는 `decr`를 기준으로 구체화한다.
- **이유:** 기존 딕셔너리 저장 구조와 공개 함수를 재사용할 수 있으므로 새 저장 계층이나 명령 처리 계층을 도입할 필요가 없다. `set`에서는 문자열 전용 거절뿐 아니라 문자열만 가정하는 크기 계산도 함께 변경해야 한다.
- JSON 자료형 지원은 보존적으로 확장한다. 기존 `MiniRedis`·인스턴스별 `_data`·`set/get/delete`와 HTTP JSON 전달 경로를 유지하고, 필요한 타입 검증·크기 계산만 확장한다. 타입별 저장소·래퍼·변환 계층이나 JSON 문자열 저장을 추가하지 않는다. 기존 코드로 충족되는 조회·삭제는 재작성하지 않는다.

## 명령 처리 순서

- `INCR`, `DECR`, `set`, `get`, `delete`를 같은 처리 순서에 포함하고, 서버가 순서를 정한 대로 명령 하나씩 처리한다. 사용자가 보낸 순서나 응답을 받은 순서는 보장하지 않는다.
- 증감은 현재 수치 읽기 → 결과 계산 → 조건 확인 → 성공 시 저장을 다른 명령이 끼어들지 않는 하나의 작업으로 처리한다. 조건 불충족이면 저장하지 않는다.
- 단일 프로세스·`threaded=False`인 기존 HTTP 서버의 순차 처리를 사용하며, 애플리케이션은 전달받은 요청 하나를 처리한다. 별도 명령 큐·소비자·순서 관리 계층을 만들지 않는다. 서버의 처리 순서를 클라이언트 전송 순서나 물리적 도착 순서의 보장으로 해석하지 않는다.
- 구현은 단일 요청 처리 스레드를 유지하고 요청을 백그라운드·작업 풀로 넘기지 않는다. 대기는 기존 서버와 운영체제의 연결 대기 기능에만 맡긴다. 하위 에이전트의 작업 병렬성이 서버의 요청 병렬 처리를 뜻하지 않는다. 세부 제약은 [탑다운 문서의 최상위 실행 구조 제약](02-top-down-functions.md#최상위-실행-구조-제약--모든-범위에-적용)을 따른다.
- 만료와 증감의 경합은 이번 범위에서 제외하고 시나리오 04의 만료 정책을 정할 때 논의한다. 제외는 해당 상황의 안전성 보장을 뜻하지 않는다.
- **이유:** 조회와 저장이 각각 안전해도 그 사이에 다른 명령이 끼어들면 변경이 유실되거나 같은 조건을 여러 요청이 잘못 사용할 수 있다.

## 응답과 거절

- 증감 성공 응답은 HTTP 200과 `{"ok":true,"value":...}`다. 해당 명령이 처리된 직후의 `value`이며, 이후 다른 명령이 실행될 수 있으므로 응답 수신 시점에도 최신이라는 보장은 아니다.
- 실패는 키 없음, 숫자가 아닌 타입, 음수 증감량, 조건 불충족, 표현 범위 초과 등 상황에 따라 구분한다. 조건 불충족과 표현 범위 초과는 별개의 실패다.
- 대상 `value`·증감량·상한·하한이 숫자가 아닌 경우 어느 부분이 잘못됐는지와 실제 타입을 알린다.
- 조건 불충족 응답에는 조건을 판단한 시점의 현재 `value`를 포함한다. 요청한 증감량·조건·계산 결과를 모두 반환하기로 한 것은 아니다.
- 정상적인 거절은 저장 상태를 변경하지 않는다. 오류는 `INVALID_INPUT`·400, `TYPE_MISMATCH`·400, `NEGATIVE_AMOUNT`·400, `NOT_FOUND`·404, `OUT_OF_RANGE`·422, `CONDITION_NOT_MET`·409, 예상하지 못한 내부 오류는 `INTERNAL_SERVER_ERROR`·500으로 구분한다. 500은 상태 미변경을 보장하는 거절과 다르다.
- 일반 오류는 `error`만 반환한다. 타입 오류는 `field`와 `actual_type`, 조건 불충족은 판단 시점의 `value`를 추가한다. 적용 조건과 상태를 선택한 이유는 REST API 명세 8.3~8.4절을 따른다.
- 증감 요청의 반대 방향 조건과 알 수 없는 필드는 `INVALID_INPUT`으로 거절한다. 조건이 조용히 무시되는 것을 막기 위한 규칙이며 기존 PUT의 추가 필드 정책은 변경하지 않는다.
- **이유:** 사용자가 성공 결과와 거절 원인을 구분할 수 있어야 하며, 실패한 요청 때문에 상태가 바뀌면 안 된다.

### 여러 오류가 겹칠 때의 판정 순서

다음 순서로 확인하고 먼저 발견한 오류 하나만 반환한다.

1. 요청 형식과 필수 입력
2. 키·증감량·조건의 타입과 입력 제한
3. 대상 키의 존재 여부
4. 저장된 `value`의 숫자 타입
5. 계산 결과의 표현 가능 여부
6. 계산 결과의 상한·하한 충족 여부

같은 입력 검증 단계에서는 키 → 증감량 → 조건 순으로 확인한다. 예를 들어 없는 키에 음수 증감량을 요청하면 음수 증감량 오류를 반환하고, 계산 결과가 표현 범위와 상한을 모두 초과하면 표현 범위 초과를 반환한다. 구체적인 숫자 범위는 이슈 #1에서 정한다.

- **이유:** 요청 자체의 유효성을 먼저 확인한 뒤 저장 상태를 확인하고, 계산 결과를 정상적으로 표현할 수 있는지 확인한 다음 조건을 판단한다. 오류가 겹쳐도 판정 결과를 일관되게 유지한다.

## 대기·연결·재시도

- [이슈 #4](https://github.com/bennjung/jungle-mini-redis-week11/issues/4)의 확정 결정에 따라 직접 대기 큐를 만들지 않고 기존 서버와 운영체제의 연결 대기 기능을 사용한다. 현재 연결 대기 한도를 별도로 조정하지 않는다. 연결 대기 수를 명령 수로 해석하거나 가득 찼을 때 특정 JSON 거절 응답을 보장하지 않는다.
- 연결 실패·시간 초과가 관찰되거나 대기 수 제한·초과 거절 등의 명시적 보장이 필요해지면 기존 서버 설정부터 확인하고 재검토한다. 명령 대기 시간 제한도 이번에 추가하지 않으며 [이슈 #3](https://github.com/bennjung/jungle-mini-redis-week11/issues/3)에서 후속 검토한다.
- 클라이언트가 연결을 끊어도 서버가 연산을 취소하거나 이미 반영된 연산을 되돌린다고 보장하지 않는다.
- 응답을 받지 못한 클라이언트는 실제 처리 여부를 알 수 없다. [이슈 #2](https://github.com/bennjung/jungle-mini-redis-week11/issues/2)의 작성자 댓글에 따라 이번에는 재시도하지 않는다. 재시도에 따른 중복 방지도 보장하지 않는다.
- **이유:** 요청이 몰릴 때 성공과 거절을 구분해야 성능 결과를 해석할 수 있다. 연결 종료만으로 요청이 실행되지 않았다고 보장할 수 없고, 이미 처리된 연산을 뒤늦게 되돌리면 다른 요청의 결과와 충돌할 수 있다.

## 검증 범위

정상·실패·경계·동시 상황을 모두 검토한다. 아래는 검증 방향이며, 정확한 사전 상태·입력·호출 경로·검증 시점·유지 조건은 테스트 계약을 확정할 때 정한다.

- 구체화한 입력·관찰·유지 조건과 코드의 연결, 미검증 범위는 [테스트 케이스 문서](02-test-cases.md)에 둔다. 테스트 작성과 실행이 구현 완료를 뜻하지 않는다.

- **정상:** 정수·소수 증감, 음수인 대상 `value`, 증감량 `0`, 조건 충족, 상한·하한과 결과가 정확히 같은 경우를 확인한다.
- **동시 증가:** 같은 키에 100건을 동시 진행하는 사례를 포함한다. 모두 성공한 경우 각 성공 응답의 변경 직후 `value`와 최종 상태를 함께 확인한다. 다른 변경 없이 0에서 1씩 증가한다면 응답의 1부터 100까지가 각각 한 번 나타나는지 검토한다.
- **입력 거절:** 없는 키, 숫자가 아닌 대상·증감량·조건, 음수 증감량을 확인한다. 숫자가 아닌 타입은 해당 부분과 실제 타입을 확인하고, 거절 시 상태가 보존되는지 확인한다.
- **조건과 범위:** 상한 초과·하한 미달, 현재 수치가 조건 밖인 경우, 소수 경계와 표현 범위 초과를 검토한다. 조건 불충족 시 판단 시점의 현재 `value`와 상태 보존을 확인한다. 정확한 숫자 범위는 이슈 #1 결정 후 정한다.
- **혼합 요청:** 성공과 거절이 섞일 때 요청별 응답과 최종 상태를 대조하고, 거절된 요청은 반영되지 않는지 확인한다. 수치 1, 하한 0에서 1 감소 요청 두 건이면 한 건은 성공하고 다른 한 건은 `value` 0을 기준으로 거절되는 상황을 검토한다.
- **기존 명령과 여러 키:** 증감과 `set`·`get`·`delete`가 겹칠 때 결과가 실제 처리 순서로 설명되는지, 서로 다른 키의 변경이 섞이지 않는지 검토한다. 여러 키를 한 번에 변경하거나 실패한 일부를 되돌리는 보장은 결정하지 않았다.
- **연결 실패·과부하:** 기존 서버의 대기 기능을 사용하므로 앱 큐 포화에 대한 명시적 거절 테스트를 이번 계약으로 강제하지 않는다. 연결 실패나 시간 초과가 있으면 실패를 임의로 제외해 통과시키지 않고 기록하며, 이슈 #4의 재검토 조건으로 다룬다.
- **자료형과 크기:** JSON의 모든 자료형과 중첩 내용에 대해 저장·조회·삭제 시 타입과 내용 보존을 확인하고, 위 크기 계산 기준의 65,536바이트 경계와 초과 시 상태 보존을 확인한다. 문자열 숫자와 실제 숫자, 불리언과 숫자, 조건 생략과 실제 `null`을 구분한다.
- 테스트는 반복하고 완료 대기 한도를 둔다. 미완료 요청을 제외해 통과시키지 않는다. 반복 횟수와 한도는 미정이며, 테스트 완료 한도는 서버의 대기 시간 제한과 다르다.
- **이유:** 최종합만으로는 유실과 중복이 상쇄되는 경우를 구분하지 못한다. 요청별 결과·최종 상태·실패 후 상태를 함께 보더라도 모든 실행 순서의 안전성이 증명되는 것은 아니다.

## 성능 비교와 검증 한계

- 시나리오 03에서도 정확성을 유지하고, 보낸 요청 수와 성공·거절·미완료 건수, 성공과 거절의 응답 시간을 구분한다. 거절을 성공 처리량으로 계산하지 않는다.
- 순차 처리 개발 서버에서의 검증을 저장소 자체의 다중 스레드 호출 안전성으로 확대하지 않는다. 성능 우위는 동일한 조건으로 측정하기 전에 확정하지 않는다.
- **이유:** 많은 요청을 빠르게 거절하는 결과를 실제 작업 처리 성능으로 오해하지 않고, 검증하지 않은 안전성을 주장하지 않기 위해서다.
