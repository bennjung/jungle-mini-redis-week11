# 같은 카운터의 동시 증가 — 검토 메모

검토 대상: [02-concurrent-counter-scenario.md](02-concurrent-counter-scenario.md).
작성 기준: [공통 검토 템플릿](../템플릿-scenario-preparation-template.md).

아래는 개인 검토 의견이며, 합의 전에는 확정된 동작이 아니다. 기존 S2-01~03을 다시 작성하거나 설계·코드를 확정하지 않는다. 원문에 이미 적힌 미정 사항은 누락으로 세지 않고, 논의할 질문을 구체화했다.

사용자 피드백: 다른 키의 value 보존·반복 조회의 상태 유지·입력 거절 시 `INVALID_INPUT` 반환과 기존 value 보존은 기본 동작으로 본다. 이 세 항목은 별도의 빠진 상황 목록에서 제외했다. 정상·거절 요청이 섞이는 경우는 계속 검토하며, 아래 응답 수 판정은 사용자가 제시한 의견을 구체화한 것이다.

### 빠진 상황

- **[S2-02~03] 정상 요청과 거절 요청이 섞이는 경우** — 현재는 100건 모두 성공한 경우만 다룬다. 검토 의견은 정상 통신 조건에서 요청 100건 각각에 대응하는 응답 100건을 확인하는 것이다. 각 요청에 맞게 성공 또는 `INVALID_INPUT` 응답을 확인하고, 모두 완료된 뒤 대상 카운터의 최종 value에는 성공한 증가분만 반영되었는지 확인하자. 정상·거절 요청의 구체적인 입력 구성은 숫자 정책 합의 후 정한다. 기존의 100건 모두 성공하는 시나리오는 유지한다.

### 다른 의견

- **[S2-01~03] 싱글 스레드에서도 증가 로직이 꼬일 수 있음 (`get → get → set → set`)**
  - **문제 상황:** 두 클라이언트가 조회와 저장을 별도 요청으로 보내면 싱글 스레드여도 `A조회(0) → B조회(0) → A저장(1) → B저장(1)` 순서로 처리될 수 있다. 두 번 증가했으므로 기대하는 최종 value는 문자열 `"2"`지만, 실제로는 문자열 `"1"`이 되어 증가분 하나가 유실된다.
  - **원인:** 서버가 각 HTTP 요청을 하나씩 처리해도, 증가 한 번을 구성하는 조회·계산·저장이 여러 요청으로 나뉘어 있으면 그 사이에 다른 클라이언트의 요청이 들어갈 수 있다. 한 클라이언트가 모든 증가를 하나씩 끝낸 뒤 다음 증가를 시작하는 테스트만으로는 이 상황을 확인하기 어렵다.
  - **해결방안:** 외부 사용자는 증가 요청 한 번을 보내고, 서버가 `읽기 → +1 계산 → 쓰기` 전체를 하나의 작업 단위로 끝낸 뒤 다음 증가 요청을 처리한다. 그러면 A는 0에서 1로, B는 A가 반영한 1에서 2로 증가시킨다. 서버의 대기·실행 순서를 정할 때도 작업 단위는 쓰기만이 아니라 증가 전체다. 구체적인 증가 HTTP 요청·응답 표현은 별도로 합의한다.
  - **작업 큐 처리 방안:** 별도 큐를 도입한다면 증가 요청 전체를 작업 하나로 넣고, 소비자 하나가 해당 작업의 읽기·계산·쓰기를 끝낸 뒤 다음 작업을 꺼내는 방안을 검토한다. 성공 응답은 큐 삽입 시점이 아니라 실제 증가 완료 후 보낸다. GET과 SET을 별도 작업으로 넣기만 하면 `get → get → set → set`을 막지 못한다. 현재처럼 요청 전체를 순차 처리할 수 있다면 별도 작업 큐가 필수인 것은 아니다. 큐 도입 여부·크기·가득 찼을 때의 처리·대기 한도는 미정이다. 소비자를 여러 개 두는 방식의 정합성은 이 방안으로 보장하지 않는다.
  - **작업 의존성 처리:** GET 완료 콜백에서 SET을 큐에 넣으면 해당 작업의 `GET → SET` 순서는 맞출 수 있다. 다만 다른 클라이언트의 GET·SET이 사이에 들어오는 상황은 남는다. 증가분 보존을 위해서는 콜백 연결과 별개로 증가 전체의 실행 경계를 보장해야 한다.
  - **Redis의 원자적 실행 참고:** 실제 Redis에서는 `INCR` 또는 서버 내부 Lua 스크립트가 증가 전체를 처리할 수 있다. `MULTI/EXEC`도 묶인 명령 사이에 다른 클라이언트 명령이 끼어드는 것을 막지만, GET 결과는 EXEC 후 받으므로 클라이언트가 그 결과로 계산하는 GET·SET을 단순히 묶는 것으로 해결되지 않는다. 이 경우 WATCH로 변경을 확인하고 재시도하거나 서버 내부 계산을 사용한다. Mini Redis에 트랜잭션·Lua를 구현하기로 확정한 것은 아니다. [Redis 트랜잭션](https://redis.io/docs/latest/develop/using-commands/transactions/), [Redis Lua 실행](https://redis.io/docs/latest/develop/programmability/eval-intro/).
  - **관찰 방안:** 문제를 설명·재현할 때는 두 조회가 각 저장보다 먼저 끝나는 순서를 확인한다. 해결 후에는 여러 클라이언트의 증가 요청을 진행시키고, 모든 성공 응답 뒤 S2-02의 문자열 `"100"`, S2-03의 문자열 `"110"`을 확인한다. 요청을 보낸 순서와 응답이 도착한 순서를 서버의 처리 순서로 간주하지 않는다.
  - **요청 전송 방식 검토:** 슬라이딩 윈도우는 테스트 클라이언트에서 응답 대기 중인 증가 요청을 최대 `W`건 유지하고, 응답이 오면 다음 요청으로 채우는 방식이다. `W=1`은 순차 호출 기준선, `W=100`은 원문의 100건 동시 진행을 검토할 조건이다. `1<W<100`은 추가 조건이며 원문의 100건 동시 조건을 대신하지 않는다. 전체 100건의 응답을 받은 뒤 최종 카운터를 조회한다. 연결 수·클라이언트 설정이 전송을 직렬화하지 않는지 확인하며, 추가 윈도우 크기·시작 조율 방법은 미정이다.
  - **전송 대안 — 파이프라이닝:** 실제 Redis처럼 각 명령의 응답을 기다리지 않고 여러 증가 명령을 연달아 보낸 뒤 각각의 응답을 확인하는 방식을 참고할 수 있다. 송수신을 묶어 대기·I/O 비용을 줄이는 장점이 있지만, 큰 묶음은 응답 버퍼를 더 사용하고 묶음 전체를 기다리면 느린 명령이 다음 묶음 전송을 지연시킬 수 있다. 묶음 안의 GET·SET 전체가 자동으로 원자적 실행되는 것은 아니다. [Redis 파이프라이닝](https://redis.io/docs/latest/develop/using-commands/pipelining/).
  - **대안 적용 범위:** 슬라이딩 윈도우와 파이프라이닝은 클라이언트의 요청 전송 정책이며 함께 사용할 수도 있다. 작업 큐는 서버에서 실행 전 작업을 보관·전달하는 수단이다. 전송 방식 자체에 별도 작업 큐가 필수인 것은 아니다. 현재 Mini Redis는 HTTP이므로 Redis 프로토콜의 파이프라이닝을 바로 적용할 수 있다고 보지 않는다. HTTP에서 여러 요청을 진행하는 방식과 전송을 실제로 묶는 방식은 구분하고, 전송 규약·일괄 API·클라이언트 도구를 새로 도입할지는 별도 합의한다. S2의 정확성 기대 결과는 유지하며, TPS 우위는 문서 3에서 같은 조건으로 측정하기 전에는 확정하지 않는다.
  - **구분할 점:** 슬라이딩 윈도우는 여러 요청이 진행 중인 상황을 만드는 전송 방식이며, 증가 전체를 하나의 작업으로 묶는 서버 처리가 유실을 막는다. TCP 자체의 윈도우는 바이트 단위 전송 제어다. [TCP 윈도우 설명](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.8.6). 현재 `app.py`는 `threaded=False`이고 [HTTP 담당 문서](../scenario_01_storage/01-http-scope.md)도 순차 처리를 명시하므로, 이 검증을 저장소의 다중 스레드 호출 안전성 보장으로 확대하지 않는다.
- **[S2-01~03] 증가 성공 응답도 직접 확인** — 최종 조회 결과만 확인하지 말고 각 요청의 성공 상태와 본문도 확인하자. 증가 요청의 응답에 갱신된 수를 넣을지, 성공 여부만 넣을지는 아직 미정이다. 응답이 도착한 순서를 실제 증가 처리 순서로 간주하지 않는다.
- **[S2-02~03] 최종합으로 확인할 수 있는 범위** — 최종 문자열 `"100"`·`"110"`은 필요한 검증이다. 다만 유실과 중복이 같은 수만큼 발생해 상쇄되는 경우까지 최종합만으로 구분하지는 못한다. 원문의 “유실·중복 없음”을 어디까지 입증할지, 합의한 응답으로 추가 관찰할 수 있는지 논의하자. 이를 위해 요청 ID나 로그를 필수로 도입하자는 제안은 아니다.
- **[S2-02~03] 끝나지 않는 요청의 판정** — “모두 성공 응답을 받은 뒤”만 있으면 응답이 끝내 오지 않을 때 테스트가 무한 대기할 수 있다. 완료 대기 한도와 시간 초과 시 실패 판정을 정하자. 초과한 요청을 제외한 결과로 통과시키면 안 된다. 반복 횟수·실행 조건도 원문의 한계 설명에 맞춰 합의하자.

### 미정 사항에 대한 생각

- **[S2-01~03] 숫자 표현** — 기존 저장소는 `"10"`을 문자열로 보관한다. 증가할 때 `"01"`·`"+1"`·`"1.0"`·`" 1 "`·빈 문자열·문자열 `"null"` 중 어디까지 숫자로 받아들일지 정해야 한다. 허용한 표현을 증가 후 어떤 문자열로 저장할지도 필요하다. 기존 `set`이 숫자를 자동 해석하도록 바꾸자는 뜻은 아니다.
- **[S2-01~03] 없는 키와 실제 null** — 원문에 이미 미정인 항목이다. 키 없음, 실제 `null`이 저장된 키, 문자열 `"null"`인 키는 문서 1에서 서로 다른 상태다. 이를 모두 초기값 0으로 취급할지 자동으로 결정하지 말자.
- **[S2-01~03] 숫자 범위와 증가량** — 현재 케이스는 모두 `1` 증가다. 이번 기능도 1 증가만 제공할지, 증가량을 입력받을지 확인하자. 음수·소수·0 증가의 지원을 자동으로 추가하지 않는다. Redis와 같은 64비트 정수 범위가 필수라고 단정할 근거도 없다. 허용할 숫자 범위와 기존 문자열 value의 65,536바이트 상한을 어떻게 함께 적용할지는 미정이다. 상한 초과를 거절한다면 `INVALID_INPUT` 반환과 기존 내용 보존을 기본 동작으로 본다.
- **[S2-02~03] 실패·응답 유실·재시도** — 이미 별도 계약이 필요한 항목이다. 입력 거절, 실제 반영 뒤 응답 유실, 같은 요청의 재전송을 구분하자. 실패 응답·시간 초과만 보고 “증가가 반영되지 않았다”고 판단하거나, 재시도가 자동으로 중복 제거된다고 가정하지 않는다.
- **[S2-02~03] 일반 저장과 증가가 겹칠 때의 범위** — 삭제·만료와의 경합은 제외한다고 적혀 있지만, 같은 키의 `set`과 증가가 겹치는 경우는 명시되어 있지 않다. 이번 범위에 포함할지 제외할지 정하자. 제외한다면 “다른 요청 없음”을 S2-03의 사전 상태에도 명확히 적용하는 편이 좋다.

모임에서는 위 의견과 기존 미정 사항을 논의하고, 합의한 내용만 대상 시나리오에 반영한다. 문서 3의 성능 비교에도 같은 카운터 정확성·실패 판정 기준을 적용하되, 이 메모로 성능 조건까지 확정하지 않는다.
