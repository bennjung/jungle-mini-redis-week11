# JSON 자료형 지원·증감 — 탑다운 함수 초안

## 기준과 상태

- 행동과 이유는 [통합 결론](02-concurrent-counter-integrated-review.md)을 따른다. 이 문서는 해당 행동을 기존 함수와 새 증감 함수에 배치하는 설계 초안이다.
- 기존 `app.py` → `storage.py` 흐름과 `MiniRedis._data`를 사용한다. 별도 명령 큐나 처리 계층은 만들지 않는다.
- 아래 코드는 호출 관계와 책임을 표현하는 골격이며 실행 코드가 아니다. 범위 사이의 호출·반환은 아래 공통 계약을 기준으로 설계한다. 조건 생략의 내부 구현 방식은 고정하지 않는다. 승인된 외부 경로·요청 필드·응답·오류는 [REST API 명세 8절](../../rest-api.md#8-json-자료형증감-확장-계약--승인-미구현)을 따른다.
- 구현 시에는 확정된 호출 계약에 대한 테스트를 먼저 작성하고 실행한 뒤 본문을 구현한다. 기존 확정 테스트는 구현에 맞춰 임의로 바꾸지 않는다.
- [테스트 케이스 문서](02-test-cases.md)는 기존 저장소 함수와 승인된 HTTP 계약을 코드에 연결한다. J1은 자료형 저장, A01~07은 HTTP 경계, C01~06은 저장소 직접 증감의 독립 테스트이며 실제 연결·동시 요청 테스트도 유지한다.

## 설계 범위 구분 — 이슈 #1과 시나리오 02 전체

아래 구분은 설계 책임의 범위다. 사람 수에 따른 분담, 새 파일·계층·큐의 도입이나 별도 구현을 뜻하지 않는다. 기존 `create_app(storage)`와 `MiniRedis` 안에서 요청 → 저장 상태 → 증감의 순서로 구체화한다.

### 범위 A. 외부 요청·응답 연결 — #1·02 공통

- 대상: `app.py`의 `create_app(storage)`, 기존 `put_kv`·`get_kv`·`delete_kv`, 추가할 `incr_kv`·`decr_kv`.
- #1: 기존 저장·조회·삭제 경로에서 JSON 타입을 변환 없이 전달하고 반환한다. JSON 해석과 기본 반환 기능을 새로 만들지 않는다.
- 02: `POST /kv/incr`·`POST /kv/decr`의 필수·허용 필드를 확인하고, 조건 생략과 명시적 null을 구분해 저장소 연산 한 번으로 전달한다.
- 저장소 반환을 승인된 HTTP 상태·JSON 본문으로 연결하고 예상하지 못한 내부 오류는 상세 노출 없이 500으로 구분한다.
- 경계: HTTP가 저장된 상태를 미리 조회하거나 증감 계산·상하한 판정을 하지 않는다. 키·자료형·크기와 연산 입력 검증은 저장소 책임이며 HTTP에서 중복 구현하지 않는다.
- 검증 연결: J1의 HTTP 경로, S2-07·08 및 나머지 S2의 요청·응답. 실제 저장소 연결 테스트와 오류 경계 테스트를 구분한다.

### 범위 B. JSON 자료형 저장·반환 — 이슈 #1

- 대상: `storage.py`의 `MiniRedis.set/get/delete`와 기존 `_data`.
- `set`: 키 검증 → JSON 자료형·중첩 내용 검증 → 자료형별 64KiB 확인 → 저장 또는 덮어쓰기. 입력 거절은 상태를 바꾸지 않는다.
- `get`·`delete`: 저장한 JSON 타입과 내용을 유지하며 기존 `found`·`value` 계약을 사용한다. 기존 코드로 충족되는 부분까지 불필요하게 재작성하지 않는다.
- 문자열 전용 거절과 크기 계산을 함께 바꾼다. 저장을 위해 JSON 문자열로 변환하지 않는다.
- 경계: 숫자 문자열의 자동 해석, 증감 계산·조건 판단은 이 범위가 아니다. 배열·객체의 직접 호출 시 변경 전파 정책과 구체적인 숫자 범위는 미정 사항으로 남기며 임의 확정하지 않는다.
- 검증 연결: J1-01~04의 저장소·HTTP 테스트. 기존 숫자 거절 테스트와 관련 명세는 계약 전환 시 함께 갱신할 대상으로 구분한다.

### 범위 C. 증감 연산과 상태 변경 — 시나리오 02

- 대상: `MiniRedis.incr`·`MiniRedis.decr`.
- 키 → 증감량 → 지정 조건 순으로 입력을 검증한 뒤 대상 존재와 숫자 타입을 확인한다. 불리언은 숫자로 취급하지 않는다.
- 현재 수치 읽기 → 증감 계산 → 결과 표현 가능 여부·크기 확인 → 상한·하한 확인 → 성공 시 저장을 호출 한 번 안에서 마친다.
- 성공은 변경 직후 `value`, 타입 오류는 잘못된 부분과 실제 타입, 조건 불충족은 판단 시점의 현재 `value`를 반환한다. 정상적인 거절은 전체 저장 상태를 보존한다.
- 경계: HTTP 상태 코드를 저장소 책임으로 옮기지 않는다. 외부 `get`·`set` 요청을 묶어 증감을 대신하지 않는다. 직접 큐·잠금·소비자·재시도 중복 제거를 새로 도입하지 않는다. 저장소 직접 다중 스레드 안전성도 이번 순차 서버 설계로 보장하지 않는다.
- 검증 연결: C01~06의 직접 호출 테스트와 S2-01·04~06의 실제 저장소 연결 HTTP 테스트. #1 구현 전 숫자 준비 실패를 별도로 구분한다.

### 전체 연결 검증 — A·B·C의 공동 완료 범위

- 범위 B의 정상 저장으로 숫자 사전 상태를 준비하고, 범위 A를 통해 범위 C를 호출한 뒤 응답과 최종 상태를 확인한다.
- 실제 순차 서버에 동시 요청을 보내 S2-02·03·09~14의 증가분, 성공·거절 혼합, 조건부 감소, 여러 키, 저장·조회·삭제 경합을 확인한다.
- 현재 실패하는 숫자 사전 상태 준비를 내부 딕셔너리 변경으로 우회하지 않는다. 요청 실패와 미완료를 제외해 통과시키지 않는다.
- 반복 횟수·완료 대기 한도와 숫자 범위의 보류 상태는 유지한다. 구현 전 테스트 작성이나 한 부분의 통과를 전체 구현 완료로 보고하지 않는다.

### 의존 관계와 병렬 설계

- 탑다운은 상위 계약에서 하위 책임을 도출하는 방식이지 A 구현 완료 → B 설계 → C 설계의 직렬 작업 순서가 아니다. 아래 경계 계약을 공통 기준으로 두고 A·B·C의 설계를 병렬로 진행할 수 있다.
- B의 숫자 저장은 실제 증감 실행·통합 검증의 선행 조건이다. C의 설계가 B의 구현 완료를 기다려야 한다는 뜻은 아니다. 연결 검증에서는 실제 숫자 저장의 성공을 확인한다.
- A·B·C는 기존 두 실행 파일 안의 책임 구분이다. 구체적인 보조 함수나 새 모듈을 필요성 확인 전에 만들지 않는다.

## 병렬 설계용 공통 계약

### 호출과 반환의 연결

HTTP는 해석된 입력을 아래 저장소 호출로 전달한다. 저장소는 HTTP 상태가 아닌 결과 딕셔너리만 반환하고, HTTP는 그 결과를 응답 본문으로 연결한다. 정상적인 명령은 결과를 반환하기 전에 처리를 끝낸다.

| 외부 요청 | 저장소 호출 | 저장소 정상 반환 → HTTP 응답 |
| --- | --- | --- |
| `PUT /kv`, 본문 `key`·`value` | `set(key, value)` | `{"ok": True}` → 200 |
| `GET /kv`, 쿼리 `key` | `get(key)` | `{"found": True, "value": ...}` 또는 `{"found": False}` → 200 |
| `DELETE /kv`, 쿼리 `key` | `delete(key)` | 삭제 직전 `{"found": True, "value": ...}` 또는 `{"found": False}` → 200 |
| `POST /kv/incr`, `key`·`amount`만 | `incr(key, amount)` | `{"ok": True, "value": 변경직후수치}` → 200 |
| 위 요청에 `maximum` 포함 | `incr(key, amount, maximum=전달받은내용)` | 같은 성공 반환 → 200 |
| `POST /kv/decr`, `key`·`amount`만 | `decr(key, amount)` | `{"ok": True, "value": 변경직후수치}` → 200 |
| 위 요청에 `minimum` 포함 | `decr(key, amount, minimum=전달받은내용)` | 같은 성공 반환 → 200 |

- `key`, `value`, `amount`와 선택 조건은 변환하지 않는다. 실제 `null`은 Python `None`으로 전달한다.
- 조건 필드가 없으면 해당 키워드 인자를 전달하지 않는다. 조건 필드가 있으면 내용이 `None`이어도 전달하며 저장소에서 타입 오류로 거절한다. `None`을 생략 기본값으로 사용해 두 상태를 합치지 않는다.
- `amount`는 필수이며 HTTP나 저장소가 임의의 기본 증감량을 넣지 않는다. `maximum`·`minimum`은 선택 키워드 인자다.
- 조건 생략을 내부에서 어떤 객체로 표시할지는 구현 세부사항이다. 다른 범위는 생략된 호출과 명시적 `None` 호출이 다르게 판정된다는 계약만 의존한다.

### A와 B·C 사이의 검증 책임

- A: JSON 해석, 객체 형태의 본문, 필수 필드 존재, 증감의 허용 필드 검사를 한다. 이 단계에서 거절하면 저장소를 호출하지 않는다. 입력 오류는 400과 `{"error":"INVALID_INPUT"}`이다.
- B·C: HTTP 없이 직접 호출되어도 키·자료형·크기와 해당 연산의 입력 규칙을 검사한다. HTTP는 이 검증을 복제하거나 저장된 value를 사전 조회하지 않는다.
- B: JSON 전체 자료형을 보관하고 조회·삭제에서 타입과 내용을 유지한다. 키는 문자열 1~256 UTF-8 바이트, value는 통합 결론의 자료형별 64KiB 기준을 따른다.
- C: 키 → 증감량 → 지정 조건 → 대상 존재 → 저장된 숫자 타입 → 계산 결과 표현·크기 → 계산 결과 조건 순서로 판정한다. 먼저 발견한 오류 하나만 반환한다.
- A·B·C 모두 입력을 문자열이나 숫자로 자동 변환하지 않는다. 불리언과 숫자를 구분한다.

### 저장소 실패 반환 → HTTP 연결

| 저장소 결과 딕셔너리 | HTTP 상태 | 적용 |
| --- | --- | --- |
| `{"error":"INVALID_INPUT"}` | 400 | 잘못된 키, set의 지원하지 않는 value·크기 초과 등 |
| `{"error":"TYPE_MISMATCH","field":...,"actual_type":...}` | 400 | 증감의 숫자가 아닌 대상·증감량·조건 |
| `{"error":"NEGATIVE_AMOUNT"}` | 400 | 음수 증감량 |
| `{"error":"NOT_FOUND"}` | 404 | 없는 대상의 증감. get·delete의 정상적인 없음과 구분 |
| `{"error":"OUT_OF_RANGE"}` | 422 | 증감의 표현 범위 위반·계산 결과 크기 초과 |
| `{"error":"CONDITION_NOT_MET","value":현재수치}` | 409 | 계산 결과의 상한·하한 위반 |

- 타입 오류의 `field`는 `value`·`amount`·`maximum`·`minimum`, `actual_type`은 해당 JSON 타입 이름이다. 필드 외의 상세 정보는 API 명세에 정한 범위를 넘겨 추가하지 않는다.
- 예상하지 못한 예외는 정상적인 실패 딕셔너리로 삼키거나 입력 오류로 바꾸지 않는다. HTTP 경계에서 500과 `{"error":"INTERNAL_SERVER_ERROR"}`로 연결하며 내부 상세는 노출하지 않는다. 500은 상태 미변경 보장이 아니다.

### 공유 상태와 완료 시점

- 한 `MiniRedis` 인스턴스의 기존 `_data`를 함께 사용한다. #1과 02에 별도 저장 상태를 만들지 않는다.
- `set`·`incr`·`decr`는 모든 정상 검증을 끝낸 뒤 상태를 변경한다. 정상적인 거절이면 대상·다른 키를 포함한 전체 상태를 보존한다.
- `incr`·`decr`는 읽기부터 결과 저장까지 한 번의 호출 안에서 완료한다. A는 반환을 받은 뒤 성공 응답을 생성한다. 반환 후 다른 요청이 처리될 수 있으므로 반환 수치의 지속적인 최신성은 보장하지 않는다.
- 현재 단일 프로세스·순차 처리 서버가 각 요청을 하나씩 실행한다. 별도 큐·소비자나 저장소 직접 다중 스레드 안전성을 전제하지 않는다.

### 병렬 설계에서 확정하지 않는 사항

- 배열·객체를 직접 호출로 주고받을 때 원본·조회 결과 변경의 전파, 구체적인 숫자 표현 범위, 깊은 중첩 한계는 미정이다. 관련 동작을 임의로 가정하거나 완료했다고 보고하지 않는다.
- 위 미정 항목을 제외한 정상 자료형·크기·증감·조건·실패 흐름은 공통 계약에 맞춰 설계할 수 있다. 다른 범위가 먼저 구현됐다는 가정은 필요하지 않다.

```python
        # 하한이 생략되면 storage.decr(key, amount)
        # 하한이 존재하면 storage.decr(key, amount, minimum=하한)
        # 명시적인 null도 그대로 전달해 숫자 타입 오류로 판정
        # 반환 결과를 HTTP 응답으로 연결
        ...

    # 기존처럼 Flask 앱 반환
```

HTTP는 문자열을 숫자로 재해석하거나 직접 증감하지 않는다. 성공은 200과 `{"ok":true,"value":...}`, 실패는 REST API 명세의 오류 코드별 HTTP 상태와 JSON 형식으로 연결한다. 예상하지 못한 오류를 입력 오류로 바꾸지 않는다.

## 2. 저장소의 공개 함수 — `storage.py`

```python
class MiniRedis:
    def __init__(self):
        self._data = {}  # 기존 인스턴스별 저장 상태 유지

    def set(self, key, value):
        # 키: 문자열 1~256 UTF-8 바이트 확인
        # value: JSON 자료형과 중첩 내용의 유효성 확인
        # 자료형별 크기 기준으로 64KiB 이하인지 확인
        # 거절이면 INVALID_INPUT 반환, 전체 상태 유지
        # 검증이 끝난 뒤 지정한 키에 저장 → {"ok": True}
        ...

    def get(self, key):
        # 기존 키 검증과 없음 구분 유지
        # 있으면 {"found": True, "value": ...}
        # 없으면 {"found": False}
        # 상태를 변경하지 않음
        ...

    def delete(self, key):
        # 기존 키 검증과 없음 구분 유지
        # 있으면 삭제 직전 value를 확보하고 해당 키 삭제
        # {"found": True, "value": ...} 또는 {"found": False}
        ...

    def incr(self, key, amount, *, maximum=...):
        # 키 → 증감량 → 지정된 상한 순으로 입력 검증
        # 대상 키 존재 → 대상 value의 숫자 타입 확인
        # 결과 = 현재 value + amount
        # 결과 표현 가능 여부와 크기 확인
        # 상한을 지정했다면 결과 <= 상한 확인
        # 실패: 상태 보존, 해당 실패 결과 반환
        # 성공: 해당 키에 결과 저장, 변경 직후 value 반환
        ...

    def decr(self, key, amount, *, minimum=...):
        # 키 → 증감량 → 지정된 하한 순으로 입력 검증
        # 대상 키 존재 → 대상 value의 숫자 타입 확인
        # 결과 = 현재 value - amount
        # 결과 표현 가능 여부와 크기 확인
        # 하한을 지정했다면 결과 >= 하한 확인
        # 실패: 상태 보존, 해당 실패 결과 반환
        # 성공: 해당 키에 결과 저장, 변경 직후 value 반환
        ...
```

- `amount`는 필수 증감량 인자다. 숫자이면서 0 이상이어야 하며 불리언은 숫자로 허용하지 않는다.
- `maximum`·`minimum`은 선택 조건의 키워드 인자다. 기본값의 `...`는 이 문서에서 **생략을 나타내는 임시 표기**다. 실제 코드에서 생략을 표현할 방법은 고정하지 않으며 `None`을 생략으로 취급하지 않는다.
- `incr`·`decr`는 읽기부터 저장까지 한 번의 호출에서 끝낸다. 외부에서 `get`·`set`을 여러 번 호출하는 방식으로 조합하지 않는다.
- 조건 불충족은 판단 시점의 현재 `value`를 반환하고 저장하지 않는다. 타입 오류는 잘못된 부분과 실제 타입을 알린다. 표현 범위 초과는 조건 불충족과 구분한다.
- 이 단계에서는 중복 제거를 위해 공통 연산 함수나 검증 함수를 새로 확정하지 않는다. 실제 본문을 구체화할 때 필요한 최소 범위를 판단한다.

## 3. `set`의 자료형·크기 처리

HTTP에서 해석한 문자열·숫자·불리언·실제 `null`·배열·객체를 그대로 다룬다. 중첩 내용도 JSON 자료형이어야 하며 객체 필드 이름은 문자열이다. `NaN`·무한대·순환 참조는 지원하지 않는다.

1. 최상위 문자열은 기존 `len(value.encode("utf-8"))` 기준을 유지한다.
2. 최상위 실제 `null`은 기존 0바이트 기준을 유지한다.
3. 나머지는 `json.dumps(value, ensure_ascii=False, separators=(",", ":"), allow_nan=False)` 결과의 UTF-8 바이트 수로 계산한다.
4. 65,536바이트까지 허용한다. 초과하면 새 항목을 만들거나 기존 내용을 덮어쓰지 않는다.

JSON 표현 생성은 크기 측정용이다. 실제로 JSON 문자열을 저장하는 것으로 바꾸지 않는다. 표준 JSON 변환기가 일부 Python 타입이나 문자열 아닌 객체 키를 자동 변환할 수 있다는 이유로 지원 대상에 포함하지 않는다.

## 4. 연결해서 확인할 흐름

- #1: `put_kv` → `MiniRedis.set` → `get_kv`·`delete_kv`로 자료형과 내용을 확인한다.
- 시나리오 02: 숫자 value를 `set`으로 준비 → `incr_kv`·`decr_kv` → `MiniRedis.incr`·`MiniRedis.decr` → 결과 응답·조회로 확인한다.
- 실패: 요청 형식 → 입력 검증 → 키 존재 → 저장된 타입 → 계산 결과 표현 가능 여부 → 조건 순서 중 처음 발견한 실패를 확인한다.
- 동시 요청: 현재 단일 프로세스·순차 처리 서버로 실제 외부 요청을 보내 각 응답과 최종 상태를 확인한다. 저장소 직접 다중 스레드 안전성으로 확대하지 않는다.

아직 구현되지 않은 사항을 동작한다고 보고하지 않는다. 외부 요청·응답은 REST API 명세에 반영한 계약을 따른다. 숫자 저장을 위한 기존 테스트 계약 변경, 배열·객체를 직접 호출로 주고받을 때의 변경 전파와 구체적인 숫자 범위는 해당 계약을 확정한 범위에서 테스트·구현한다.
