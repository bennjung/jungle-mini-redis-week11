# 시나리오 03 구현·실행·분석 기록

## 상태

- 사용자 승인: JMeter 설계 구현과 실제 테스트 실행. 구현 담당은 CommandCode의 DeepSeek V4.1 Flash 하위 에이전트이며, 결과 분석·최종 판정은 메인 에이전트가 수행한다.
- 기준: [성능 비교 계약](03-performance-scenario.md), [JMeter 테스트 설계](03-jmeter-test-design.md).
- JMeter 실행 계획·조율·집계·도구 검증을 구현했다. 파일럿에서 추가 확인한 전체 마감 경계도 회귀 수정했고, 메인의 최종 도구 검증은 **83 통과·0 건너뜀**이다. 확정 조건의 실행은 아래 단계별 실제 결과를 따른다. 기존 기능 검증을 S3-01·S3-02 완료로 세지 않는다.
- 파일럿 후 N·시간 한도를 확정하고 본 측정하는 승인 절차는 유지한다. 예비 실행 수치를 확정된 성능 비교 결과로 제시하지 않는다.

## 실행 환경 준비

- 호스트: Linux `7.3.3-1-cachyos-bore`, x86_64, AMD Ryzen 7 7840HS, 논리 CPU 16개, `/proc/meminfo` 총 메모리 31,496,500KiB. 다른 작업과 CPU 주파수 변동을 완전히 통제한 전용 장비가 아니다.
- 기존 시험 환경: Python 3.14.10, pytest 9.2.0, Flask 3.1.3, Werkzeug 3.1.9. 프로젝트의 전역 의존성은 바꾸지 않는다.
- 설치된 Werkzeug 소스에서 응답마다 `Connection: close`를 설정함을 확인했다. 이번에 시작한 기존 `app.py` 서버의 실제 GET 응답에서도 HTTP 200과 `Connection: close`, `Werkzeug/3.1.9 Python/3.14.10`을 확인했다. JMeter에서 객체 재사용을 TCP 재사용으로 보고하지 않는다.
- 호스트의 `mysql` 명령은 MariaDB 13.0.2 클라이언트다. 이를 MySQL 기준선으로 대체하지 않으며 별도 MySQL 8.4 시험 컨테이너를 준비한다. 사용자 DB를 사용하거나 변경하지 않는다.
- JMeter 5.6.3은 공식 배포 파일과 Apache SHA512를 대조했다. Connector/J 9.2.0은 Maven Central 배포의 SHA1과 대조했으며, 로컬 SHA256은 `7e9941bbdcca244d878ea95bfff788fd9ba6a65af757f24be6c632930d61c7ed`다. Maven 해당 경로는 SHA256 검증 파일을 제공하지 않아 404였음을 구분한다.
- 도구·원자료·시험 비밀은 `/tmp/opencode/` 아래에 두며 인증정보는 이 문서나 저장소에 기록하지 않는다. MySQL 데이터의 실제 저장 위치·내구성 설정은 컨테이너 준비 후 별도로 기록한다.
- JRE 배포 조회의 첫 공급자 API가 403을 반환했다. 같은 경로를 반복 요청하지 않고 공식 Eclipse Temurin 컨테이너 배포로 준비 경로를 변경했다.
- JRE는 공식 Eclipse Temurin 이미지의 17.0.21+9를 사용한다. 배포 이미지 식별자는 `sha256:0b6521287f850ec1c4b31c9074c5a1ae1d67c5922c3fefd21065c7c32e244d4a`다. 실행 파일은 시스템 설치 없이 시험 도구 위치로 추출했다.
- MySQL 서버는 공식 `mysql:8.4` 이미지의 8.4.13이다. 이미지 식별자는 `sha256:a81d043930e51745522bd5c430961cf8286f0a23f0a9a2a6e0108f7ea71b0902`다. 로컬 루프백에만 공개한 별도 포트·시험 전용 DB를 사용하며, 실제 DB 데이터는 Docker의 별도 볼륨에 저장한다. 메모리 임시 DB로 바꾸지 않았다.
- 확인한 MySQL 설정: `autocommit=1`, `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, `log_bin=1`, `transaction_isolation=REPEATABLE-READ`, `innodb_buffer_pool_size=134217728`, `max_connections=151`, `innodb_lock_wait_timeout=50`, `performance_schema=ON`. 성능을 위해 내구성 설정을 낮추지 않았다.
- JMeter 버전 실행은 성공했다. 실행 시 플러그인 패키지 탐색의 향후 지원 중단 경고가 출력되며, 이를 시험 실패나 결과 검증 통과와 혼동하지 않는다.

## 구현 검토와 회귀 보완

- 구현 담당이 1차 구현 뒤 보고한 HTTP 중심 도구 검증은 46 통과·1 건너뜀이다. 당시 실제 JDBC 검증은 미완료였다. 이 결과를 양쪽 검증 완료로 확대하지 않았다.
- 메인 코드 검토에서 응답 반환과 마감 판정의 경쟁, 전체 요청 완료 후 남은 전체 한도 예약, SQL 쿼리 제한의 서버 취소 의미, 최종 수치의 소수 절단, 나노초 정수의 부동소수 변환, 시간 기록 검산, 결과 폴더 변경으로 미해결 표식을 우회하는 문제를 확인했다.
- 같은 하위 에이전트가 실패 회귀를 먼저 추가하고 이를 수정했다. 결과 폴더와 독립적인 필수 `--state-dir`와 원자적 잠금, 마감 이후 늦은 응답 불변, 정확한 수치 비교, 단조 시계 검산을 보완했다.
- 실제 JDBC를 위해 시험 전용 테이블만 명세 SQL로 생성했다. Connector/J의 쿼리 제한을 0으로 두고 통신 연결·읽기 제한을 명시한다. 자동 재연결은 사용하지 않는다.
- 하위 에이전트는 보완 후 실제 JMeter·MySQL 포함 77 통과를 보고했다. **메인이 동일 명령으로 별도 실행하여 77 통과·0 건너뜀, 189.25초를 확인했다.** 메인 실행 JUnit 원자료는 `/tmp/opencode/m3-main-verification.xml`이다.

- M3-01~18을 다루며 리뷰에서 추가한 마감·정밀도·표식 회귀를 포함한다. 실패를 의도한 시험이 통과했다는 것은 실패를 정확히 분류했다는 뜻이지 실패한 요청을 성공으로 처리했다는 뜻이 아니다.

- 강제 종료 후의 처리 여부 불명확·기록 유실을 통과로 만들지 않도록 검증했지만, 운영 서버의 취소·복구 보장을 추가한 것은 아니다. DB 연결 종료는 시험 계정이 볼 수 있는 자기 연결 범위에서 확인했다.

## 메인 직접 실행: 사전 정확성 확인

- Mini Redis 기존 `app.py` 서버에 N=100, C=100으로 실제 JMeter 요청을 보냈다. 한도는 사전 확인 입력으로 요청 5초·전체 60초·준비 30초·종료 15초를 사용했다. 이는 아직 본 측정 확정 수치가 아니다.
- 결과: 실제 시도 100·성공 100·실패/시간 초과/미완료 0·최종 숫자 100, JTL·정규화 기록·완료 표식 검산 통과.
- C=100은 최대 동시 실행 설정이다. 호출 시각으로 계산한 이번 최대 진행 수는 72였다. 설정 수와 실제 관찰 수를 혼동하지 않는다. 이 짧은 정확성 실행의 지연·처리량을 정식 성능 비교로 제시하지 않는다.
- 원자료: `/tmp/opencode/m3-main-results/precheck-http/`, 요약 `/tmp/opencode/m3-main-precheck-http.json`.

## 후속 실행 기록

### MySQL 사전 정확성 확인

- N=100, C=100으로 실제 MySQL/JDBC를 실행했다. 시도100·성공100·최종 수치100, 산출물 검산 통과. 원자료는 `/tmp/opencode/m3-main-results/precheck-jdbc/`다.
- 양쪽 사전 확인은 통과했지만 한도는 예비 입력이다. 파일럿 후 확정한 조건의 S3-01·S3-02를 대체하지 않는다.

### N=1,000 파일럿: 양쪽·모든 동시성 완료

요청5초·전체120초·준비30초·종료15초를 예비 입력으로 사용했다. 각 대상·조건 **1회**이며 순서는 C별 Mini Redis → MySQL이다. 본 측정의 5회 교차 반복과 구분한다.

| 동시성 | Mini Redis 성공 처리량(건/초) | MySQL 성공 처리량(건/초) | Mini Redis p95(ms) | MySQL p95(ms) | Mini Redis p99(ms) | MySQL p99(ms) |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 942.22 | 64.51 | 1.634 | 17.980 | 2.417 | 22.350 |
| 10 | 1,794.83 | 82.76 | 7.842 | 138.824 | 8.778 | 155.839 |
| 50 | 1,745.87 | 82.32 | 40.709 | 677.784 | 46.117 | 696.646 |
| 100 | 1,696.31 | 81.50 | 85.248 | 1,323.546 | 95.217 | 1,348.025 |

- 전체 8개 실행에서 실제 시도 1,000·성공 1,000·실패/시간 초과/미완료 0·최종 수치 1,000을 확인했다. MySQL의 연결 식별은 C개 각각 전후 일치했다. C=1/10/50/100에서 관찰한 최대 진행 수도 각각 1/10/50/100이었다.
- 원자료와 묶음 요약: `/tmp/opencode/m3-main-results/pilot-1000/`, `/tmp/opencode/m3-main-results/pilot-1000-cli.json`.

### N=10,000 파일럿: 전체 한도 때문에 중단

- Mini Redis C=1은 10,000건 모두 성공·최종10,000, 전체 측정6.369초, 성공 처리량1,570.14건/초, p95=0.971ms, p99=1.511ms였다.
- 다음 MySQL C=1은 **예비 전체 한도120초에 도달**했다. 시도7,992건 중 성공7,991·미완료1로 기록됐고, 늦게 반환한 요청도 실제 반영되어 종료 후 관찰 수치는7,992였다. 나머지2,008건은 보내지 않았다.
- N=1,000에서 측정한 MySQL C=1 처리량64.51건/초를 적용하면 10,000건은 약155초가 필요하다. **메인이 예비 실행에 둔120초는 부족했다.** 이 결과를 MySQL이 10,000건을 처리할 수 없다는 결론이나 요청별5초 시간 초과로 해석하지 않는다.
- 묶음은 중단했고 C=10/50/100의 양쪽6개 실행은 미실행으로 기록했다. 실패 회차를 지우거나 한도를 몰래 늘려 재실행하지 않았다. 원자료: `/tmp/opencode/m3-main-results/pilot-10000/`와 `pilot-10000-cli.json`.
- 실패 표식 `/tmp/opencode/m3-main-state/.state/20261114T012545-jdbc-c1-r1.json`은 유지한다. 기록 변경 없이 서버를 조회하여 해당 연결3543이 사라졌고, 시험 계정 연결·활성 트랜잭션이 없음을 확인했다. 다음 초기화는 수행하지 않았다. 이 확인을 근거로 재개 승인 시에만 기존 실패 기록을 보존하고 표식을 해제할 수 있다.

### 중단 경계에서 발견한 측정 도구 오류

- 전체 마감은 `56085726372658ns`였지만 `beginCall`이 이를 직접 검사하지 않고 감시 콜백의 중단 신호만 확인했다. 콜백이 늦게 실행되는 사이 요청7,992를 `56085736322616ns`에 허용했다.
- 뒤늦은 콜백이 해당 기록의 결정 시각을 전체 마감으로 소급하면서 **결정 시각이 시작보다 이른 기록**을 만들었다. 요청7,991도 전체 마감 이후 응답을 성공으로 셌다. 산출물 검산은 이 문제를 정상 완료로 통과시키지 않았다.
- 메인이 원자료·실제 코드로 원인을 확인하고 같은 하위 에이전트에 진입/복귀 양쪽의 실제 마감 검사와 콜백 지연 회귀를 맡겼다. 원래 실패 기록은 수정하지 않는다. 이 오류의 존재 때문에 중단 실행에서 계산한 부분 처리량을 정상 성능 지표로 제시하지 않는다.
- 수정 후 전체 마감을 지난 호출은 생성하지 않으며, 반환 판정도 요청별 마감과 전체 마감 중 앞선 시각을 적용한다. 콜백을 의도적으로 늦춘 격리 회귀에서 이전의 ‘총한도 후 시작·결정이 시작보다 이전’ 패턴을 재현한 뒤 차단을 확인했다. 연결 식별 후조회도 전체 측정 결정 완료 장벽 뒤로 옮겨 다른 측정 요청과 겹치지 않게 했다.
- 메인이 이 경계와 후조회 장벽 회귀6개를 실행해 **6 통과·77 선택 제외, 49.88초**를 확인했다. 이후 실제 HTTP/JDBC를 포함한 전체 수정본을 다시 실행해 **83 통과·0 건너뜀, 239.16초**를 확인했다. 원자료: `/tmp/opencode/m3-main-deadline-regression.xml`, `/tmp/opencode/m3-main-final-verification.xml`.

## 메인 예비 분석: 본 측정 전 당시의 판단

1. **정확성:** N=1,000의8개 예비 실행에서는 증가분 보존과 성공률100%를 확인했다. 실패가 포함된10,000건 MySQL 실행은 같은 통과 조건을 충족하지 않았다.
2. **현재 구성의 성능 차이:** N=1,000 예비 실행에서 Mini Redis 처리량은 MySQL보다 약14.6~21.7배 높게 관찰됐다. 1회 예비 실행의 관찰이지 5회 반복 결과나 모든 저장소 작업의 우위가 아니다. HTTP/드라이버 경로와 메모리 반영/디스크 내구성 보장이 다르다.
3. **동시성을 늘린 효과:** 양쪽 모두 C=10 이후 처리량이 거의 늘지 않았고 p95·p99는 커졌다. 예를 들어 C=10→100에서 Mini Redis p95는7.842→85.248ms, MySQL은138.824→1,323.546ms다. 동시에 대기하는 요청 수를 늘려도 성공 처리량이 비례하지 않는 조건을 찾았다.
4. **병목 원인은 미확정:** JDBC 기본 지연 중앙값과 첫 응답 지연도 비슷했고 연결 확보 시간은 기본 밀리초 기록에서0으로 나왔다. 0은 측정 해상도 아래일 수 있으므로 연결 비용이 없다고 단정하지 않는다. SQL 문장·행 잠금·디스크 기록의 세부 분리는 아직 하지 않았다. 설정이 내구성 대기를 포함한다는 사실만으로 그것이 단독 원인이라고 주장하지 않는다.
5. **CPU 부분 관찰:** MySQL C=100 측정 구간 일부에서29개 표본을 얻었다. 평균 MySQL CPU15.5%, JMeter Java 합계20.4%였고100%는 논리CPU1개다. 이 구간에서 전체 CPU 포화를 관찰하지는 않았지만, 전 구간·모든 CPU 제한 원인을 배제하는 증거는 아니다. 표본은 `/tmp/opencode/m3-pilot-cpu-samples.json`에 보존한다.
6. **N=1,000의 한계:** Mini Redis 측정은 약0.56~1.06초로 짧다. C=1의10,000건 결과와도 처리량 차이가 보여 실행 길이·초반 준비·변동의 영향을 확인할 필요가 있다. 짧은 실행 한 번만으로 대표 성능을 확정하지 않는다.
7. **남은 일:** 전체 마감 경계 수정·회귀 재검증, 승인된 재개 절차와 표식 정리, 고정 조건 S3-01 재확인·파일럿 재확인 및5회 본 비교. 서버 내부 상세 진단 계측은 별도 미구현 범위다.

## 최종 분석: 메인 에이전트 판단

1. **현재 구성의 사용 성능 차이는 관찰됐다.** 같은 카운터의 증가분을 보존하고400,000건 모두 성공한 조건에서 Mini Redis의 성공 처리량 중앙값은 MySQL보다 약23.9~31.2배 높았다. 동일 내구성의 저장소 연산끼리의 비교나 모든 작업의 성능 우위로 일반화하지 않는다.
2. **동시성10 이후에는 요청을 더 겹쳐도 처리량이 늘지 않았다.** Mini Redis는 C=10에서 약2,582건/초, C=100에서 약2,483건/초였다. MySQL은 같은 구간에서 약82.65→82.23건/초였다. 반면 p95는 각각 약5.835→52.651ms, 134.819→1,322.698ms로 커졌다. 이번 입력에서 C를100으로 늘리는 것은 성공 처리량보다 대기 지연을 주로 늘렸다.
3. **MySQL의 낮은 CPU 사용은 시험 정지를 뜻하지 않았다.** 실행 중 잠금 대기 관계와 변경 확정 대기를 직접 관찰했고, 기록 파일은 계속 갱신됐다. 같은 행의 쓰기 경합은 실제 관찰된 현상이다. 조회된 `updating` 상태를 CPU에서 계속 계산한다는 뜻으로 해석하지 않는다.
4. **변경 확정과 디스크 보존 비용을 제외하지 않았다.** MySQL은 `log_bin=1`·`sync_binlog=1`·`innodb_flush_log_at_trx_commit=1`이다. 관찰 기준점 이후 서버 전역 누적 차이에서 행 잠금 대기181,763회·잠금 대기 합계114,707,419ms와 로그 동기화345,095회를 확인했다. 이는 파일럿 일부와 본 측정 전체를 포함하는 집계이며 특정 회차 전용이 아니다. 여러 요청의 대기 합계는 벽시계 시간보다 클 수 있다. 동기화 횟수만으로 요청 지연 중 디스크 비중을 계산하지 않는다.
5. **Mini Redis는 같은 장애 보장을 제공하지 않는다.** 메모리 반영과 성공 응답은 확인했지만 재시작 후 데이터 보존은 보장하지 않는다. 따라서 이번 수치는 ‘이 구현과 현재 MySQL 구성의 외부 사용 경로’ 차이다. 내구성이 필수인 재고·결제 등의 작업에서 이 수치만 보고 DB를 대체하도록 권장하지 않는다.
6. **기본 비교의 완료와 개선 작업은 구분한다.** 합의한 정확성·부하·반복 조건의 비교는 완료했다. 제품 서버나 저장소를 최적화한 것은 아니다. 개선 전후 성능 향상을 입증했다고 보고하지 않는다.
7. **다음 원인 조사 범위는 좁힐 수 있다.** Mini Redis는 C=10 이후의 전체 경로 포화에서 통신·순차 요청 처리·클라이언트 계측의 기여를 별도 진단할 수 있다. MySQL은 관찰한 동일 행 잠금과 변경 확정 대기를 출발점으로 구간별 시간을 확인할 수 있다. 제품 내부 상세 계측과 디스크 대기 비율은 아직 미검증이며, 비교 결과에 맞추어 서버 모델이나 내구성을 몰래 바꾸지 않는다.
8. **한계:** 고정 동시성·같은 키·정수1 증가의 로컬 시험이다. 일정 도착률의 과부하 수용 한계·혼합 읽기/쓰기·다중 키·장애 복구·시나리오04 응답 캐시 성능은 검증하지 않았다. 5회 중앙값·범위만으로 통계적 유의성을 주장하지 않는다.

### 결과 해석의 추가 제한과 후속 작업 보류

- 결과 검토 뒤 사용자와 측정의 한계를 재검토했다. 위의 ‘독립 재검산’은 메인 에이전트가 같은 검산 코드를 다시 실행했다는 뜻이다. 별도 도구로 독립 측정한 것이 아니며 공통 측정 오류를 배제하지 못한다.
- `M3Coordinator.beginCall()`·`markReturn()`은 공유 잠금을 얻은 뒤 시작·반환 시각을 기록한다. 기록 생성·감시 예약·잠금 대기의 영향이 개별 지연과 전체 처리량에 서로 다르게 반영될 수 있다. 상세 계측을 켠 경우와 끈 경우의 대조는 아직 수행하지 않았다.
- 따라서 처리량 정체를 서버 자체의 포화로 확정하지 않는다. 83개 검증과 400,000건 성공은 정확성·기록 일관성의 근거이지 측정의 무편향을 증명하지 않는다. 위 처리량 비율은 현재 계측 구성에서 관찰한 수치로 한정한다.
- 사용자 결정에 따라 계측 영향 검증·구간별 시간 진단·커널 큐와 사용자 공간 큐 비교·Redis 기준 비교는 [후속 이슈 #5](https://github.com/bennjung/jungle-mini-redis-week11/issues/5)에 남기고 보류한다. 새 큐 도입이나 추가 실험은 승인되지 않았다. 기존 큐 결정은 유지한다.

- 본 측정 이후 자신이 시작한 Mini Redis 시험 프로세스에만 종료 신호를 보내고 시험용 MySQL 컨테이너만 정상 정지했다. 사용자 서버·DB·기존 변경은 되돌리거나 삭제하지 않았다. 시험 데이터 볼륨과 로컬 증거는 보존했다.
- 정리 후 전체 기본 pytest를 다시 실행했다: `COUNTER_TEST_REPEAT=1 COUNTER_TEST_TIMEOUT=5`와 사용자 전용 비밀 파일 경로를 지정하여 **562 통과·29 건너뜀, 2.39초**. 건너뛴29개는 기본 실행에서 외부 JMeter/MySQL 실행을 명시적으로 켜지 않았기 때문이며, 별도 실제 도구 활성 실행에서는 전체83개를 이미0건 건너뜀으로 통과했다. 건너뜀을 새 통과로 더하지 않는다.
- 기본 전체 회귀 결과 XML: `/tmp/opencode/m3-final-default-suite.xml`. 기존 기능508개와 새 측정 도구83개의 실행 근거를 구분한다.
- 문서·수치 JSON·소스 해시 검산, 결과 인증정보 노출 검사, `git diff --check`를 통과했다. 완료 알림을 보냈다.
