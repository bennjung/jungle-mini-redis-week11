# 시나리오 03 — 서버 스택·무효화 성능 비교 실행 계획

## 1. 목적과 지위

- 목적: 같은 조건에서 (1) Flask와 FastAPI의 HTTP 스택 차이, (2) FastAPI에 TTL·무효화 기능을 더한 비용, (3) 실제 TTL 만료·active 정리 작업이 핫 경로에 주는 영향을 관찰한다.
- 이 문서는 **실행 계획**이다. [03 성능 비교 계약](03-performance-scenario.md)의 S3-01·S3-02 조건과 기존 결과를 바꾸지 않는다. 새 시나리오 S3-03A·S3-03B의 상세 계약은 [승인된 제안](03-invalidation-performance-proposal.md)을 따른다.
- **MySQL은 사용자 결정으로 제외한다.** 기존 MySQL 결과는 역사 기록으로 보존하고 새 비교표에 넣지 않는다.
- 이 문서는 이전 4대상(MySQL·Flask·FastAPI·FastAPI+timer) 계획을 대체한다. 이전 계획의 T4 정의는 이번 B(FastAPI + TTL·무효화·타이머)로 구체화됐다.

## 2. 비교 대상

| ID | 이름 | `app.py` | `storage.py` | 실행 |
| --- | --- | --- | --- | --- |
| F | Flask 기준선 | `e61a81a` | `ce427a2` | Flask 3.1.3/Werkzeug 3.1.9, `threaded=False`, `127.0.0.1:5000` |
| A | FastAPI 기준선 | `ce427a2` | `ce427a2` | FastAPI 0.162.7/uvicorn 0.54.0, `workers=1`, `127.0.0.1:5000` |
| B | FastAPI + TTL·무효화 | `c5df702` (실행 시 고정) | `c5df702` | A와 같고 lifespan 100ms active 만료 타이머 포함 |

- F와 A는 같은 `storage.py`를 써서 HTTP 계층 차이만 본다.
- B만 TTL 저장소를 쓴다.
- 세 대상 모두 Python 3.14.10. F는 별도 Flask 측정 환경, A·B는 프로젝트 `.venv`.
- 한 번에 한 서버만 5000 포트에서 실행한다. 서버 시작·종료는 측정 밖이다.

## 4. 비교 묶음

### 4.1 S3-02 카운터 — F/A

- 기존 `counter.jmx`·`counter.groovy`·`run_performance.py` 경로를 그대로 쓴다.
- 2 대상 × 4 C × 5회 = **40회**.
- 홀수 회차 F→A, 짝수 A→F. 5회는 완전 균형이 아니다.

### 4.2 S3-03A 캐시 수명주기 — F/A/B

- 새 `invalidation.jmx`의 `cache_lifecycle` 분기.
- 4,000개 공유 키: GET hit 4,000 → DELETE 2,000 → GET miss 2,000 → PUT refill 2,000 = 10,000요청.
- 3 대상 × 4 C × 5회 = **60회**.
- 단계별 op 지표와 전체 지표를 함께 집계한다.
- 만료는 없다. "수동 무효화 경로의 TTL 부기 비용"으로 한정한다.

### 4.3 S3-03B 콜드 키 만료 백로그 — A/B

- 새 `invalidation.jmx`의 `expiry_backlog` 분기.
- 콜드 키 10,000개를 TTL 5초로 채우고, 마지막 저장 뒤 6초 대기한다.
- 핫 키 GET 10,000건. B는 active 정리, A는 TTL 무시로 방치.
- 2 대상 × 4 C × 5회 = **40회**.
- A↔B 기능 비교이며 3자 동일 시나리오가 아니다.

## 5. 실행 순서와 비용

- C=`1`·`10`·`50`·`100` 순서.
- 각 C에서 회차마다 대상 순서를 회전한다.
  - F/A: 홀수 F→A, 짝수 A→F.
  - F/A/B: 1회 F→A→B, 2회 A→B→F, 3회 B→F→A, 4회 F→A→B, 5회 A→B→F. 완전 균형이 아님을 기록.
  - A/B: 홀수 A→B, 짝수 B→A.
- 총 **140회**. HTTP만 실행하므로 이전 MySQL 포함 campaign(47분 39초)보다 짧을 것으로 예상하지만, 예상 시간을 결과로 제시하지 않는다.
- 각 실행은 서버 시작 → 준비 → JMeter → 서버 종료 순서. 서버 로그는 결과 폴더에 남긴다.

## 6. 하네스

| 산출물 | 책임 |
| --- | --- |
| `counter.jmx`·`counter.groovy`·`jmeter.properties` | 기존 카운터 경로. **동결** |
| `invalidation.jmx` | S3-03A/B 실행 구조·단계 장벽·op 샘플러 |
| `invalidation.groovy` | 시작 장벽·요청별 마감·op 판정·최종 상태·기록 |
| `invalidation.properties` | JTL 열·`m3_operation`·재시도 금지 |
| `run_invalidation.py` | 서버 시작·종료, 실행 단위, 산출물 검산, 5회 집계 |

- 기존 83개 측정 도구 검증은 카운터 경로를 바꾸지 않았으므로 유효하다.
- 새 하네스는 사전 확인과 본 측정 산출물 검산으로 검증한다.
- 상세 입력·성공 판정은 [승인된 제안](03-invalidation-performance-proposal.md) 4~7절을 따른다.

## 7. 사전 확인·파일럿

1. 소스 고정: F/A/B `app.py`·`storage.py`와 하네스 파일의 SHA256.
2. 환경 기록: 호스트·OS·CPU·메모리, Python·Flask·Werkzeug·FastAPI·uvicorn·JMeter·JDK.
3. F/A가 `PUT`의 `ttl`을 받아들이고 무시하는지, B가 TTL을 저장하는지 확인.
4. 소규모 기능 확인: 캐시 K=4/N=10/C=1, 캐시 K=40/N=100/C=10, 만료 콜드 K=10/N=10/C=1.
5. 전 규모 확인: 캐시 K=4,000/N=10,000을 A·B의 C=1과 B의 C=100, 만료 콜드 K=10,000/N=10,000을 B의 C=1.
6. 카운터 F/A N=100/C=1.
7. 위 확인이 통과하면 본 측정 140회를 실행한다. 사전 확인은 본 측정에 섞지 않는다.

- 파일럿은 새 시나리오의 소규모·전 규모 확인으로 대체한다. 별도 N=1,000 파일럿을 본 측정 5회에 섞지 않는다.
- 실패가 나오면 뒤 단계를 실행하지 않는다.

## 8. 결과·판정

- 대상별·C별·op별 5회 중앙값과 범위로 성공 처리량, p50·p95·p99, 성공률을 기록한다.
- 비교표:
  - S3-02: F/A 처리량·지연 차이.
  - S3-03A: F/A/B 및 op별 차이.
  - S3-03B: A/B 핫 경로 차이.
- 통과 판정은 정확성·측정 유효성만 한다. 성능 우열은 관찰로 서술하고 합격 기준으로 만들지 않는다.
- 실패 회차가 있으면 5회 요약을 만들지 않는다.
- S3-03B를 TTL 정확성·메모리 회수 근거로 사용하지 않는다.
- 기존 결과 파일·worklog 수치는 덮지 않는다. 새 결과 파일과 새 절을 추가한다.

## 9. 하지 않는 것

- MySQL 비교·재측정. 기존 결과는 역사 기록으로만 둔다.
- 제품 API·저장소 계약·응답 필드 변경, 성능 전용 API 추가.
- Flask를 운영 스택으로 되돌리는 것.
- 03 계약의 N·시간 한도·반복 횟수 변경.
- S3-03B를 3자 동일 시나리오로 표현하는 것.
- 분산 부하, 대시보드, 상시 추적.

## 10. 리스크와 한계

- Flask 개발 서버와 uvicorn은 배포 모델이 다르다. "각 스택의 현재 단일 워커 구성"이며 순수 프레임워크 비교가 아니다.
- Werkzeug의 연결 종료와 uvicorn의 지속 연결 차이가 측정 경로에 포함된다.
- S3-03A는 TTL 만료를 피한다. "차이 없음"을 "TTL 비용 0"으로 단정하지 않는다.
- S3-03B의 차이는 active 정리와 콜드 키 집합 축소가 합쳐진 값이다. 하위 비용을 개별 분해하지 않는다.
- 5회 중앙값·범위는 통계적 유의성을 입증하지 않는다.
- 기존 계측 영향 미검증 한계(후속 이슈 #5)가 그대로 적용된다.
