# 시나리오 03 — 서버 스택 4종 성능 비교 계획

## 1. 목적과 지위

- 목적: 같은 카운터 증가 작업을 네 대상에서 측정해 (1) 저장소·경로 차이, (2) 서버 스택 차이, (3) 타이머 비용을 같은 조건에서 관찰한다.
- 대상: ① MySQL, ② Flask, ③ FastAPI, ④ FastAPI + timer.
- 이 문서는 **실행 계획**이다. [성능 비교 계약](03-performance-scenario.md)과 [JMeter 테스트 설계](03-jmeter-test-design.md)의 계약을 바꾸지 않는다. S3-01·S3-02를 그대로 사용하며 새 시나리오 ID를 만들지 않는다.
- 이전 측정 상황을 그대로 재사용한다. N·동시성·시간 한도·반복·정확성·집계·실패 처리 규칙을 다시 합의하지 않는다.
- 실행 시점: 사용자가 실행을 요청할 때. 그 전까지 이 문서는 조건을 고정해 두는 용도다.
- 현재 상태: timer 미구현, TTL 저장소 미구현, Flask 기준선 환경 미설치, 측정 하네스 4대상 미지원. 이 계획은 승인 후 실행한다.

## 2. 재사용하는 확정 조건

| 항목 | 값 | 출처 |
| --- | --- | --- |
| 비교 작업 | 같은 카운터 `counter:one`에 `1` 증가, 증가 성공 확인 | S3-02 |
| 정확성 선행 | S3-01, N=100, C=100, 최종 `value`=100 | S3-01 |
| 본 측정 | N=10,000, C=`1`·`10`·`50`·`100`, 대상별·C별 5회 | S3-02 |
| 시간 한도 | 요청별 5초, 전체 360초, 준비 30초, 종료 15초 | 확정 |
| 워밍업 | 측정과 분리한 100건, C별 `100/C`건 | 설계 4절 |
| 클라이언트 | JMeter 5.6.3, HTTPClient4, closed-loop, 재시도 0 | 설계 3·5절 |
| MySQL | 8.4.13, Connector/J 9.2.0, 자동 커밋, 기존 내구성 설정 유지 | 설계 3절 |
| 집계 | 회차별 지표 → 5회 중앙값·최솟값~최댓값, p50·p95·p99 선형 보간 | 설계 8절 |

| 산출물 | JTL, 정규화 기록, 완료 표식, 묶음 요약, 원자료 보관 | 설계 11절 |

- 기본 판정은 정확성과 측정 유효성이다. 속도 우열은 판정이 아니라 관찰 결과다.
- 이전 결과의 수치·조건·한계 문장은 바꾸지 않는다. 새 측정은 새 결과 파일과 새 기록 절로 남긴다.

## 3. 대상 정의

| ID | 대상 | 소스 | 실행 방식 | 기록할 스택 |
| --- | --- | --- | --- | --- |
| T1 | MySQL | 기존 시험 전용 `benchmark_counter` | JDBC 직접 호출, HTTP 서버 없음 | MySQL 8.4.13, Connector/J 9.2.0 |
| T2 | Flask | `git show e61a81a:app.py` + 현재 `storage.py` | Flask 개발 서버, `threaded=False`, `use_reloader=False`, `127.0.0.1:5000` | Flask 3.1.3, Werkzeug 3.1.9 |
| T3 | FastAPI | 현재 `app.py` + 현재 `storage.py` | uvicorn `workers=1`, `127.0.0.1:5000` | fastapi 0.162.7, uvicorn 0.54.0 |
| T4 | FastAPI + timer | T3 + timer 브랜치 | T3와 같고 timer가 추가된 구성. 세부는 8절 | 3절과 동일 + timer 계약 |

- T2와 T3는 `app.py`만 다르고 `storage.py`는 같다. 측정 시 `storage.py` SHA256을 기록하고, 달라지면 같은 묶음에 섞지 않는다.
- 현재 `.venv`에는 Flask가 없다. T2는 고정 버전을 설치한 별도 측정 환경을 쓴다.
- 모든 HTTP 대상은 한 번에 하나만 `127.0.0.1:5000`에서 실행한다. 이전 서버를 종료하고 포트가 비었는지 확인한 뒤 다음 대상을 시작한다.
- Python은 세 HTTP 대상 모두 3.14.10을 쓴다. 버전이 다르면 새 환경 기록으로 새 묶음을 시작한다.
- T4의 정의는 아직 없다. 정의가 고정되기 전에는 T4를 측정하지 않는다.

## 4. 비교 축과 해석 규칙

| 비교 | 측정되는 차이 | 말할 수 있는 것 | 말할 수 없는 것 |
| --- | --- | --- | --- |
| T1 ↔ T2·T3 | 저장소, 내구성 보장, 전송 경로 | 현재 구성의 외부 사용 경로 차이 | 저장소 내부 연산만의 차이, 동일 내구성 비교 |
| T2 ↔ T3 | HTTP 서버 런타임(WSGI/ASGI), 연결 처리, 요청 해석 | 같은 저장소·경로·단일 워커에서 서버 스택을 바꾼 효과 | 순수 프레임워크 성능, 저장소 성능 |
| T3 ↔ T4 | timer가 요청 경로에 주는 비용 | 같은 부하에서 timer 추가의 관찰 가능한 영향 | TTL 기능의 정확성, 메모리 회수 보장 |

- T2와 T3의 연결 동작 차이는 보정하지 않고 기록한다. Werkzeug는 응답마다 연결을 닫을 수 있고 uvicorn은 지속 연결을 쓸 수 있다. 실제 연결 수·재사용 여부를 남기며, 이 차이를 없애려고 서버 설정을 바꾸지 않는다.
- 5회 중앙값과 범위만으로 통계적 유의성을 주장하지 않는다.
- 느린 조건을 찾아도 원인은 별도 진단으로만 좁힌다. 전체 경로 비교로 행 잠금·디스크 기록·이벤트 루프 대기를 확정하지 않는다.

## 5. 실행 조건 고정

- 같은 호스트, 같은 Python, 같은 `storage.py`, 같은 엔드포인트, 같은 JMeter·JVM·JMX·프로퍼티를 쓴다.
- 워커 1, 리버스 프록시 없음, 디버그·상세 로그 없음, 리로더 없음.
- 대상 실행은 별도 JMeter 프로세스다. 대상들을 동시에 실행하지 않는다.
- 측정 코드는 이전처럼 고정 사본으로 복사하고 파일별 SHA256을 기록한다. 단계마다 사본 해시가 바뀌지 않았는지 확인한다.
- 환경 기록에는 호스트·OS·CPU·메모리, Python·프레임워크·서버·JMeter·JDK·MySQL·드라이버 버전, MySQL 내구성 설정, `storage.py`·`app.py` 해시를 남긴다.
- 비밀은 환경 변수 또는 사용자 전용 파일에서 읽고 JMX·결과·문서에 남기지 않는다.

## 6. 실행 단위와 순서

- 4 대상 × 4 동시성 × 5회 = **80회 대상 실행**.
- 회차 순서는 대상 4개를 회전해 순서 효과를 분산한다. 5회는 1회와 같은 순서가 되므로 5회에서는 완전 균형이 깨진다. 이 사실을 결과에 기록한다.

```text
1회: T1 → T2 → T3 → T4
2회: T2 → T3 → T4 → T1
3회: T3 → T4 → T1 → T2
4회: T4 → T1 → T2 → T3
5회: T1 → T2 → T3 → T4   (1회와 같음)
```

- 동시성은 `1`·`10`·`50`·`100` 순서로 진행한다.
- S3-01은 대상별 1회(N=100, C=100)로 4회 실행하고 본 80회와 분리한다.
- 예상 시간: 이전 40회가 47분 39초였고 그 대부분이 MySQL 20회였다. 새 묶음도 MySQL 20회가 같은 비중을 차지하고 HTTP 60회는 상대적으로 짧다. 대략 1시간 안팎으로 보되, 예상 시간을 측정 결과로 제시하지 않는다.

## 7. 측정 하네스 변경 (승인 필요)

현재 `run_performance.py`는 `TARGETS = ("http", "jdbc")`이고 두 대상 교차만 지원한다. 4대상 실행에는 다음 변경이 필요하다.

- 대상 레지스트리: `jdbc`, `flask`, `fastapi`, `fastapi_timer`와 대상별 HTTP 접속 설정.
- 캠페인 계획: 6절의 4대상 회전.
- 결과 키: 대상 이름을 포함해 80회 결과를 구분.
- 유지: JMX 구조, Sampler 라벨, 성공 판정, 정확성 검사, 집계 함수, 실패·중단 규칙.

확정:

- **Flask 기준선 확보 방식(사용자 확정):** 저장소에 상시 파일로 추가하지 않는다. 실행 시 `git show e61a81a:app.py`로 고정 사본에 추출하고 해시를 기록한다. `storage.py`는 현재 파일을 쓴다.
- T2 환경은 `flask==3.1.3`, `werkzeug==3.1.9`를 고정한 별도 측정 의존성으로 준비한다.
- 하네스를 바꾸므로 M3 도구 검증 83건을 새 코드로 다시 통과시킨다. 통과 전 본 측정을 하지 않는다.
- 기존 결과 JSON·worklog 수치는 덮지 않는다. 새 결과 파일과 새 절을 추가한다.

## 8. T4 정의 — timer 구현 후 결정

- **사용자 결정:** timer 구현이 끝난 뒤 그 구현을 기준으로 T4의 정의와 측정 계약을 정한다. 구현 전에 T4를 확정하지 않는다.
- **결정 반영:** D-24에서 active 만료를 FastAPI `lifespan`의 100ms 주기 타이머로 확정했다. T4는 그 타이머를 켠 구성이다.
- timer 구현이 끝나면 T4에서 고정할 것: 주기·표본 수·반복 상한(현재 100ms·표본 20개·최대 2회), 저장소 접근 방식(같은 이벤트 루프의 동기 호출), 카운터 키에 TTL을 거는지 여부.
- 선행 의존: timer는 TTL 저장소 구현(`_expires`·`_ttl_keys`·`_ttl_pos`, lazy/active) 위에 얹는다. TTL 구현이 먼저다. timer 브랜치는 그 뒤에 만든다(제안 이름 `feature/ttl-active-timer`).
- 부하 조건도 timer 구현 후 함께 정한다. 후보:
  - (a) 기존 카운터 부하만 쓴다. timer가 요청 경로에 주는 영향만 관찰되고, TTL 키가 없으면 정리 표본이 비어 비용이 검출 한계 아래일 수 있다.
  - (b) 카운터 부하에 TTL 키를 미리 채운다. 정리 비용이 포함되지만 사전 상태가 T2·T3와 달라져 직접 비교할 수 없다.
  - (c) 정리 비용은 별도 보조 실험으로 분리한다.
- T4는 timer 외에 카운터 경로·응답 계약을 바꾸지 않아야 한다. 측정 전 전체 테스트 통과를 확인한다.

## 9. 실행 절차

1. timer 브랜치를 구현·병합한 뒤 T4 정의와 측정 계약을 확정한다. TTL 저장소 구현이 그 선행이다. 전체 테스트 통과를 확인한다.
2. 하네스를 변경하고 M3 도구 검증 83건을 다시 통과시킨다.
3. 환경 기록을 만든다. 버전·해시·호스트·MySQL 설정·Flask 환경을 포함한다.
4. 연결 확인용 짧은 실행을 대상별 N=1,000·C=1로 1회씩 한다. 기록만 하고 결과에 넣지 않는다. 이는 새 N 결정이 아니다.
5. S3-01을 대상별로 실행한다(N=100, C=100, 4회).
6. 본 측정 80회를 실행한다.
7. 산출물 검산, 회차별 지표, 5회 집계를 수행한다.
8. 자신이 시작한 서버만 종료하고 기본 pytest 회귀를 실행한다.

- 4~6 중 하나라도 실패하면 뒤 단계를 실행하지 않는다. 실패 원자료를 보존하고 새 묶음은 별도 확인 후 시작한다.
- 시간 초과·처리 불명확이 나오면 기존 중단 원칙을 적용한다. 한도를 늘리거나 실패 회차를 대체하지 않는다.

## 10. 결과 형식과 판정

- 대상별·C별 5회 중앙값과 범위로 성공 처리량, p50·p95·p99, 성공률을 기록한다.
- 비교표는 T2/T3, T3/T4, T1 대비 T2·T3 비율을 중앙값 기준으로 만들고 범위를 함께 적는다.
- 실제 연결 수·재사용, 관찰한 최대 진행 수, 실제 버전·해시, 부하 조건을 함께 기록한다.
- 통과 판정은 정확성과 측정 유효성만 한다. 성능 우열은 관찰로 서술하고 합격 기준으로 만들지 않는다.
- 실패 회차가 있으면 5회 요약을 만들지 않는다.
- T4 결과를 TTL 동작의 정확성·메모리 회수 근거로 사용하지 않는다.

## 11. 하지 않는 것

- 제품 API·저장소 계약·응답 필드 변경, 성능 전용 API 추가.
- Flask를 운영 스택으로 되돌리는 것.
- MySQL 내구성 설정을 낮춰 성능을 올리는 것.
- 기존 결과 파일·worklog 수치 덮어쓰기.
- 03 계약의 N·시간 한도·반복 횟수 변경.
- 분산 부하, 대시보드, 상시 추적.

## 12. 리스크와 한계

- Flask 개발 서버와 uvicorn은 배포 모델이 다르다. 결과는 "각 스택의 현재 단일 워커 구성"이며 순수 프레임워크 비교가 아니다.
- Werkzeug의 연결 종료와 uvicorn의 지속 연결 차이가 측정 경로에 포함된다.
- T4가 TTL 키 없는 카운터 부하만 쓰면 timer 비용이 검출 한계 아래일 수 있다. "차이 없음"을 "비용 0"으로 단정하지 않는다.
- 4대상 5회 회전은 완전 균형이 아니다. 회차별 순서와 환경 변동을 기록한다.
- MySQL 20회가 전체 실행 시간을 지배한다. 장시간 실행 중 열·부하 변동이 생길 수 있다.
- Python 3.14.10에서 Flask 3.1.3 동작을 실행 전에 확인한다. 실패하면 버전을 임의로 바꾸지 않고 별도 결정을 받는다.
- 5회 중앙값·범위는 통계적 유의성을 입증하지 않는다.
