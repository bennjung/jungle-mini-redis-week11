# 시나리오 03 — 서버 스택·무효화 성능 비교 제안과 실행 계약

## 0. 상태와 범위

- 2026-11-14 사용자 승인, 2026-11-15 실행 완료. 이 문서는 승인된 실행 계약이며, [03 성능 비교 계약](03-performance-scenario.md)의 **S3-01·S3-02 조건과 기존 결과를 바꾸지 않는다.** 실행 결과는 [03-stack-comparison-results.json](03-stack-comparison-results.json)과 [실행 기록](03-performance-test-worklog.md)의 "서버 스택·무효화 비교" 절에 있다.
- 사용자 요청에 따라 **MySQL은 이번 비교에서 제외한다.** 기존 MySQL 측정값은 역사 기록으로만 보존하고 새 비교표에 넣지 않는다.
- 비교는 두 층으로 나눈다.
  1. **공통 3자** — Flask / FastAPI@ce427 / FastAPI@HEAD가 모두 수행할 수 있는 **수동 무효화 캐시 수명주기**.
  2. **기능 전용** — FastAPI@ce427와 FastAPI@HEAD만 수행하는 **콜드 키 TTL 만료 백로그**.
- 두 층을 하나의 "3자 무효화 비교"로 합치지 않는다. F/A는 TTL 만료를 수행하지 않으므로 만료 시나리오의 동등한 3자 대상이 아니다.

## 1. 왜 두 층인가

- S3-02 카운터는 단일 키 쓰기 전용이라 캐시 재사용·무효화·만료를 측정하지 않는다.
- 원안의 4요청 사이클은 TTL을 전체 한도보다 길게 두어 **만료를 한 번도 일으키지 않았다.** 그 상태의 B는 TTL 인덱스 부기를 하는 정도이고, "무효화 기능의 성능"이 아니라 "공통 캐시 경로의 부기 비용"이다.
- F/A는 TTL이 없다. TTL 만료를 공통 3자 시나리오에 넣으면 F/A가 TTL을 무시하게 되어 같은 응답을 만들 수 없다.
- 따라서 **공통 비교는 만료를 빼고 수동 무효화만** 수행하고, **만료는 기능 전용 A/B 비교**로 분리한다.

## 2. 비교 대상

| ID | 이름 | `app.py` | `storage.py` | 실행 방식 |
| --- | --- | --- | --- | --- |
| F | Flask 기준선 | `e61a81a` | `ce427a2` | Flask 개발 서버, `threaded=False`, `use_reloader=False`, `127.0.0.1:5000` |
| A | FastAPI 기준선 | `ce427a2` | `ce427a2` | uvicorn `workers=1`, `127.0.0.1:5000` |
| B | FastAPI + TTL·무효화 | `c5df702` (실행 시 고정) | `c5df702` | A와 같고 lifespan의 100ms active 만료 타이머가 켜진 구성 |

- F와 A는 **같은 `storage.py`**를 쓴다. 두 대상의 차이를 HTTP 서버 계층으로 좁히기 위해서다. `e61a81a`와 `ce427a2`의 `storage.py`는 SHA256이 같다(`cd5bea4b...ad95ee`).
- B는 최신 TTL 저장소·HTTP 표면·active 타이머를 포함한다. 실행 시점의 커밋을 고정하고 `app.py`·`storage.py` SHA256을 기록한다.
- 세 대상 모두 Python 3.14.10을 쓴다. F는 `flask==3.1.3`·`werkzeug==3.1.9`를 고정한 별도 측정 환경, A·B는 `fastapi==0.162.7`·`uvicorn==0.54.0`을 쓴다.
- 한 번에 한 서버만 `127.0.0.1:5000`에서 실행한다. 서버 시작·종료는 측정 밖이며, 이전 서버를 종료하고 포트가 비었는지 확인한 뒤 다음 대상을 시작한다.
- 측정 코드는 고정 사본으로 복사하고 파일별 SHA256을 기록한다.

## 3. 비교 1 — 카운터 (기존 S3-01·S3-02 그대로)

- 대상: F, A.
- 시나리오: 기존 [S3-01·S3-02](03-performance-scenario.md)를 그대로 쓴다. 새 시나리오 ID를 만들지 않는다.
- 작업: `counter:one`에 `1` 증가, `POST /kv/incr`, 성공은 HTTP 200과 `{"ok":true,"value":<숫자>}`.
- 정확성 선행: S3-01 N=100, C=100, 최종 `value`=100.
- 본 측정: N=10,000, C=`1`·`10`·`50`·`100`, 대상별·C별 5회, 워밍업 100건, 요청 5초·전체 360초·준비 30초·종료 15초.
- 순서: 홀수 회차 F→A, 짝수 회차 A→F. 5회에서는 완전 균형이 아니므로 실제 순서를 기록한다.
- 실행 수: 2 × 4 × 5 = **40회**.
- 기존 Flask 결과는 역사 기록으로 남긴다. 새 비교는 같은 세션에서 F를 다시 측정한 값과 A를 짝지어 사용한다.

## 4. 비교 2 — 공통 3자: 캐시 수명주기 S3-03A

### 4.1 목적과 04 연결

- 목적: 공유 키 집합에서 **hit → 수동 무효화 → miss → 재채움**의 수명주기를 실행해, TTL 인덱스 생성·삭제와 lazy 검사가 공통 캐시 경로에 주는 비용을 단계별로 관찰한다.
- 04 연결: [S4-01 보관한 API 응답 재사용](../scenario_04_response_cache/04-response-cache-scenario.md)과 [S4-03 사용자가 응답을 수동 무효화](../scenario_04_response_cache/04-response-cache-scenario.md)를 KV HTTP 표면으로 옮긴 것이다.
- 원본 날씨 API는 서버 밖 소비자이므로 성능 경로에 넣지 않는다.

### 4.2 정확한 입력과 단계

| 항목 | 값 |
| --- | --- |
| 키 | `weather:cache:{j}`, j=0..3,999 (공유 키 집합) |
| value | 문자열 `{"temperature":22,"observed_at":"2026-11-14T12:00:00Z"}` |
| TTL | `600000`ms. 전체 한도 360초보다 길어 측정 중 만료가 없다. |
| 사전 상태 | 회차마다 4,000개 키를 `PUT`으로 채우고 `GET`으로 전부 확인한다. 측정 밖이다. |
| 단계 1 | 4,000개 `GET` — 전부 `{"found":true,"value":V}` |
| 단계 2 | 앞 2,000개 `DELETE` — 전부 `{"found":true,"value":V}` |
| 단계 3 | 같은 2,000개 `GET` — 전부 `{"found":false}` |
| 단계 4 | 같은 2,000개 `PUT` — 전부 `{"ok":true}`. TTL 600,000ms를 다시 건다. |
| 전체 요청 | 10,000건 |
| 동시성 | C=`1`·`10`·`50`·`100` |
| 워밍업 | 스레드당 1회의 미니 수명주기(PUT→GET→DELETE→GET), 전체 4C요청. 측정 밖이다. |
| 회차 | 대상별·C별 5회 |
| 시간 한도 | 요청별 5초, 전체 360초, 준비 30초, 종료 15초 |
| 최종 상태 | 4,000개 키가 전부 `{"found":true,"value":V}`. 측정 밖에서 확인한다. |

- 키 배분: 스레드 `t`는 `j = (t-1) + (loop-1)*C`를 처리한다. 단계마다 키 인덱스를 다시 `t-1`로 초기화한다. 단계 1은 4,000/C회, 단계 2~4는 2,000/C회 반복한다. C=1/10/50/100에서 모두 정수다.
- 단계 사이에 모든 스레드가 도착하는 장벽을 둔다. 장벽 대기는 단계별 지연에 넣지 않고 전체 실행 구간에만 포함한다.
- 단계별 응답은 정확히 정해지므로 공유 키 집합에서도 성공 판정이 결정적이다. 같은 키에 동시 PUT/GET/DELETE가 섞이는 경합은 이 시나리오의 범위가 아니다.

### 4.3 이 단계가 재는 것

- `GET hit` — lazy 만료 검사가 읽기 경로에 주는 비용.
- `DELETE` — lazy 검사와 TTL 인덱스 제거(swap-pop)가 무효화 경로에 주는 비용.
- `GET miss` — 삭제 뒤 miss 경로의 비용.
- `PUT refill` — TTL 인덱스 생성·갱신이 재채움 경로에 주는 비용.
- F↔A는 HTTP 스택 차이, A↔B는 TTL 부기 비용이다. 단계별 지표를 먼저 보고 합계는 보조로 본다.

### 4.4 이 단계가 재지 않는 것

- TTL 만료 경계와 만료 뒤 재조회. 이는 가짜 시계를 쓰는 S4-02 기능 테스트가 담당한다.
- 콜드 키 대량 회수·active 만료 처리량. 기능 전용 S3-03B가 담당한다.
- 같은 키 동시 접근, stampede, single-flight, 대량 무효화, 원본 API 비용, 다중 워커, MySQL.

## 5. 비교 3 — 기능 전용: 콜드 키 만료 백로그 S3-03B

### 5.1 목적

- 실제 TTL 만료와 100ms active 정리 작업이 **핫 키 요청 경로**에 주는 영향을 A↔B로 관찰한다.
- F/A가 TTL을 수행하지 않으므로 **A↔B 기능 비교**이며 3자 동일 시나리오가 아니다.

### 5.2 정확한 입력과 절차

| 항목 | 값 |
| --- | --- |
| 콜드 키 | `weather:cold:{j}`, j=0..9,999 |
| 콜드 value | 문자열 `{"temperature":22,"observed_at":"2026-11-14T12:00:00Z"}` |
| 콜드 TTL | `5000`ms |
| 핫 키 | `weather:hot` |
| 핫 value | 문자열 `{"temperature":19,"observed_at":"2026-11-14T12:00:00Z"}` |
| 사전 상태 | 콜드 키 10,000개를 TTL 5초로 채우고, 마지막 저장 뒤 6초를 기다려 전부 만료시킨다. 핫 키는 TTL 없이 저장하고 확인한다. 측정 밖이다. |
| 측정 작업 | `GET /kv?key=weather%3Ahot`을 N=10,000건 실행한다. 전부 `{"found":true,"value":V_H}` |
| 동시성 | C=`1`·`10`·`50`·`100` |
| 워밍업 | 전체 100건, 스레드당 100/C건. 측정 밖이다. |
| 회차 | 대상별·C별 5회 |
| 시간 한도 | 요청별 5초, 전체 360초, 준비 30초, 종료 15초 |
| 최종 상태 | 핫 키가 `{"found":true,"value":V_H}`. 측정 밖에서 확인한다. |

- B는 대기 중과 측정 중 100ms 타이머로 만료된 콜드 키를 정리한다. A는 TTL을 무시하므로 콜드 키가 남고 정리 작업이 없다.
- 핫 키 응답은 A/B가 같다. 차이는 active 정리 작업과 콜드 키 집합 축소가 핫 경로에 주는 영향이다. 두 효과를 개별 분해하지 않는다.
- 콜드 키의 정확한 정리 진행률은 HTTP로 관찰하지 않는다. 기능 정확성은 01 TTL 테스트가 담당한다. 정리 작업이 실제로 시작됐다는 것은 사전 상태(만료된 콜드 키 10,000개)와 B의 타이머 계약으로 확인한다.
- 이 단계의 결과를 TTL 만료 정확성·메모리 회수 보장의 근거로 사용하지 않는다.

## 7. 하네스와 검증

### 7.1 하네스

- 기존 `counter.jmx`·`counter.groovy`·`run_performance.py`의 카운터 경로는 **동결**한다.

  - 시나리오·서버 식별, `operation` 기록.
  - 단계 장벽과 스레드별 키 인덱스.
  - PUT·GET hit·DELETE·GET miss의 op별 성공 판정.
  - 최종 캐시 상태 확인(4,000키)과 핫 키 확인.
- `run_invalidation.py`는 서버 시작·종료, 결과 폴더·상태 표식, 산출물 검산, 5회 집계를 담당한다.

### 7.2 사전 확인·검증

- 소규모 기능 확인: 캐시 K=4/N=10/C=1, 캐시 K=40/N=100/C=10, 만료 콜드 K=10/N=10/C=1을 F/A/B에서 통과했다.
- 전 규모 확인: 캐시 K=4,000/N=10,000을 A·B의 C=1과 B의 C=100에서 통과했다. 만료 콜드 K=10,000/N=10,000을 B의 C=1에서 통과했다.
- 카운터 F/A의 N=100/C=1을 통과했다.
- 기존 83개 측정 도구 검증은 `counter` 경로를 바꾸지 않았으므로 그대로 유효하다. 새 하네스의 op별·최종 상태 검증은 위 사전 확인과 본 측정 산출물 검산으로 확인한다.
- 사전 확인은 본 측정 5회에 섞지 않는다. 별도 결과 폴더에 보존한다.

### 7.3 산출물 검산

- 완료 표식: 시나리오, 서버, C, N, 시도·성공·실패 건수, 워밍업, 최종 상태, 시작·종료 시각, 처리 불명확, 한도 도달, 준비 실패.
- 정규화 기록과 JTL: `(thread_name, request_sequence)` 집합 일치, op 일치, 결과·시작·결정 시각 일치, 성공 건수 = N.
- op별 건수: 캐시 `get_hit=4,000`, `delete=2,000`, `get_miss=2,000`, `put_refill=2,000`; 만료 `get_hot=10,000`.
- 최종 상태: 캐시 4,000키 전부 hit, 만료 핫 키 hit.
- 최대 진행 수 ≤ C, 스레드별 진행 수 ≤ 1.
- 전체 시작 ≤ 첫 호출 시작, 전체 종료 = 마지막 결정. 회차별 지표를 먼저 계산하고 5회 중앙값·최솟값~최댓값을 만든다.

## 9. 한계와 해석 규칙

- **TTL 의미 차이:** F/A는 `ttl`을 무시하고 B만 저장한다. S3-03A는 만료를 피해 같은 외부 응답을 만들지만, 동등한 TTL 기능 비교가 아니다. "수동 무효화 경로의 TTL 부기 비용"으로만 읽는다.
- **비용 분해 없음:** A↔B 차이는 lazy 검사, TTL 인덱스, active 타이머, 콜드 키 집합 축소가 합쳐진 값이다. 하위 비용을 개별 분해하지 않는다.
- **키 집합 크기:** S3-03A는 4,000키, S3-03B는 콜드 10,000키다. 04의 실제 캐시 규모를 대표하지 않는다.
- **단일 프로세스:** Flask `threaded=False`, uvicorn `workers=1`의 현재 구성이다. 다중 워커·운영 배포 성능이 아니다.
- **연결 동작 차이:** Werkzeug의 연결 종료와 uvicorn의 지속 연결 차이가 측정에 포함된다. 이 차이를 없애려고 서버 설정을 바꾸지 않고 실제 연결 수·재사용 여부를 기록한다.
- **순서 효과:** 5회 회전은 완전 균형이 아니다. 회차별 순서와 환경 변동을 기록한다.
- **계측 영향:** 기존 03 하네스의 공유 잠금·기록·감시 예약이 처리량·지연에 주는 영향은 아직 검증되지 않았다(후속 이슈 #5). 이 한계는 새 비교에도 그대로 적용되며, 처리량 정체를 서버 포화로 확정하지 않는다.
- **통계적 유의성:** 5회 중앙값·최솟값~최댓값은 신뢰구간이나 유의성 증명이 아니다.
- **MySQL 제외:** 이번 결과를 MySQL 대비 우위나 동일 내구성 비교로 확장하지 않는다.
