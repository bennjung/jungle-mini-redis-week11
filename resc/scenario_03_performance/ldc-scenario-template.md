## 다른 의견

- **S3-02는 한 번의 큰 부하가 아니라 여러 동시성 조건에서 측정해야 한다.** 동시성 1·10·50·100 같은 곡선이 있어야 처리량이 어디까지 오르고 어디서 꺾이는지 보인다. 한 점만으로는 포화 지점과 지연 증가를 알 수 없다.
- **S3-02의 기대값은 100이 아니라 N이다.** 100은 S3-01의 작은 정확성 케이스다. 성능 측정에서 N건을 보내면 최종값은 N이고, 응답 값은 1~N이 각각 한 번이어야 한다. N은 그 실행의 성공한 증가 건수다.
- **측정 조건을 고정해야 한다.** 양쪽 비교 대상에 같은 서버 모델·HTTP 클라이언트·환경을 쓰고, 같은 요청 수·동시성·초기값으로 측정한다. DB 쪽은 원자적 증가로 정확성을 맞춘다.
- **워밍업과 반복이 필요하다.** 초반 요청은 버리고, 여러 회 반복해 중앙값과 범위를 기록해야 한다. 구체적인 횟수와 순서는 미정 사항에서 정한다.
- **지표는 처리량만이 아니라 p50·p95·p99, 성공·실패·타임아웃, 최종값을 함께 기록해야 한다.** 평균만 보면 꼬리 지연을 놓친다.
- **현재 `threaded=False` 서버가 먼저 포화될 수 있다.** 그러면 Mini Redis와 DB의 차이가 아니라 단일 스레드 HTTP 서버의 한계를 재게 된다. 두 경로를 같은 서버 모델로 맞추거나, 저장소 계층에서 직접 재는 별도 실험을 둬야 한다.
- **개선 폭 기준은 지금 정하지 말고 파일럿 후에 정해야 한다.** 성능 변화 폭을 모르는 상태에서 숫자를 정하면 결과를 보고 기준을 맞추게 된다. 파일럿으로 분산을 확인한 뒤 최종 측정 전에 기준을 정하고 동결한다. 과제는 차이 비교이므로, 신뢰구간이 0을 포함하면 개선을 주장하지 않는 정도로 둘 수 있다.

## 미정 사항에 대한 생각

- **미사용 기준선과 측정 경로** — "사용자 관점"은 HTTP를 무조건 포함한다는 뜻이 아니라, 사용자가 실제로 쓰는 경로를 재는 것이다.
  - 제품이 HTTP API라면 사용/미사용 양쪽 모두 같은 HTTP 경로를 거친다. HTTP는 공통 비용이고, 캐시 이득이 그 비용을 넘는지를 본다.
  - 라이브러리나 내장 저장소라면 HTTP를 넣지 않는다. 넣으면 인위적인 비용이 붙는다.
  - DB를 HTTP로 한 번 더 감싸지 않는다. 같은 앱 안에서 드라이버로 직접 호출하고, Mini Redis도 같은 앱에서 호출한다.
  - 한쪽에만 HTTP를 붙이면 비교가 아니다.
  - 03의 카운터 비교는 저장소 계층 비교로 두고, HTTP가 제품 경로인 04의 응답 캐시 비교와 분리한다.
  - HTTP 오버헤드가 저장소 차이보다 커서 개선 폭이 작게 나오는 것은 결과다. 경로를 임의로 빼지 말고, 측정 인터페이스와 경로를 문서에 명시한다.
- **측정 유효성** — 기본 비교는 시스템 실패(타임아웃·5xx·연결 거절) 0건. 고동시성 스트레스는 실패율을 별도로 기록하고 처리량에는 성공 건만 넣는다. 400은 유효한 증가만 보내고, 예상 밖 400은 실행 무효로 본다.
- **정확성** — N건 +1, 모두 성공 시 최종값 N, 응답 값 1~N이 각각 한 번. N은 100이 아니라 그 실행의 요청 수(성공 건수)다.
- **비교 경로** — 03은 저장소 계층 직접 비교로 확정한다. `MiniRedis.incr` vs MySQL 원자적 증가, HTTP 없음. HTTP가 제품 경로인 04와 분리한다.
- **DB** — MySQL. SQLite의 DB 전체 쓰기 락 같은 다른 병목을 피한다.
- **측정 절차** — 워밍업 100건(측정 전, 결과 버림) → 카운터 0 초기화 → 고정 건수 N 측정 → 5회 반복, 중앙값과 범위 기록. A/B 순서는 회차마다 교차한다. N은 파일럿 후 1,000~10,000에서 정한다.
- **워밍업** — 측정 시작 전에 같은 경로로 몇 번 요청해 시스템을 데우는 단계다. 결과는 버린다.
  - DB 커넥션 풀: 첫 요청은 연결 수립이 느리다.
  - MySQL 버퍼 풀: 첫 쿼리는 디스크에서 읽고, 이후에는 메모리에서 읽는다.
  - OS 페이지 캐시, HTTP 클라이언트 keep-alive, Python 모듈·할당자 준비.
  - 워밍업이 없으면 초반 요청이 느려 처리량이 낮게 나오고, 특히 DB 쪽이 불리해진다.
  - 카운터 한 행 기준 100건이면 충분하다. 데이터가 커지면 늘린다.
  - '측정 구간의 첫 100건'이 아니라, 측정 전 별도 단계다. 워밍업 후 카운터를 0으로 초기화하고 측정을 시작한다.
