# 시나리오 03 — JMeter 테스트 설계

## 1. 목적·상태·설계 경계

- 행동 계약은 [03 성능 비교 시나리오](03-performance-scenario.md)를 따른다. 이 문서는 S3-01·S3-02를 JMeter로 실행하기 위한 설계다. 과제 요구사항에 새 사용자 기능을 추가하지 않는다.
- **확정:** JMeter 사용. 기존 Mini Redis 서버 유지, 실제 재연결 비용 포함, 전체 N건 제한에 기본 기능 재사용, MySQL 시험 전용 데이터·요청별 자동 커밋 사용. 처리 종료가 불명확한 실패에서는 새 요청 배분을 멈추고 측정 묶음을 중단하며 다음 회차를 초기화하지 않는 방침도 사용자 승인 사항이다.
- **구현 승인 및 반영:** 사용자가 이 설계의 구현과 결과 분석을 요청했다. 아래의 기본 시험용 SQL·JMeter 배치·조율·결과 집계를 구현했다. 진단 계측을 모두 구현한 것은 아니며, 검증 범위와 실제 결과는 [실행 기록](03-performance-test-worklog.md)을 따른다. 파일럿 후 수치 확정 절차는 유지한다.
- **파일럿 검토 후 확정:** N=10,000, 요청별5초·전체360초·준비30초·종료15초. 초기 전체120초 중단 자료와 새 조건의 결과는 분리한다. 확정 근거·재개 승인은 [실행 기록](03-performance-test-worklog.md)을 따른다.
- **환경 준비 시 확정·기록:** JMeter·JDK·MySQL·Connector/J·Python·Flask·Werkzeug 버전과 실제 접속 주소, DB 전용 스키마·계정, 자원 배치. 선택한 버전으로 아래 도구 검증을 통과하기 전 본 측정을 하지 않는다.
- JMX·조율 스크립트·SQL·집계 코드·측정 도구 검증이 존재한다. 기본 비교와 별도 서버 내부 진단 계측의 구현·검증 상태를 구분한다. 실행한 항목만 [실행 기록](03-performance-test-worklog.md)에 표시한다.

### 기존 구조를 재사용하는 범위

| 문제 | 재사용할 기존 기능 | 새로 필요한 최소 처리 |
| --- | --- | --- |
| Mini Redis 요청 | `app.py`의 `POST /kv/incr`, `MiniRedis.incr`, 기존 순차 처리 | HTTP 요청 설정과 결과 판정 |
| 정확성 선행 검증 | S3-01, 시나리오 02의 성공·최종 상태 계약 | JMeter 결과를 같은 기준으로 판정 |
| 전체 N건 | `Throughput Controller`의 `Total executions`, `Per User` 해제 | 시작·중단 조율, 실제 시도 수 검산 |
| DB 연결·갱신 | `JDBC Connection Configuration`, `JDBC Request` | 자동 커밋·전용 연결 설정, 변경 행 수 1 판정 |
| 기록 | JMeter JTL과 `sample_variables` | 측정 구간·성공 요청 필터·회차별 집계 |
| 요청별 한도 | HTTP·JDBC의 기본 통신 한도 | 전체 호출의 논리적 마감 시각과 늦은 응답 구분 |

기존 `tests/scenario_02_concurrent_counter/test_counter_concurrent.py`의 요청별 `opener` 생성과 한 묶음 실행을 성능 실행기로 그대로 옮기지 않는다. 기존 기능 테스트는 유지한다. 제품에 명령 큐·새 저장 계층·성능 전용 API를 추가하지 않는다.

## 2. 실행 단위와 책임

한 **측정 묶음**은 같은 환경·N·시간 한도로 수행하는 양쪽 × 동시성 4종 × 5회 비교다. 각 **대상 실행**은 대상 하나·동시성 하나·회차 하나이며 별도 JMeter 프로세스로 실행한다. 파일럿·기본 비교·진단은 서로 다른 묶음으로 기록한다. 결과 폴더와 독립된 동일한 `--state-dir`를 대상 환경별로 공유하며, 원자적 잠금과 진행/미해결 표식으로 중복 실행과 다음 묶음 시작을 차단한다. 새 결과 폴더나 상태 위치 변경으로 실패를 우회하지 않는다.

```text
실행·집계 담당
  ├─ 환경·설정 확인, 묶음 기록, 실행 순서 결정
  ├─ 대상 실행마다 JMeter 프로세스 한 개 시작
  │    ├─ 준비: 시험 데이터·C개 실행 주체·연결·워밍업
  │    ├─ 시작 조율 → 숫자 0 초기화 → 전체 시간 시작
  │    ├─ 기본 Controller가 전체 N건 배분
  │    │    ├─ HTTP Request → 기존 Mini Redis 서버
  │    │    └─ JDBC Request → MySQL
  │    └─ 종료 확인 → 최종 조회 → 기록·연결 종료
  └─ 결과 검산 → 회차별 지표 → 5회 중앙값·범위

처리 여부 불명확 / 전체 한도 초과 / 기록 불완전
  → 대상 실행 실패 기록 → 묶음 중단 → 다음 초기화 금지
```

- JMeter는 요청 전송과 동시 실행을 담당한다. 별도 Python 부하 실행기를 병행하지 않는다.
- 실행·집계 담당은 기존 Python 환경과 표준 라이브러리로 순서·프로세스·결과 검산만 담당하는 안이다. 서버나 MySQL을 임의 시작·재시작·종료하지 않는다.
- JMeter는 단일 로컬 실행 엔진을 사용한다. 기본 Controller의 전역 횟수는 여러 분산 엔진에 걸친 N이 아니므로 분산 모드는 이번 범위에서 제외한다.
- 구현 연결: `counter.groovy`의 `M3Coordinator`가 조율·시간 경계를, `run_performance.py`의 `run_single`·`run_pilot`·`run_campaign`이 실행 단위를, `RunStateStore`가 공통 상태 위치의 잠금·실행 표식을 담당한다. 아래 단계의 입력·출력·실패 연결을 유지한다.

## 3. 정확한 작업과 시험 데이터

### Mini Redis

- 대상 키: `counter:one`.
- 준비·초기화: `PUT /kv`, 본문 `{"key":"counter:one","value":0}`. HTTP 200과 `{"ok":true}` 확인.
- 증가: `POST /kv/incr`, 본문 `{"key":"counter:one","amount":1}`, `Content-Type: application/json`. 상한은 생략한다.
- 성공 판정: HTTP 200, JSON 객체의 필드가 `ok`·`value`, `ok`가 실제 불리언 `true`, `value`가 실제 숫자. 본문 전체 수신 후 판정하며 필드 순서는 강제하지 않는다. 변경 직후 수치 집합의 검증은 기존 02 계약과 구분한다.
- 최종 조회: `GET /kv?key=counter%3Aone`, HTTP 200과 `{"found":true,"value":N}` 확인. S3-01은 N 대신 100.
- 자동 재시도·리다이렉트 추적·응답 캐시·추가 리소스 요청을 사용하지 않는다.

### MySQL

기존 MySQL 스키마·접속 코드·JMX가 없음을 확인한 뒤, 사용자 데이터와 분리한 다음 **시험 전용 구조**를 추가했다. 제품 저장소의 스키마가 아니다.

```sql
CREATE TABLE benchmark_counter (
    counter_key VARBINARY(256) PRIMARY KEY,
    value BIGINT NOT NULL
) ENGINE=InnoDB;
```

- `counter_key`에는 `counter:one`의 바이트를 사용한다. 모든 요청이 같은 행에 접근한다. 일반 Mini Redis 자료형 전체를 DB에 재현하는 설계가 아니다.
- N 후보와 워밍업 합계는 `BIGINT` 범위 안이다. 범위 초과·소수는 이번 비교 입력에 포함하지 않는다.
- 시험 전용 스키마를 명시적으로 지정해야 하며 일반 업무 스키마로 자동 대체하지 않는다. 기존 테이블 구조가 다르면 덮어쓰거나 자동 마이그레이션하지 않고 준비 실패로 종료한다.
- 사전 상태는 대상 행의 존재와 숫자 0을 확인한 상태다. 준비 과정의 삽입과 초기화는 측정 밖에서 수행한다. 초기화의 변경 행 수가 0이어도 이미 0일 수 있으므로 조회로 확인한다.
- 측정 작업: `UPDATE benchmark_counter SET value = value + 1 WHERE counter_key = ?`. 한 요청당 문장 하나·자동 커밋. 키만 매개변수로 전달하며 `get` → 계산 → 덮어쓰기를 하지 않는다.
- 성공 판정: JDBC 오류 없음, 변경 행 수 정확히 1. JDBC의 정상 상태 코드만으로 성공시키지 않는다. 준비된 갱신 요청의 결과 형식은 선정 버전에서 도구 검증으로 확인한다.
- 최종 조회: 같은 행을 `SELECT value`로 조회하여 1행·수치 N 확인. 요청마다 조회를 붙이지 않는다. 변경 확정 이전의 응답을 성공으로 계산하지 않는다.
- Connector/J의 자동 재연결과 애플리케이션 재시도는 끈다. DB 잠금 시간 초과·교착 오류도 재시도하지 않는다. 내구성 설정은 실제 구성 그대로 기록하며 성능을 위해 조용히 낮추지 않는다.

## 4. JMeter 배치와 전체 N건 배분

HTTP와 JDBC의 실행 계획은 공통 구조를 사용하되, 대상 실행에서 한 종류만 활성화한다. 사용자별 고정 `N / C` 반복이나 자체 공유 카운터로 배분하지 않는다.

```text
Test Plan
  ├─ 공통 설정, 선택 대상의 HTTP 또는 JDBC 설정
  ├─ setUp Thread Group: 1개 실행 주체
  │    └─ 입력 검증·공유 상태 준비·대상 행/키 준비
  ├─ Thread Group: C개 실행 주체, 외부 반복 1회
  │    ├─ 실행 주체별 연결 준비
  │    ├─ 워밍업: 각 100/C건, 전체 100건
  │    ├─ 준비 완료 통지
  │    ├─ 대표 실행 주체: 모두 준비 대기 → 0 초기화·조회 확인
  │    ├─ 전체 시작 시각 기록 → 시작 허용
  │    └─ 측정 반복: 최대 N회 기회
  │         └─ Throughput Controller
  │              Total executions=N, Per User=false
  │              └─ 중단 여부 확인 → 증가 Sampler 정확히 하나
  │                   ├─ 호출 직전 기록
  │                   ├─ HTTP 또는 JDBC 요청
  │                   └─ 수신 직후 기록·결과 판정
  └─ tearDown Thread Group: 종료 상태 확인·최종 조회·결과 내보내기
```

- C는 `1`·`10`·`50`·`100`이므로 `100/C`는 항상 정수다. 따라서 모든 측정 실행 주체가 실제 연결·요청을 경험하면서 워밍업 합계가 정확히 100건이다. 워밍업 대상 숫자는 준비 단계에서 먼저 0으로 만든다.
- `Throughput Controller` 아래에는 측정 증가 Sampler 하나만 둔다. 준비·조회·계측 Sampler가 N에 포함되지 않게 한다. 해당 Controller를 회차 재실행용 바깥 반복으로 감싸지 않는다. 회차는 새 프로세스로 분리한다.
- 측정 반복의 N은 실행 주체별 **기회 상한**이며 실제 전송 횟수가 아니다. 전역 Controller가 전체 전송을 N으로 제한한다. 선택한 버전의 부모 반복과 전역 횟수 동작은 도구 검증으로 반드시 확인한다.
- 완료한 실행 주체가 다음 기회를 가져간다. 빠른 실행 주체가 더 많이 처리해도 되고, 끝부분에는 진행 중 요청 수가 C보다 줄어든다.
- Controller의 허용 횟수, 호출 직전 기록 수, 실제 응답 수는 서로 다르다. 중단이나 준비 실패로 호출하지 못한 기회를 시도 건수에 넣지 않는다.
- `Synchronizing Timer`를 측정 요청의 부모 범위에 두지 않는다. 매 요청마다 C개를 기다리면 고정 동시성 시험이 아니라 묶음별 동기 실행으로 바뀐다.

## 5. 연결·준비·시작 조율

### DB 연결

- JDBC 설정은 실행 주체별 단일 연결을 갖는 `Max Number of Connections=0`, `Auto Commit=true`를 사용한다. 각 주체의 워밍업을 통해 연결 생성을 완료한다. 설정 객체를 만들었다는 이유만으로 연결 준비 완료로 보지 않는다.
- 준비·워밍업·측정은 같은 실행 주체와 연결 풀을 유지한다. 워밍업을 별도 Thread Group에서 끝내고 다른 측정 스레드의 연결까지 준비됐다고 가정하지 않는다.
- 기본 비교에서는 불필요한 연결 유효성 검사 쿼리가 요청마다 추가되지 않도록 선정 버전의 실제 동작을 확인한다. 측정 중 연결 장애는 재연결로 숨기지 않는다.
- 연결 식별 후조회는 각 주체의 마지막 요청 직후가 아니라 `m3-wait-complete` 장벽 뒤에 둔다. 전체 측정 결정이 끝나기 전에는 후조회가 측정 요청과 겹치지 않으며, 실패·처리 불명확이면 조회하지 않는다. 이 장벽을 격리 시험으로 검증했다.

### HTTP 연결

- HTTPClient4와 실행 주체별 클라이언트 상태를 사용한다. 가능하면 지속 연결을 사용하되 기존 서버가 닫은 연결을 억지로 유지하지 않는다.
- 기존 Werkzeug 서버의 `Connection: close` 동작은 사전 확인 요청과 실제 버전의 소스·진단 자료로 확인한다. 세션 객체 재사용을 실제 TCP 연결 재사용으로 보고하지 않는다.
- 이 경우 측정 전에 클라이언트 준비·워밍업은 할 수 있지만 모든 측정 요청의 TCP 연결 생성을 미리 끝낼 수는 없다. **측정 중 필요한 재연결 비용은 포함한다.** 이것이 기존 서버를 유지하는 승인된 비교 범위다.
- `httpclient4.retrycount=0`, `httpclient4.request_sent_retry_enabled=false`를 명시한다. 서버의 정상적인 연결 종료 후 다음 새 요청을 위해 연결을 여는 것과, 실패한 증가를 다시 보내는 재시도를 구분한다.

### 시작 조율

- 공유 상태는 JMeter 프로세스 한 개 내부에만 둔다. C개 준비 완료 통지, 시작 허용 신호, 중단 신호, 호출별 관찰 기록이 필요하다. Java 표준 동기화 기능을 쓰는 작은 Groovy 코드로 처리하고 외부 조율 서비스는 만들지 않는다.
- 준비 완료 통지는 각 주체가 자기 워밍업 응답을 모두 검증한 뒤 보낸다. 대표 주체는 C개 모두를 확인한 다음 기존 요청 경로로 0 초기화와 조회 확인을 수행한다. 다른 주체는 측정 요청을 보내지 않고 대기한다.
- 대표 주체는 전체 시작 시각을 먼저 기록하고 시작 신호를 해제한다. 요청마다 같은 시작 장벽을 다시 사용하지 않는다.
- 워밍업·연결·초기화·장벽 대기 중 실패하면 측정을 시작하지 않는다. 준비 한도 안에 시작되지 않으면 준비 실패로 기록하며 요청 지연이나 성공 처리량을 만들지 않는다.

## 6. 시간 경계와 결과 기록

### 시간의 기준

- 기본 Sampler의 `Elapsed`는 요청 전체 지연을 검산하는 자료다. HTTP는 본문 전체 수신, JDBC는 변경 확정된 실행 결과 반환까지를 포함한다. JDBC의 문장 준비·결과 구성·연결 풀 반환 같은 클라이언트 비용도 경로의 일부이며 순수 SQL 실행 시간으로 해석하지 않는다. 최종 보고의 지연 기준은 아래 고해상도 호출 경계 시간으로 통일한다.
- JTL의 `Latency`를 전체 지연으로 사용하지 않는다. HTTP에서는 첫 응답까지의 시간이며, JDBC와 동일한 의미의 서버 처리 시간으로 비교할 수 없다.
- JTL의 기본 시간 단위는 밀리초다. 0ms 표본을 지연 0으로 단정하지 않는다. 로컬 MySQL처럼 밀리초보다 짧은 차이가 중요한 경우를 위해 마지막 PreProcessor와 첫 PostProcessor에서 `System.nanoTime()`으로 호출 경계도 기록하는 설계다. 이 값에는 프레임워크 진입·복귀 비용이 포함되며 네트워크만의 시간이 아니다.
- 측정 증가 Sampler에는 대기 Timer를 두지 않는다. 사전 기록 이후에 별도 대기나 결과 검증을 끼워 고해상도 지연을 부풀리지 않는다. 기록·조율 코드의 비용은 도구 검증과 파일럿에서 확인한다. 단위가 나노초라고 정확도가 나노초라고 주장하지 않는다.
- 최종 보고의 지연 기준은 고해상도 호출 경계 시간으로 통일하고 기본 `Elapsed`는 검산·기본 보고서용으로 보존하는 안이다. 선정 버전에서 경계 계측 검증이 실패하면 본 측정하지 않는다. 기준을 도중에 바꾸지 않는다.
- 전체 시작은 준비 완료 후 시작 신호 해제 직전이다. 정상 전체 종료는 모든 실제 호출의 결과가 결정된 마지막 시각이다. 응답 수신 시각은 결과 판정 전에 기록하며, 마지막 판정의 처리 시간을 전체 종료 시각에 더하지 않는다. 마지막 JTL 쓰기·검증·최종 조회·프로세스 종료 시각으로 대신하지 않는다.

### 호출 기록과 상태 보존

- 기록에는 대상 실행 식별자·단계(준비/워밍업/측정/검증)·실행 주체·주체 내부 요청 순번·호출 시작·마감·결과 결정 시각·관찰된 반환 시각·결과 분류·기본 Elapsed/Latency/Connect Time을 남긴다.
- 요청 식별은 실행 주체와 내부 순번의 조합을 사용한다. 이 식별자는 부하 배분을 위한 별도 전역 카운터가 아니다. 요청 본문이나 제품 응답에 새 필드를 넣지 않는다.
- 성공·명시적 거절·시간 초과·기타 실패·한도 시점 미완료를 배타적으로 분류한다. ‘처리 여부 불명확’은 별도 속성이다. 예를 들어 시간 초과 건은 실패 한 건이며, 별도 미완료 요청으로 다시 더하지 않는다.
- 공유 기록은 측정 호출 수 범위로 제한한다. 본문 전체나 인증정보를 저장하지 않고, 성공 판정에 필요한 요약과 오류 코드를 남긴다. JTL의 `sample_variables`로 연결하고 대상 실행 종료 후 정규화된 결과로 내보낸다.
- 감시 스레드는 공유된 호출 기록과 중단 신호만 갱신하고 다른 실행 주체의 JMeter 변수나 `SampleResult`를 직접 바꾸지 않는다. 요청이 복귀한 PostProcessor가 자기 기록을 읽어 시간 초과를 실패로 반영한다. JTL의 늦은 정상 응답을 정규화 단계에서 성공으로 되살리지 않는다.
- 준비 실패·오류가 나도 조용히 성공 결과를 만들지 않는다. JTL·정규화 결과·실행 기록 사이에 누락·중복이 있으면 기록 불완전으로 판정한다.
- 기록 완료 여부는 결과 파일 존재만으로 판단하지 않는다. 정상 종료 표식·시도 수 검산·최종 조회 결과가 모두 필요하다. 강제 종료로 호출 기록을 복구하지 못하면 해당 건수는 ‘알 수 없음’으로 남기며 추정하여 채우지 않는다.

## 7. 시간 초과와 중단 해결

### 기본 한도 옵션만으로 충분하지 않은 이유

HTTP의 연결/읽기 한도와 JDBC 쿼리 한도는 요청 전체 호출의 마감과 같지 않다. JDBC Sampler가 인터럽트를 받아 즉시 끝난다고도 가정하지 않는다. 테스트 종료와 서버의 실행 취소는 별개다.

### 논리적 마감과 늦은 응답

1. 호출 직전 단조 증가 시계로 시작 시각과 요청별 마감을 기록한다. 연결 확보 대기부터 마감에 포함한다.
2. 프로세스 내부의 제한된 감시 기능이 마감까지 결과가 결정되지 않은 기록을 시간 초과로 한 번만 결정하고 중단 신호를 세운다. 스레드별 별도 감시 프로세스는 만들지 않는다.
3. 응답 복귀와 시간 초과 판정은 같은 호출 기록에서 원자적으로 경쟁한다. 한 요청은 한 번만 결과를 결정한다. 복귀 시점에도 마감을 검사하여 감시 실행이 늦었다는 이유로 마감 이후 응답을 성공시키지 않는다.
4. 뒤늦게 응답이 와도 이미 기록한 시간 초과를 성공으로 바꾸지 않는다. 늦은 반환·응답 내용은 보조 관찰로만 남긴다. 마감과 감지 시각은 별도 기록하여 감시 지연을 숨기지 않는다.
5. 통신 한도는 막힌 호출에서 빠져나오는 보조 수단이다. HTTP 연결/응답 제한과 Connector/J 통신 설정은 요청 한도와 대응시켜 기록한다. 서버에 별도 취소 요청을 보내지 않는 범위에서 구성하고 실제 동작을 지연 응답 검증으로 확인한다. DB의 쿼리 제한 옵션으로 서버 취소 의미를 조용히 추가하지 않는다.

전체 마감도 작업 허용·응답 복귀에서 직접 검사한다. 예약 콜백이 제때 실행된다고 가정하지 않는다. 전체 마감 후 호출 시작을 막고, 반환이 늦으면 요청별 마감과 전체 마감 중 앞선 기준에 따라 시간 초과/미완료를 구분한다. 본문 수신이 마감 전인 경우와 수신 후 분류 작업이 늦은 경우를 혼동하지 않는다. 파일럿에서 발견한 실제 경계 오류와 회귀 결과는 실행 기록에 보존한다.

감시는 준비 단계에서 만든 단일 스케줄 실행기를 사용하며 요청마다 운영체제 스레드를 만들지 않는다. 완료된 요청의 예약을 취소·제거하여 대기 감시 작업 수를 진행 중 요청 수 수준으로 제한한다. 호출 기록은 최대 N건을 보존한다. 감시기 시작 실패·미처리 예외도 실행 실패로 연결하며 감시 없이 시험을 계속하지 않는다.

### 중단과 다음 회차 금지

- 시간 초과·응답 유실·HTTP 500·DB 연결 단절 등 변경 여부를 확인하지 못하는 실패는 기본 비교 통과가 아니다. 새 작업 허용을 중단하고 해당 측정 묶음을 중단한다. 중단 신호 전에 이미 허용된 진행 중 요청은 즉시 취소됐다고 주장하지 않는다.
- 중단 검사와 작업 허용의 경계를 공유 상태에서 조율한다. 이미 허용된 요청은 C개 이하이며 시작·복귀·시간 초과 중 어느 상태인지 남긴다. 중단 뒤 새 업무를 임의로 이어붙이지 않는다.
- 전체 한도에 도달하면 새 작업을 막고 아직 결과가 결정되지 않은 호출을 미완료로 기록한다. 개별 시간 초과로 먼저 결정된 요청을 다시 미완료로 분류하지 않는다.
- 호출 반환과 클라이언트 종료를 한도 내 기다린다. 끝나지 않으면 실행 담당이 **자신이 시작한 JMeter 프로세스만** 종료한다. 이것을 서버 작업 종료의 증거로 사용하지 않는다. DB·Mini Redis 서버는 자동 종료하지 않는다.
- 종료가 불명확한 실행은 실패 기록과 미해결 표식을 남기고 묶음을 끝낸다. 실행 담당은 다음 초기화·다음 대상·다음 회차·자동 재실행을 하지 않는다. 새 실행도 해당 표식이 있으면 거절한다.
- 실행 담당은 최초 변경 요청을 허용하기 전에 진행 중 표식을 디스크에 남긴다. 정상 종료·기록 검산·최종 조회까지 확인한 경우에만 정상 종료로 전환한다. 도중 프로세스가 사라지거나 결과를 쓰지 못하면 남은 표식으로 새 묶음을 차단한다. 표식 기록 자체가 실패하면 요청을 보내지 않는다.
- 복구는 별도 사람 확인 대상이다. 최종 수치가 몇 번 같거나 GET이 성공했다는 이유만으로 이전 작업 종료를 인정하지 않는다. 필요한 서버 상태 확인·시험 전용 환경 재준비를 승인받은 뒤 새 묶음을 시작한다.
- 형식 오류처럼 완료 응답을 받은 명시적 거절도 기본 비교 실패다. 처리 여부가 명확한 거절만 있다면 해당 대상 실행의 나머지 N건은 기록을 위해 완료하되, 실패 실행을 정상 회차로 교체하지 않고 묶음을 종료한다. 진행 중 처리 여부 불명확 오류가 생기면 즉시 앞의 중단 경로로 전환한다.

## 8. 집계·실행 순서·환경 고정

- 기본 비교는 C=`1,10,50,100` 순서로 수행한다. C별 회차 1·3·5는 Mini Redis → MySQL, 2·4는 MySQL → Mini Redis다. 각 대상 실행은 별도 JMeter 프로세스이며 대상들은 동시에 실행하지 않는다.
- S3-01은 N=100, C=100으로 위 성공·최종 수치를 확인한다. S3-02의 부하 N과 혼동하지 않는다. 기본 성능 결과에는 S3-01·파일럿·워밍업·최종 조회를 넣지 않는다.
- 정상 실행의 불변 조건: 시도=N, 결과가 결정된 요청=N, 성공=N, 다른 결과=0, 최종 수치=N. 각 주체의 진행 중 요청은 최대 1건이고 전체는 C 이하이다.
- 중단 실행은 계획 N, 실제 시도, 결과별 건수, 아직 시도하지 않은 수를 구분한다. 기록이 완전할 때만 `시도=결과별 합계`, `N=시도+미시도`를 검산한다. 강제 종료로 실제 시도를 모르면 검산 불가를 명시한다.
- 성공 처리량은 성공 건수/전체 요청 실행 구간이다. 개별 지연 평균의 역수나 JMeter 기본 전체 요청 처리량으로 대신하지 않는다. 성공률은 성공/실제 시도이며 분모 0은 수치 없음이다.
- 성공 지연의 p50·p95·p99는 동일한 계산법으로 구한다. 제안 계산법은 정렬한 m개 표본에서 `h=(m-1)*p` 위치를 선형 보간하는 방식이다. p50은 중앙값과 일치한다. 성공 표본 1개는 세 지표 모두 해당 표본, 0개는 수치 없음이다. 실패·시간 초과를 성공 분포에 넣지 않는다.
- 회차별 지표를 먼저 계산하고 5회 중앙값·최솟값·최댓값을 구한다. 기본 실패 회차가 있으면 ‘5회 기본 비교 통과’ 요약을 만들지 않는다. 부분 관찰은 실패·미실행 회차를 드러낸 채 남긴다.
- JMeter 기본 HTML 보고서는 보조 자료다. 결과 원본은 요청별 기록과 전체 구간 기록이며 5회 집계는 별도 수행한다. 대시보드가 서로 다른 백분위수 추정법이나 실패 포함 분포를 사용해도 합의한 주 지표를 바꾸지 않는다.
- 부하 실행은 GUI가 아닌 명령행 모드로 한다. 본 측정 중 상세 결과 트리·본문 출력·실시간 그래프를 켜지 않는다. JTL은 필요한 열만 버퍼링하여 저장하고 행별 강제 디스크 반영은 하지 않는다. 그에 따른 비정상 종료 시 기록 유실 가능성은 기록 불완전 판정으로 처리한다.
- 시험 계정·비밀번호는 환경 또는 사용자 전용 비밀 파일에서 읽으며 JMX·버전 관리 파일·명령행 인자·결과에 쓰지 않는다. 로그 오류의 접속 문자열도 비밀을 제거한다.

## 10. 병목 구간 확인: 기본 비교와 별도 진단

### JMeter만으로 알 수 있는 범위

| 관찰 | 말할 수 있는 것 | 그것만으로 단정할 수 없는 것 |
| --- | --- | --- |
| HTTP Connect Time 증가 | 연결을 얻거나 수립하는 경로의 비용 증가를 조사할 근거 | 서버 저장소 연산이 느리다는 결론 |
| HTTP Latency 증가 | 첫 응답을 기다리는 전체 경로가 길어짐 | 순수 서버 처리 시간, OS 대기와 저장소 시간의 분리 |
| HTTP Elapsed와 Latency 차이 | 응답 수신 후반부의 비용을 조사할 근거 | 네트워크만의 비용이라고 단정 |
| JDBC Connect Time | 풀에서 연결을 확보하는 경로를 조사할 근거 | HTTP 접속 시간과 동일한 의미의 시간 |
| JDBC Elapsed 증가 | 드라이버 호출 전체가 느려짐 | 행 잠금·디스크 기록·CPU 중 어느 원인인지 확정 |

구간의 백분위수끼리 빼서 새 구간의 p95·p99를 만들지 않는다. 같은 요청의 짝지어진 관찰만 비교한다. 서로 다른 프로세스의 단조 증가 시계는 기준점이 같다고 가정해 시각을 직접 빼지 않는다.

### 진단 실행안

1. 기본 결과에서 처리량 증가가 멈추거나 p95·p99가 커지는 C와 C=1을 선택한다. 같은 N·요청 내용·서버 처리 구조를 유지한 별도 진단 실행으로 재현한다. 파일럿 결과와 기본 비교 결과를 섞지 않는다.
2. JMeter·Mini Redis·MySQL의 CPU·메모리·연결 상황을 같은 실행 구간에서 관찰한다. 부하 발생기가 먼저 막힌 경우 서버 최대 처리량이라고 보고하지 않는다. 권한·도구가 없으면 해당 원인은 미관찰이다.
3. Mini Redis 진단은 시험 전용 실행에서 기존 `create_app(storage)`와 순차 서버를 유지하고, 요청 처리 구간과 `MiniRedis.incr` 호출 전후를 계측하는 안이다. 테스트 전용 감싸기로 전달·계측하며 제품의 `app.py`·`storage.py` 계약이나 응답 필드는 변경하지 않는다. 상세 계측 코드는 별도 구현 승인 후에만 추가한다.
4. 진단 요청에만 상관관계 식별 헤더를 사용하여 클라이언트 표본과 서버 관찰을 대응시키는 안이다. 추가 헤더·계측 비용이 있으므로 진단 수치를 기본 성능으로 제시하지 않는다. 서버 관찰 시작 이전의 네트워크·OS 연결 대기는 여전히 구분되지 않는다.
5. MySQL 진단은 기존 `performance_schema`의 문장·대기 자료를 사용한다. 연결 식별은 준비 단계에서 수집하고 측정 증가마다 별도 조회를 추가하지 않는다. `events_statements_history_long`의 `THREAD_ID`·`EVENT_ID`·`TIMER_WAIT`·`ROWS_AFFECTED`와 `data_lock_waits`의 대기/차단 관계를 확인한다. 자료 수집 설정과 권한·이력 용량·유실을 기록한다.
6. `LOCK_TIME`은 테이블 잠금 대기 지표이며 InnoDB 행 잠금 대기 전체라고 부르지 않는다. `data_lock_waits`는 현재 대기 관계로서 짧은 대기를 놓칠 수 있다. 표본이 없다고 잠금 대기가 없었다고 단정하지 않는다. `TIMER_WAIT`는 해당 이벤트의 전체 경과 시간이지 순수 CPU 시간이나 디스크 대기만이 아니다.
7. 계측 설정은 시험 전용 환경에서만 변경 승인을 받고 적용한다. 기본 비교 중 전체 DB 계측을 자동 활성화하지 않는다. 기존 설정과 복구 절차를 기록한다. 이력·관찰 누락이면 원인 판정을 보류한다.
8. 원인을 확인하고 개선을 승인받으면 같은 조건의 기본 비교를 다시 수행한다. 진단을 끈 결과로 정확성·성공률·성능 변화를 판단한다.

이 설계는 ‘느린 조건을 발견 → 관련 구간을 좁힘 → 별도 관찰로 원인을 확인’하는 절차다. JMeter만으로 모든 요청 대기·통신·서버·저장소 시간을 완전히 분해할 수 있다는 보장은 하지 않는다.

## 11. 구현 산출물과 진입 조건

### 실행 입력·출력 계약안

- 입력: 실행 단계(도구 검증/파일럿/기본 비교/진단), 대상별 접속 정보, 결과 위치, 설정 식별자. 기본 비교는 확정된 N·요청 한도·전체 한도·준비/종료 한도와 버전 기록을 필수로 받는다. 누락되면 시작하지 않는다.
- 파일럿의 N 후보는 1,000과 10,000으로 명시한다. 요청 한도 5초는 파일럿 입력으로만 기록한다. 파일럿 결과에서 본 측정 설정을 자동 선택하지 않고 실행 시간·변동·오류와 함께 사용자에게 제시하여 고정한다.
- 실행 담당은 한 대상 실행의 설정 파일과 결과 위치를 JMeter에 전달하고 종료까지 감시한다. 비밀은 일반 설정과 분리한다. 자식 프로세스의 종료 코드가 0이어도 결과 판정이 실패하면 성공으로 반환하지 않는다.
- 호출 기록은 최소한 `run_id`, `phase`, `thread_name`, `request_sequence`, `start_ns`, `deadline_ns`, `decision_ns`, `return_ns`, `outcome`, `processing_unknown`, `client_elapsed_ns`를 갖는 형식을 제안한다. 논리적 시간 초과의 `decision_ns`는 마감이며 실제 관찰 시각도 별도 보존한다. 늦은 반환에서 `decision_ns`와 `outcome`을 덮어쓰지 않는다.
- 기본 JTL의 `elapsed`·`Latency`·`Connect`와 성공/오류 판정을 보존한다. 요청 식별 조합이 같아야 정규화 기록과 대조할 수 있다. `return_ns`는 반환이 없으면 비어 있고, 시간 초과 표본의 `client_elapsed_ns`는 성공 지연으로 사용하지 않는다.
- 대상 실행 결과는 계획·실제 시도·결과별 건수·전체 구간·최종 수치·정확성·기록 완전성·미해결 여부를 구분한다. 종료 상태가 불완전하면 최종 수치와 처리량을 정상 완료 지표로 만들지 않는다.
- 묶음 결과는 실행 예정 목록과 실제 실행 목록을 함께 보존한다. 중단 후 실행하지 않은 조건도 미실행으로 남겨 결과 목록에서 사라지지 않게 한다.

- 진단 계측은 기본 시험 구현의 필수 종속성이 아니다. 구체적인 시험 전용 계측 파일·헤더 이름은 진단 구현을 시작할 때 승인받는다. 기본 비교를 서버 계측 추가 전까지 막지는 않는다.
- 구현 승인 후 M3 검증과 코드 검토 회귀를 작성·실행했다. 도구·드라이버 버전은 실제 환경과 맞춰 고정하고, 테스트 assertion 실패·미구현·도구 미설치를 구분하여 실행 기록에 남긴다.
- Groovy 코드는 파일 기반·컴파일 캐시 사용으로 구성한다. 실행 단계와 대상은 인자로 전달하고 실행마다 다른 문자열을 스크립트 소스에 삽입하지 않는다. 같은 조율·계측 경로를 준비/워밍업에서 실행하여 본 측정 중 최초 컴파일이 발생하지 않는지 확인한다.
- 파일럿 실행 전에 도구 검증과 격리 시험 환경이 필요하다. 본 측정에는 추가로 N·시간 한도의 고정과 S3-01 통과가 필요하다. 미정 수치를 코드 기본값으로 숨겨 확정하지 않는다.
- 배포 자동화·분산 부하·대시보드 서비스·제품 서버 교체·상시 추적 플랫폼은 포함하지 않는다.

## 12. 근거와 검증 한계

- [JMeter 구성 요소](https://jmeter.apache.org/usermanual/component_reference.html): Throughput Controller 전역 횟수, HTTP/JDBC 요청·연결, 조율 범위.
- [ThroughputController 소스](https://github.com/apache/jmeter/blob/master/src/components/src/main/java/org/apache/jmeter/control/ThroughputController.java): 전역 실행 횟수의 동기화. 선택 버전의 실제 반복 배치는 M3-01·02로 별도 확인한다.
- [JMeter 시간 용어](https://jmeter.apache.org/usermanual/glossary.html), [SampleResult](https://jmeter.apache.org/api/org/apache/jmeter/samplers/SampleResult.html), [기록 설정](https://jmeter.apache.org/usermanual/properties_reference.html): Elapsed/Latency·밀리초 결과·추가 기록 변수.
- [JDBC Sampler 소스](https://github.com/apache/jmeter/blob/master/src/protocol/jdbc/src/main/java/org/apache/jmeter/protocol/jdbc/sampler/JDBCSampler.java): 연결 확보·실행·풀 반환을 포함하는 경과 시간과 오류 연결.
- [JMeter 실행 권장사항](https://jmeter.apache.org/usermanual/best-practices.html), [보고서 계산](https://jmeter.apache.org/usermanual/generating-dashboard.html): 명령행 실행·기록 비용·백분위수 방식 차이.
- [Werkzeug 서버 소스](https://github.com/pallets/werkzeug/blob/main/src/werkzeug/serving.py): 연결 종료 동작. 설치 버전과 실제 동작은 실행 준비 시 확인한다.
- [MySQL 문장 이벤트](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-events-statements-current-table.html), [행 잠금 대기 관계](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-lock-waits-table.html): 진단 자료의 의미와 한계. 8.4 문서는 참고 기준이며 실행할 MySQL 버전을 자동 확정한 것이 아니다.
- 문서·소스 조사로 확인한 지원 기능과 실제 시험 통과를 구분한다. 실제 M3·S3 실행 범위와 미검증 항목은 [실행 기록](03-performance-test-worklog.md)을 따른다.
