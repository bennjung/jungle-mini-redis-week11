# 3. 정확성을 유지한 성능 비교

## 상태와 근거

- 비교 목적·요청 경로·정확성 판정·부하 방식·반복 및 집계 절차는 사용자와 합의했다. 파일럿 결과를 검토한 뒤 사용자가 **N=10,000, 요청별5초, 전체360초, 준비30초, 종료15초**로 확정했다. 전체 마감 회귀 수정·종료 확인 후 실패 원자료를 보존하고 새 묶음으로 파일럿 재확인·본 측정을 진행하도록 승인했다. 조건 확정이 실행 완료를 뜻하지는 않는다.
- 요구사항 원문: [phase.md](../phase.md)의 미니 Redis 사용 전후 성능 차이 비교.
- 이 문서는 사용자 기능이 아니라, 사용자가 선택한 경합 문제의 성능 가정을 확인하는 검증 시나리오다.
- 공통 개발 흐름: [AGENTS.md](../../AGENTS.md).
- 선행 문서: [2. 같은 카운터의 동시 증가](../scenario_02_concurrent_counter/02-concurrent-counter-scenario.md). 숫자 저장·증가·성공 응답은 [02 통합 결론](../scenario_02_concurrent_counter/02-concurrent-counter-integrated-review.md)과 최신 구현을 따른다. 이번 비교는 실제 숫자 `value`를 사용하며 문자열 숫자를 자동 변환하지 않는다.
- 개인 검토 메모는 검토 과정의 기록이다. 이 문서와 다른 과거 제안·미정 표시는 현재 계약을 대체하지 않는다.
- 성능 시험 도구는 **Apache JMeter**로 확정했다. 구체적인 실행 구조·별도 처리·도구 검증·병목 진단 설계안은 [JMeter 테스트 설계](03-jmeter-test-design.md)를 따른다. 기존 pytest 기능 테스트는 유지하며, 새 내부 설계안과 확정된 행동 계약을 구분한다.
- 실행 결과: 측정 도구83개 검증, 확정 S3-01 양쪽, 파일럿8개, 본 측정40개를 통과했다. 본 측정400,000건 모두 성공·모든 실행 최종 수치10,000이다. [실행·분석 기록](03-performance-test-worklog.md)과 [집계 JSON](03-performance-results.json)을 참고하며, 현재 구성의 비교 완료를 동일 내구성 보장이나 모든 작업의 우위로 일반화하지 않는다.
- 아래 기록된 실행 결과·수치는 Flask 3.1.3·Werkzeug 3.1.9 서버 기준이다. FastAPI/uvicorn 전환 뒤 같은 조건의 재측정은 별도 작업이며, 기존 수치를 FastAPI 결과로 바꾸지 않고 이 문서의 비교 계약도 변경하지 않는다.

## 비교 목적과 완료 판단

- 같은 카운터의 증가분을 잃지 않는 조건에서 Mini Redis와 MySQL의 처리량·응답 지연·성공률을 비교한다.
- 미니 Redis가 어떤 상황에서 유용한지 살펴보고, 이번 구현이 느리다면 개선할 지점을 찾는다.
- 포함: 같은 카운터 작업, 동일한 정확성 기준, 클라이언트 요청·응답 경로의 성능과 실패 기록.
- 제외: 모든 작업에서의 성능 우위, 측정 없는 디스크 입출력·잠금 병목 단정, 장애 복구 성능.
- 완료 판단: 합의한 조건으로 양쪽을 측정하고 정확성 및 성능 결과를 함께 기록한다. 성능 개선 여부와 과제의 비교 수행 여부는 구분하며, 개선이 없어도 비교 결과는 남긴다.
- 취약한 읽기·덮어쓰기 방식을 MySQL 기준선으로 사용하지 않는다. 동시 요청 수나 해시 테이블의 평균 상수 시간 접근만으로 병목·성능 우위를 단정하지 않는다.

## 비교 경로와 성공 판정

- Mini Redis: 클라이언트 → 기존 HTTP `POST /kv/incr` → `app.py` → `MiniRedis.incr` → HTTP 응답. 기존 단일 프로세스·순차 처리 보장을 유지하며 저장소 직접 다중 스레드 호출로 대체하지 않는다.
- MySQL: 클라이언트 → 드라이버 → MySQL → 드라이버 응답. 같은 카운터에 대한 원자적 증가를 사용한다. 비교만을 위해 MySQL에 별도 HTTP 서버를 붙이지 않는다.
- 비교 작업은 같은 카운터의 `1` 증가와 증가 성공 확인이다. Mini Redis는 합의한 증가 성공 응답을 확인한다. MySQL은 요청별 자동 커밋을 사용하고 오류 없이 변경이 확정되며 변경 행 수가 `1`인지 확인한다. 측정은 변경 확정된 응답까지 포함하며 실제 설정을 기록한다.
- MySQL에서 개별 변경 직후 `value`를 얻기 위한 추가 조회는 하지 않는다. 모든 증가 완료 후 별도 최종 조회로 총 증가분을 확인한다. 이 조회를 개별 명령 직후 `value` 반환 검증으로 해석하지 않는다.
- Mini Redis의 변경 직후 `value` 반환 계약은 유지한다. 그 기능 검증은 [02 테스트 케이스](../scenario_02_concurrent_counter/02-test-cases.md)에서 수행하며, MySQL에도 같은 반환 기능을 추가하도록 강제하지 않는다.
- 이번 결과는 **현재 구성의 사용 성능 비교**다. 통신 방식·서버 처리·변경 확정 비용이 포함되므로 전체 차이를 저장소 내부 연산만의 차이라고 단정하지 않는다. 과거 메모의 HTTP 없는 저장소 직접 비교는 이번 확정 경로가 아니다.
- Mini Redis의 메모리 반영과 MySQL의 디스크 보존·복구 보장을 같다고 가정하지 않는다. MySQL의 디스크 기록 설정과 보장 차이를 결과에 기록한다. 이 비교를 위해 장애 복구 기능을 새로 요구하지 않는다.

## 측정 시나리오

### S3-01. 비교 대상의 정확성 확인

- 사전 상태: 양쪽에서 같은 대상 카운터의 `value`는 실제 숫자 `0`이다. 공개 저장 경로로 준비하고 성공을 확인한다. Mini Redis 내부 상태에 숫자를 직접 넣어 우회하지 않는다. 다른 변경 요청은 없다.
- 입력·행동: 양쪽에 같은 카운터를 `1`씩 증가시키는 요청을 각각 `100`건 동시 진행시킨다.
- 검증 시점: 각 대상의 모든 요청이 성공 응답을 반환한 후 최종 조회 완료 시.
- 기대 결과: 양쪽 모두 100건이 위 성공 판정을 충족하며 최종 조회한 `value`는 실제 숫자 `100`이다.
- 유지 조건: 한쪽의 정확성을 낮춰 속도를 높인 결과를 동등한 비교로 제시하지 않는다.
- 실패 판정: 거절·연결 실패·시간 초과·미완료가 한 건이라도 있거나 최종 수치가 다르면 통과하지 않는다. 실패 요청을 제외해 통과시키지 않고 재시도하지 않는다.
- 시간 한도는 요청5초·전체360초·준비30초·종료15초로 고정한다. 파일럿에서의 확인과 이 확정 조건으로 실행한 검증을 구분한다.

### S3-02. 동일 작업량에서 성능 측정

- 사전 상태: 확정 조건의 S3-01 정확성을 확인했고 N=10,000·시간 한도를 환경·연결 설정과 함께 기록했다. 아래 절차에 따라 워밍업 후 대상 카운터를 실제 숫자 `0`으로 초기화하고 성공을 확인한다. 다른 변경 요청은 없다.
- 입력·행동: 같은 카운터에 `1` 증가 요청을 총 **10,000건** 실행한다. 동시 요청 수 `1`·`10`·`50`·`100`을 각각 독립 측정하며, 각 조건에서 양쪽을 5회 비교한다. 요청별5초·전체360초·준비30초·종료15초를 적용한다.
- 검증 시점: 각 측정 종료 후 요청 결과와 최종 `value`의 조회를 확인한 시점.
- 기대 결과: 성공 처리량, 성공률, 성공 응답의 p50·p95·p99, 요청 결과별 건수와 최종 `value`를 양쪽 모두 기록한다. 기본 비교의 통과 조건은 N건 모두 성공, 시스템 실패·시간 초과·예상하지 못한 거절 0건, 최종 수치 N이다.
- 유지 조건: 실패를 숨기거나 작업량·정확성 보장이 다른 결과를 같은 조건처럼 제시하지 않는다. 실패가 없어도 최종 수치가 다르면 정확성 실패다.
- 주의: 확정 조건과 다른 예비 실행·중단 결과를 본 측정 5회에 섞지 않는다.

## 부하와 연결

- N은 **전체 시도할 요청 수**, 동시 요청 수는 **한 번에 진행할 최대 요청 수**다. 실패가 있다고 N을 성공 건수로 바꾸지 않는다. S3-01의 100건과 S3-02의 N을 구분한다.
- 동시성 `1`은 요청 → 응답 → 다음 요청을 N건 반복하는 조건이다. 경합이 없는 기본 비용을 관찰한다.
- 동시성 `10`·`50`·`100`은 각 실행 주체가 한 요청의 결과를 받은 뒤 다음 요청을 보내 전체 N건까지 동시 진행 수를 유지한다. 종료 직전에는 남은 작업 수만큼 줄어든다. 묶음 전송·재시도는 하지 않는다.
- 이 방식은 응답이 느려지면 다음 요청도 늦어진다. 고정 동시성에서의 성능이며, 응답과 무관하게 초당 일정 요청이 유입되는 부하의 수용 한계를 입증하지 않는다.
- 각 대상·동시성·회차마다 새 연결 자원을 준비하고 종료한다. MySQL은 동시 실행 주체별 전용 연결을 측정 전에 준비하고 재사용한다. HTTP는 실행 주체별 클라이언트 상태를 준비하고 연결 재사용을 시도하되, 기존 서버가 응답 후 연결을 닫는 경우를 허용한다. 서버를 바꾸지 않으며 이때 필요한 요청별 재연결 비용은 측정에 포함한다. 모든 HTTP 연결 생성이 측정 전에 끝났다고 주장하지 않는다.
- 클라이언트 객체의 재사용과 실제 연결 재사용을 구분해 확인하고 실제 연결 수·재사용 여부를 기록한다. 측정 중 새 연결이 필요하면 그 비용을 사후에 임의로 빼지 않는다. 자동 재연결로 요청을 다시 보내지 않는다.

## 시간 측정과 반복 절차

각 대상·동시성·회차마다 다음 순서를 적용한다.

1. 연결 자원을 준비한다.
2. 같은 요청 경로로 워밍업 100건을 실행하고 완료를 확인한다. 측정 구간의 첫 100건을 버리는 방식이 아니라 별도 준비 실행이다.
3. 카운터를 실제 숫자 `0`으로 초기화하고 성공을 확인한다.
4. 준비된 실행 주체들의 요청 시작을 허용하기 직전에 전체 측정을 시작한다.
5. 총 N건을 실행하며 요청별 시간과 결과를 기록한다.
6. 마지막 요청의 성공·실패·시간 초과가 결정된 직후 전체 측정을 종료한다. 전체 한도 내 끝나지 못한 실행은 미완료로 기록한다.
7. 남은 작업의 종료를 확인하고 최종 `value`를 조회해 정확성을 판정한다. 종료를 확인하지 못하면 완료 시점의 최종 수치를 확인했다고 주장하지 않는다.
8. 연결 자원을 종료한다.

- 개별 지연은 클라이언트 요청 호출 직전부터 응답 본문 또는 드라이버 결과 수신 완료까지다. 호출 내부의 연결 확보 대기·전송·서버 대기·처리·응답 수신을 포함한다. 결과 검증·상세 출력은 수신 시각 기록 후 수행한다.
- 아직 호출하지 않은 나머지 작업의 대기는 개별 지연에 넣지 않지만 전체 실행 시간에는 반영된다. 초기 연결·워밍업·초기화·종료 후 최종 조회·연결 종료는 측정에서 제외한다.
- 각 동시성에서 대상별 5회 측정한다. 실행 순서는 1회 Mini Redis → MySQL, 2회 MySQL → Mini Redis처럼 회차마다 교차한다. 양쪽을 동시에 측정하지 않는다.

## 지표와 판정

- 성공 처리량: 성공 건수 ÷ 전체 요청 실행 시간(초). 분모에는 실행 중의 대기와 실패 처리 시간도 포함한다. 빠른 거절을 증가 성공으로 계산하지 않는다.
- 성공률: 성공 건수 ÷ 전체 시도 건수. 시도 건수와 원래 계획 N을 함께 기록하고, 미완료가 있는 실행에서 N건을 모두 실행했다고 주장하지 않는다.
- 요청 결과: 성공·거절·연결 등 기타 실패·시간 초과·미완료를 구분해 중복 없이 집계한다. 시간 초과도 실패 총계에 포함하며, 실패 총계와 세부 항목을 다시 더하지 않는다. 성공처럼 보이는 응답이라도 합의한 성공 형식·판정을 충족하지 못하면 성공으로 세지 않는다.
- p50·p95·p99: 성공 요청 지연을 정렬했을 때 각각 50%·95%·99%가 그 시간 이내에 완료되는 지점이다. p50은 중앙값이며 p95·p99는 느린 쪽 요청을 관찰한다. 실패 응답 시간과 시간 초과는 성공 지연 백분위수에 섞지 않고 별도 기록한다.
- 각 회차의 지표를 먼저 계산한 뒤 5회의 중앙값과 최솟값~최댓값을 기록한다. 요청 표본을 모두 합쳐 하나의 백분위수로 만들지 않는다. 회차별 원자료도 보존한다.
- 기본 비교는 시스템 실패·시간 초과·예상하지 못한 거절 0건과 정확성 통과를 요구한다. 실패한 회차도 남기고 성공할 때까지 대체 실행하거나 성공한 회차만 골라 5회 요약을 만들지 않는다.
- 실패가 있는 결과는 기본 비교 통과 결과와 분리한다. 별도 고동시성 스트레스 결과를 기록하더라도 실패율과 성공 처리량을 함께 제시하며, 실패한 기본 비교를 자동으로 스트레스 통과로 바꾸지 않는다.

## 시간 초과와 회차 간 격리

- 요청별 시간 초과는 파일럿의 출발점이던 **5초**를 본 측정 기준으로 확정했다. 전체 실행 한도는 **360초**, 준비 한도는 **30초**, 종료 확인 한도는 **15초**다. 서버의 처리 시간 제한을 새로 추가한다는 뜻이 아니다.
- 연결 실패·시간 초과 후 재시도하지 않는다. 시간 초과나 연결 종료가 서버의 미반영·취소·되돌리기를 뜻하지 않는다. 성공 건수만으로 실패 실행의 최종 수치를 계산하지 않는다.
- 이전 요청이 끝났음을 확인하기 전에는 같은 카운터를 초기화하거나 다음 회차를 시작하지 않는다. 종료 확인 한도15초 안에 확인하지 못하면 해당 실행을 미완료로 남기고 중단한다.
- 처리 종료가 불명확한 시간 초과·응답 유실 등의 실패에서는 새 요청 배분을 멈추고 측정 묶음을 중단한다. 이미 허용된 진행 중 요청이 취소됐다고 가정하지 않는다. 다음 회차 초기화나 자동 재실행 없이 미해결 상태를 남기며, 별도 확인 후 새 묶음으로 진행한다.

## 파일럿과 확정된 본 측정 조건

파일럿은 본 측정 전에 부하와 측정 도구가 적절한지 확인하는 예비 실행이다. 성능 우위를 결론 내리는 단계가 아니며 본 측정 5회에 섞지 않고 별도 기록한다.

1. 양쪽을 우선 1,000건으로 동시성 `1`·`10`·`50`·`100`에서 예비 실행하여 정확성·실행 시간·실패 여부를 확인한다.
2. 10,000건으로 늘려 실행 시간이 감당 가능한지, 결과가 지나치게 흔들리는지, 요청을 보내는 클라이언트가 병목은 아닌지 확인한다.
3. N을 1,000~10,000에서 하나 정하고 요청별 시간 초과·전체 실행 한도·남은 작업 종료 확인 한도와 함께 본 측정 전에 고정한다. N은 양쪽과 모든 동시성에 동일 적용한다. 범위로 충분하지 않으면 임의로 바꾸지 않고 재합의한다.

- 10,000건은 고정 정답이 아니라 후보 상한이다. 1,000건에서 느린 1%는 약 10건, 10,000건에서는 약 100건이므로 느린 요청을 더 관찰할 수 있지만 통계적 충분성을 보장하지는 않는다. 너무 짧은 실행의 흔들림과 반복 실행 비용을 함께 본다.
- 한쪽에 유리한 결과가 나온다는 이유로 N을 고르거나 본 측정 중 변경하지 않는다. 설정을 바꾼 실행은 기존 조건의 결과와 섞지 않는다.
- 장비·운영체제·버전·실행 위치·자원·서버 처리 설정·연결 수 및 실제 재사용·MySQL 변경 확정과 디스크 기록 설정을 고정하고 기록한다. 구체적인 환경과 사용 드라이버 등 호출 도구는 실행 준비 시 기록하며 이 문서에서 임의 선정하지 않는다.
- N=1,000 예비 실행은 양쪽·모든 동시성에서 통과했다. N=10,000은 예비 전체 한도120초에서 중단되어 나머지를 미실행으로 남겼다. 사용자가 N=10,000과 전체360초를 선택했으므로 회귀 수정 후 새 묶음에서 재확인한다. 실패 자료는 보존하며 새 결과로 덮어쓰지 않는다.
- 구현·사전 확인·파일럿·본 측정의 실제 결과는 [실행·분석 기록](03-performance-test-worklog.md)을 따른다. 예비 실행과 고정 조건의 본 측정을 구분한다.

## 원인 조사와 개선 전후 확인

- 전체 경로 측정에서 차이가 관찰되면 통신 대기·요청 처리·저장소 연산 등 관련 구간을 별도로 살펴본다. 구간별 측정은 전체 경로 비교를 대체하지 않는다.
- JMeter의 연결 시간·첫 응답 대기·전체 지연만으로 서버 내부 대기와 연산을 완전히 분리하지 않는다. 상세 진단은 [테스트 설계의 병목 구간 확인](03-jmeter-test-design.md#10-병목-구간-확인-기본-비교와-별도-진단)처럼 별도 실행하고 기본 성능 결과와 섞지 않는다.
- 잠금 대기나 디스크 입출력을 원인으로 주장하려면 별도의 관찰 근거를 남긴다. 클라이언트가 충분한 부하를 만들지 못한 것은 아닌지도 확인한다.
- 원인을 확인하고 개선한 경우 같은 작업·부하·측정 조건으로 다시 실행하여 정확성·성공과 실패·성능의 변화를 함께 기록한다. 개선하지 않았거나 개선 효과가 없어도 비교 결과를 남긴다.
- 5회 중앙값과 범위만으로 통계적 유의성을 입증했다고 주장하지 않는다. 별도의 개선 폭 합격 기준은 이번에 정하지 않았으며 비교 수행 완료와 구분한다.
