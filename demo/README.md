# 날씨 응답 재사용 데모

Open-Meteo의 날씨 응답을 기존 Mini Redis HTTP API에 1분간 저장한다.
날씨 화면은 데모 서버가 제공하며 두 서버를 각각 실행해야 한다. 위치별
좌표는 소수점 셋째 자리로 반올림해 원본 조회와 저장 키에 함께 사용한다.
캐시가 비어 있는 같은 장소의 요청이 겹치면 키별 갱신 락을 사용해 정상
경로에서는 한 요청만 Open-Meteo를 호출하고, 나머지는 저장된 응답을 재사용한다.
조회 버튼 두 번의 순차 데모도 그대로 유지한다.

## 실행

프로젝트 루트에서 한 터미널에 두 서버를 실행하려면:

```bash
.venv/bin/python demo/run.py
```

두 서버의 로그가 같은 터미널에 표시된다. `Ctrl+C`를 누르면 두 서버가 종료된다.
터미널에서는 GET은 청록색, LOCK ACQUIRE는 노란색, PUT은 초록색으로 표시한다.
터미널이 아닌 곳으로 출력을 전달하면 색상 코드 없이 표시한다.
조회 시작과 종료 사이에 GET(①), 락 획득(②), 원본 호출(③), 저장(④),
락 해제(⑤)를 표시한다. 번호는 동작 종류를 뜻하며, 경합 시 GET이나 락 획득이
반복될 수 있다. 여러 요청의 로그가 섞일 때는 요청 ID로 구분한다.

프로젝트 루트에서 의존성을 `requirements-dev.txt`로 설치한 뒤,
별도 터미널 두 개에서 각각 실행할 수도 있다.

```bash
.venv/bin/python app.py
```

```bash
.venv/bin/python -m uvicorn demo.weather_app:app --host 127.0.0.1 --port 8000 --workers 1
```

브라우저에서 <http://127.0.0.1:8000>을 열고 장소를 선택한다.
현재 위치는 브라우저 위치 권한이 필요하다. 권한을 거부해도 다른 장소를
선택할 수 있다. 실제 Open-Meteo 조회에는 인터넷이 필요하다.

## 실행 모니터

별도 탭에서 <http://127.0.0.1:8000/monitor>를 연다. 모니터는 데모 서버가 실제로
수행한 이벤트를 SSE로 받아 한 줄씩 표시한다.

- 연결된 순간 이후의 이벤트만 받는다. 새로고침하면 목록이 비워지고, 연결이
  끊긴 동안의 내역은 복구하지 않는다.
- GET, LOCK ACQUIRE, 원본 호출, PUT, LOCK RELEASE, 오류, 요청 종료를 표시한다.
  락 대기 중 100ms 간격으로 반복하는 GET과 락 획득 후 double-check GET도 각각
  한 줄로 보인다.
- 요청 ID는 락 토큰 앞 8자이며, 이벤트는 도착 순서대로 아래에 추가되고 화면이
  자동으로 따라 내려간다.
- 기존 터미널 로그와 색상은 그대로 유지된다. 모니터는 같은 이벤트를 브라우저로
  추가 전달하는 화면이다.
- 이벤트는 앱 메모리에만 있다. `demo/run.py`의 단일 워커 구성을 전제로 하며,
  다중 워커에서는 요청을 처리한 워커의 이벤트만 보일 수 있다.

SSE 원본을 터미널에서 확인하려면:

```bash
curl --no-buffer 'http://127.0.0.1:8000/monitor/events'
```

## 발표 준비와 시연

시연할 장소의 **해당 키만** 삭제한 후 조회 버튼을 두 번 누른다.
예를 들어 서울을 선택한다면:

```bash
curl --request DELETE --get 'http://127.0.0.1:5000/kv' \
  --data-urlencode 'key=weather:37.566:126.978'
```

이 명령은 해당 키의 기존 내용을 실제로 삭제한다. 다른 장소나 현재 위치는
같은 좌표 반올림 규칙으로 대상 키를 확인한 후 삭제해야 한다. Mini Redis를
재시작하면 모든 메모리 데이터가 사라지므로 초기화 방법으로 권장하지 않는다.

날씨 데모 서버 터미널에서 첫 조회의 키 부재·원본 호출·저장 성공과
두 번째 조회의 재사용·원본 호출 횟수 유지를 확인한다. 호출 횟수는 데모
서버 프로세스가 시작된 이후의 누적 횟수다. 모니터 탭을 함께 열어 두면 같은
과정을 브라우저에서도 확인할 수 있다. 저장소 또는 원본 오류는 화면에 오류를
표시하고 터미널에 기록한다.

## 같은 장소 동시 조회 (선택)

조회 버튼은 요청 중 비활성화되므로 한 탭에서는 순차 요청만 보낸다. 두 탭에서
같은 장소를 거의 동시에 조회하면 캐시 미스가 겹칠 수 있다.

- 미스가 겹치면 한 요청이 락을 얻어 Open-Meteo를 1회 호출하고, 다른 요청은
  100ms 간격으로 캐시를 확인하다가 저장된 응답을 재사용한다. 두 요청 모두
  200으로 응답한다. 대기는 최대 10초이며, 넘으면 502를 반환한다.
- 마감 시각 이후 도착한 캐시·락 응답은 늦은 응답으로 보고 성공으로 처리하지
  않는다. 늦게 획득한 락은 소유 토큰으로 해제한 뒤 502를 반환한다.
- 락 TTL은 10초이고 자동 연장하지 않는다. 소유 요청이 실패하면 락을 해제하고,
  대기 요청은 획득을 다시 시도해 원본 호출을 이어받을 수 있다. 이 실패 경로는
  Open-Meteo를 최대 2회 호출할 수 있다.
- 첫 요청이 먼저 저장을 마치면 두 번째 요청은 락 없이 일반 캐시 히트가 된다.
  어느 쪽이 되는지는 두 요청의 도착 시점에 따라 달라진다.

터미널에서 재현하려면 해당 키를 삭제한 뒤 두 요청을 거의 동시에 보낸다.

```bash
curl --silent --show-error \
  'http://127.0.0.1:8000/weather?latitude=37.5664&longitude=126.9784' >/dev/null &
curl --silent --show-error \
  'http://127.0.0.1:8000/weather?latitude=37.5664&longitude=126.9784' >/dev/null &
wait
```

두 요청이 실제로 겹치면 데모 서버 터미널에 `락 획득`, `락 경합 대기`,
`조회 성공(대기 후)`와 `원본 호출: 1회`가 요청 ID(락 토큰 앞 8자)와 함께 보인다.
첫 요청이 먼저 끝나면 두 번째는 `조회 성공`만 보일 수 있다. 원본 호출 횟수는 데모
서버 프로세스 기준 누적값이므로 비교 전에 시작 값을 확인한다.

```bash
.venv/bin/python -m pytest \
  tests/scenario_04_response_cache/test_weather_demo.py \
  tests/scenario_04_response_cache/test_weather_demo_lock.py \
  tests/scenario_04_response_cache/test_weather_demo_monitor.py -q
```

자동 테스트의 원본은 격리되어 있으며 Open-Meteo 실서비스 가용성을
보장하지 않는다. 동시 요청 테스트는 가짜 원본으로 정상 동시 성공·소유 실패
인계·대기 한도·락 만료 인계·늦은 락/캐시 응답·double-check 히트를 구분해
검증한다. 모니터 테스트는 SSE 전달 순서·연결 이후만 수신·락 대기 중 반복
GET·오류 이벤트를 검증한다. 실제 브라우저 두 탭의 도착 시점, 실제 Open-Meteo
네트워크, 다중 워커·다중 프로세스는 검증하지 않는다.
계약과 검증 경계는 [락 사용 계약](../resc/scenario_05_cache_lock/05-weather-demo-lock-usage.md)과
[실행 모니터 계약](../resc/scenario_04_response_cache/04-weather-monitor-contract.md)을
따른다. 기존 가짜 원본 시나리오는 별도다.
